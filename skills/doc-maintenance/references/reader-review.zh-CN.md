# 读者导向写作与审稿

[English](reader-review.md) · [使用的术语](reader-review.terms.yaml)

本文件拥有 NMG 的读者导向写作准则和审稿流程。起草、重组、压缩或发布面向读者的正文前，
先应用本规范。[治理设计](../../../docs/design/documentation-governance.zh-CN.md)负责文档归属，
并区分语义审稿与机械检查。

## 读者任务

明确读者是谁、要回答什么问题或完成什么动作、什么情况会读到这里，以及正文假定哪些知识。
先给答案或可用入口，再给可选背景。读者不应依赖作者的既往会话，才能判断怎么做或理解主张。

按材料选择结构，不把所有文档写成操作步骤，也不为满足模板添加空标题：

| 材料 | 组织中心 | 读者必须能判断 |
| --- | --- | --- |
| 教程 | 一个具体结果及其必要前提 | 如何得到并确认结果 |
| 操作或恢复指南 | 触发、前提、动作、结果与失败处理 | 是否应操作、做什么、何时停止或恢复 |
| API 或行为参考 | 查阅问题及适用合同 | 输入、输出、条件、例外与归属 |
| 架构或决策 | 问题、边界、机制与重要取舍 | 选择为什么适用、哪些地方不适用 |
| 实验或事故记录 | 问题、上下文、证据与限制 | 观察到了什么、为什么重要、什么仍未知 |

操作所需权限、环境和安全警告放在对应步骤之前。写明可观察的成功，以及相关失败、停止或
恢复路径。没有依据时不要发明恢复动作，明确保留未决情况。

## 局部阅读与内容归属

即使没有规则明文禁止另一种写法，也应遵循所属目录的既有命名风格。设计主题文件和目录
使用描述性的英文 kebab-case 和既有双语后缀。独立主题名不沿用父文档章节位置、生成式
截断哈希或 `— topic` 标签。有意义的版本、日期、有序步骤与稳定领域标识各有用途，不一律
删除。改名时迁移入链与术语 owner/anchor，也检查移出文件的相对链接。

章节使用可检索的主题名称。链接说明它提供必需定义/前提、替代路径还是可选背景；不要暗示
每篇链接都必须全文阅读。

正文解释自己的主题，按职责介绍直接子主题并链接其 owner。不镜像源码已经能恢复的目录或
符号清单。名称或结构造成具体歧义时，补局部定位说明。索引和生成摘要负责导航，不构成另一
规范。现行知识用仓库相对源码路径与章节，历史证据用可共享版本；私有 memory ID 不是必读材料。

一个动作或主张所需条件放在一起。精确类型、全量清单和深入解释可链接 owner，但须保留安全
使用所需的局部解释。章节过大时收窄职责，把其余完整职责路由出去；不为满足字节上限而拆散
耦合条件。

内容迁移使用[归属工作流](../SKILL.zh-CN.md#工作流)。设计、决策理由、测量证据、事故原因、
实现状态和未完成工作保持不同 owner，不把连续工作日志追加进合同。Git 保存编辑历史，但
删除工作日志不能删掉唯一必要的否决理由或失败解释。

## 压缩前先核对事实

比较修改前后的陈述，而不只比较长度。保留：

- actor、动作、对象及权威 owner；
- 作用域、前提、条件、顺序、时序和量词；
- 义务、许可、禁止、例外及失败后果；
- 成功标准、停止条件及有依据的恢复；
- 假设、不确定性和每项证据的边界。

不能把“可以”改成“必须”、“部分”改成“全部”、观察改成承诺，或条件保证改成无条件保证。
否定及其支配的条件须明确。必要时重复条件，避免改变它限定的动作。补充缺失解释，不把要求
压缩掉。

删除重复解释、装饰性主张、自我辩护和得出结论的过程稿，保留后续读者所需的结论、理由或
证据。历史证据不会因为写在现行指令旁边就成为本轮执行结果。

## 借鉴受控语言的表达

借鉴受控技术英语的清晰目标，不宣称符合 ASD-STE100。这里是 NMG 写作约定，不表示采用了
特定 STE 规则或其完整规范。

- 归属或责任重要时点明 actor，用直接动词代替含糊名词化表达。actor 无关或已明确时可用被动，
  不为机械禁止被动而歪曲主语。
- 一句话一个主要目的，一步一个主要动作。耦合条件与不可分割操作保持完整；拆句不能暗示
  只做一部分也有效。
- 条件放在受其限定的指令前或紧邻处，分清替代路径及选择方法。“如果”“除非”“只有”或代词
  含糊的短句并不是改进。
- 用具体对象和可观察结果，避免“妥善处理”“系统进行优化”“无缝工作”。“它”“这”“他们”有
  歧义时写出对象。
- 同一概念复用既有术语，不为措辞变化发明同义词，区分不同词义。使用既有
  [术语发现入口](../../../docs/design/documentation-governance.zh-CN.md#yaml-文件与查询合同)，
  不另建词典；必要时就地解释陌生术语。
- 保留正确的 literal API、命令、flag、路径、值和错误文字。解释含义，不静默翻译或简化标识符；
  示例与 owning 合同冲突时应修正并验证，不保留错误字节。明确占位符及替换要求。
- 原则同时适用于英文与中文。不对任一语言施加英文受控词表、词数目标或句长门禁。可读性
  不凌驾精确合同或必要论证。

## 审稿示例

示例解释准则，不形成新产品合同。把示例当作指令使用前，先核实其 owner。

**夸大保证**

修改前：“Gate 无缝保证文档质量。”

修改后：“`docs:check` 在已准入语料中拒绝重复同级标题，不判断正文是否准确。”

修改后点名检查，并把主张限制为观察的性质；范围由 [CI 契约](../../../docs/README.zh-CN.md#ci-契约)
拥有。

**缺少范围与恢复**

修改前：“术语搜不到时，创建定义。”

修改后：“限定目录的查询未命中时，扩大查询范围再搜索。局部未命中不证明仓库不存在该概念。”

修改后保留查询范围并给出下一步，不宣称创建时去重已实现；行为由
[查询合同](../../../docs/design/documentation-governance.zh-CN.md#yaml-文件与查询合同)拥有。

## 审稿与验收

对每个正在修改的阅读单元：

1. 选一个代表性读者问题或动作，按已写前提从入口跟读；不依赖私有会话，也不假设每条链接
   都要读。
2. 跟随适用分支直到答案或可观察结果。操作指南同时核对失败/恢复分支；参考和论证检查答案
   的范围与限制，不发明操作成功标准。
3. 按上述事实清单对照源码合同、旧文和改稿。操作含义受影响时实际验证命令或示例，标出未验
   环境与未决事实。
4. 迁移后双向跟随受影响引用。确认目标包含所需约束，而不只检查文件存在。
5. 核对配对文字的事实、义务、警告与命令，不比较段落数；保留生命周期元数据及其作用域。
6. 运行 [CI 契约](../../../docs/README.zh-CN.md#ci-契约)要求的检查，区分实际执行、作者审稿和
   独立审稿。

读者能找到并理解答案，或带必要条件完成动作；事实对照不存在未解决的重要遗漏/矛盾；适用
检查通过，单元才就绪。缺少前提、分支歧义、义务变化或无依据主张须修正，或在 owner 明确
解决，不能用绿色文风评分代替。记录剩余不确定性，不暗示它已解决。

说明哪些单元已改写/审稿，哪些仍待处理。结构检查、单个可运行示例或抽样审稿不证明全仓
文笔合格。本流程不要求新增小节哈希、审批数据库或机械文笔门禁。
