# NMG 事故复盘

[English](README.md)

事故记录。一次失误到达了它不该到达的地方——用户、`main`、已合并的 PR、已发布的数字——而值得留下的部分不是那一行修复，而是 _流程为什么让它通过_。

本目录是失败叙述的唯一归属。防止重演的规则不写在这里：它属于各自的 owner，由记录链接过去（[doc-maintenance](../../skills/doc-maintenance/SKILL.md)）。记录如何变成那条规则，见[消费端](#消费端从记录到规则)。

## 什么时候写一篇

三个条件同时成立才写：

- **机制隐蔽。** 机制不显然，慎重的工程师也得绕远路重新推导一遍。
- **系统性。** 它逃过的原因是测试、工具、校验或约定上的缺口，而不是一次笔误。
- **重新发现的代价高。** 它实际消耗过调试时间，而且还会再消耗一次。

普通的 bug 修复留在它自己的 commit 里。三个条件不全成立的候选，就是一段 commit body，不是事故复盘。

## 什么属于这里，什么不属于

| 事实                                             | Owner                                                                                                                     |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| 什么坏了、机制是什么、每一道安全网为什么都没拦住 | 本目录                                                                                                                    |
| 现在能防住同类问题的规则、校验或测试             | 它自己的 owner：测试文件、[CI 契约](../README.md#ci-contract)的一行、[Skill](../../skills/) 约定，或[决策](../decisions/) |
| 一次刻意的选择、它的替代方案与后果               | [`decisions/`](../decisions/)                                                                                             |
| 测到了什么                                       | [`experiments/`](../experiments/)                                                                                         |
| 对某个断言提出的、带复现步骤的质疑               | [`.rcp/counterexamples.yaml`](../../.rcp/counterexamples.yaml)                                                            |
| 尚未造成失败的已知缺口或未完成事项               | [improvement-areas](../design/improvement-areas.md)、[temporary-todo](../design/temporary-todo.md)                        |

每道防护写在 _Guardrails added_ 下面并链接过去，不要复述它的规则：规则的副本正是[精简清单](../../skills/doc-maintenance/SKILL.md#one-home-per-fact-and-the-slop-checklist)要删除的东西。

## 必需章节

头部块——第一个章节之前的所有行——只承载一个字段：

```markdown
**Status:** open | resolved
```

字段名与冒号在每一篇记录里都保持英文，`.zh-CN.md` 译文也一样；可以翻译的是章节标题（检查两种写法都认）。之所以让状态独占这个字段，是因为读者——以及下面的提升触发条件——要找的就是它。

`resolved` 表示防护已存在且已链接。`open` 表示失败机制已弄清、但尚未被拦下；未修复的事故同样要留下记录，因为机制本身才是重新发现代价最高的部分。失败日期留在 commit 里；需要时在 _Timeline_ 中说明。

每篇记录都要回答下面的问题，且每个章节非空。确实没有答案的章节要用文字说明（"未重建"），不能省略或留空；`npm run docs:check` 会因缺失或空章节失败。

| 章节              | 它回答的问题                                                              |
| ----------------- | ------------------------------------------------------------------------- |
| Executive summary | 30 秒能读完的一段：什么坏了、用平实语言说的根因、为什么逃过、可留下的教训 |
| Summary           | 发生了什么，详细到足以判断其余部分                                        |
| Impact            | 影响了谁或什么，以及这次失败**不可能**做到什么                            |
| Timeline          | 产生它的顺序，包括中间通过的评审与检查                                    |
| Root cause        | 机制本身，写到读者能预测同类问题的下一次出现                              |
| Guardrails added  | 现在能拦住这一类问题的每道防护，链接到拥有它的文件或文档                  |
| Lessons           | 超出本次事故、可以迁移的部分                                              |

## 命名与索引

记录按 `NNNN-slug.md` 编号放在本目录，从 `0001` 起连续。编号是引用某次事故的方式；日期在 git 里。记录通常配 `.zh-CN.md` 版本；缺译文只产生警告，与决策记录一致。

[索引](#索引)为每篇记录列出一行，并带上它的 **failure class**（失败类别）——这是文件名和标题都不具备的可检索维度。新增记录时在同一处变更里加行：`docs:check` 会因记录未进入索引、或索引行指向不存在的记录而失败。类别写成简短名词短语（"silent degradation"、"batch overwrite"、"verification blind spot"），让这一列累积成这个仓库反复重新发现的逃逸类别清单。

## 消费端：从记录到规则

记录是“这一类失败存在”的证据，不是防护。防护是下次会大声失败的机制。本节决定一类失败要不要、以及在哪获得防护。

**优先要门，而不是提醒。** 把一类失败提升到下面第一个能承载它的位置：

| 若这类失败……           | 它变成……                     | 归属                                                                     |
| ---------------------- | ---------------------------- | ------------------------------------------------------------------------ |
| 可被机器检测           | 一道校验                     | [CI 契约](../README.md#ci-contract)的一行、一个测试，或验证器的一个分支  |
| 是校验看不到的会话行为 | 一条常驻规则                 | 拥有该领域的 `AGENTS.md` 或 [Skill](../../skills/)，一到三行，链接到记录 |
| 是带真实替代方案的判断 | 一篇决策                     | [`decisions/`](../decisions/)                                            |
| 是局部约定             | 已经拥有该流程的文档中的一节 | 那份文档                                                                 |

**下列任一条成立就应当提升：**

- 这一类已经逃过两次——索引里出现两篇同一 failure class 的记录；
- 防护只以文字形式存在于记录里——记录声称有条规则，但没有任何校验、常驻文档或决策拥有它；
- 记录是 `open`，即这一类仍然活着。

**不要提升**只出现过一次、且预防成本高于失败成本、或机制在本仓库不可能复现的情况。这也是正当结果：记录在 `Lessons` 里写明（“没有规则，这只是一次故事”），而不是把问题悬空。

**每一篇记录都是事后写的。** 记录通常跟在失败之后、常常跟在修复之后，所以提升是一次对账而不是计划：在 _Guardrails added_ 里写出并链接已经存在的防护，再用上面的优先顺序检验它。如果唯一的防护就是记录自己的文字，那么这一类并没有被拦住，记录也就不算 `resolved`——要么补上防护，要么用 `Status: open` 说明为什么补不了。

把规则提升进 Skill 或 `AGENTS.md` 需要[审批](../decisions/implemented/2026-09-09-approval-tiers.zh-CN.md)。当语料显示本节失效时——比如类别不断累积却没有任何规则，或产生了并不需要的规则——按[元规则](../../skills/doc-maintenance/SKILL.md#meta-rule-nmgs-own-rules-are-governed)修订，而不是直接编辑。

## 分类与典型案例

索引把每篇记录的类别写成自由文本。本表是分类体系：一类失败有一个典型案例——读者应先读的那篇记录——和它产生的规则时，就占一行。规则列空着，就意味着这一类目前没有任何东西拦住它，而把它写下来正是意义所在。

| 类别                    | 典型案例                                     | 它产生的规则 |
| ----------------------- | -------------------------------------------- | ------------ |
| ----                    | --------                                     | ------------ |

类别名是简短名词短语，不是句子；在没有案例可指之前不凭空发明：第一篇记录命名它，第二篇确认它。记录的类别只写在索引里，不写在记录里，所以整个分类体系只有一处可读。
