# 0006 - 提交在第一个问题之前就失败了：线上端点的并发上限

[English](0006-concurrency-ceiling-on-the-live-endpoint.md) · [Terms used](0006-concurrency-ceiling-on-the-live-endpoint.terms.yaml)

**Status:** open

## Executive summary

一天里七次计分尝试都没有产出分数，而没有一次是失败在检索逻辑里。从干净网络对已部署端点实测：
并发 **1** 和 **2** 时所有请求都正常；到 **4** 就不行了——24 次 Add 里 7 次死在 120 秒的调用上限上，
Add 的中位数从 2.6 秒变成 106 秒；到 **16** 时，32 次连接里有 5 次根本没建立。

比赛方在开始前会探测 `/health`，所以**一次连接失败就足以让整次尝试作废**——那两次
`PARTICIPANT_ENDPOINT_UNAVAILABLE` 就是这种情况。当天更早的两次 `SEARCH_TIMEOUT · HTTP 504` 是同一机制
下沉一层的结果：请求一直跑到平台上限。

运维决定是**以并发 1 运行**：用墙钟时间换一次能跑完的评测。作废的尝试损失一切，慢一点的只损失几分钟。

## Summary

三个互相独立的限制，任何一个单独成立就足够：

1. **写路径在每次 CAS 重试里重做 MB 级的工作。** 一次 Add 要读用户 manifest、读写最多 8 MiB 的分区，
   并在对手赢下比较交换时最多重试十二次。并发对此没有帮助：写者在同一份 manifest 上串行，所以并发
   放大的是失败重试的次数，不是吞吐。
2. **并发到四个请求时，连接建立开始不可靠。** `/health` 的实测在 2.3–14.5 秒之间，其中两次落在 ~10 秒
   ——那正是相关客户端默认的建连超时。越过这条线，客户端根本拿不到状态码。
3. **每次部署都是一段不可用窗口。** 切换期间发出的请求被拒绝，当天发生两次，两次的错误都是
   `PARTICIPANT_ENDPOINT_UNAVAILABLE`，与网络故障无法区分。

## Timeline

- 05:18–10:43 220 次调用全部精确死在 120000 ms。诊断为：单次嵌入超时被写成 90 秒，而客户端会重试超时，
  再乘以单次检索里最多四十次的串行调用。修复为 10 秒单次超时、不重试超时、每种用途一次批量调用、
  25 秒检索预算、45 秒写入预算。
- 17:4x 把「端点」从嵌入索引身份里移除。此前它让每个既有用户的下一次写入都在重试循环里重嵌整个库，
  Add 从 53–76 秒回到 0.6–3.8 秒。
- 18:55 与 19:01 两次 `PARTICIPANT_ENDPOINT_UNAVAILABLE`，平台日志干净——那是「请求根本没到」的特征。
- 19:1x 从干净网络在并发 1、2、4、16 下实测。

## Root cause

实测，同一用户、每次运行使用全新用户、部署 `8d5d91d3`：

| 并发 | Add                                                             | Search              | 失败             |
| ---- | --------------------------------------------------------------- | ------------------- | ---------------- |
| 1    | 24/24 200，p50 **2.6 s**，max 21.9 s                            | 8/8，p50 7.2 s      | 无               |
| 2    | 16/16 200，p50 **3.6 s**，max 41.2 s                            | 4/4，p50 5.7 s      | 无               |
| 4    | 17/24 200 + **7 个 504**，p50 106 s（第一轮）/ 51.6 s（第二轮） | 8/8，p50 8.4–11.1 s | 7 个 504         |
| 16   | 27/32 200，p50 **45.6 s**                                       | 15/16               | 5 次建连超时 + 1 |

并发 1–2 下的最大值（21.9 s、41.2 s）是折叠：每接受八条就重写一次分区。并发 4 时折叠与接受争抢同一份
manifest，输掉的那次尝试每次都要重做 MB 级的分区读、导出与上传——于是一个 5 秒的操作变成三位数。

预检随后因为同样的原因失败：十六次调用各自占着一个实例数十秒，健康探测拿不到实例，而它的建连超时比
等待时间更短。

## Guardrails added

- `onlion/scripts/soak-endpoint.mjs`：从任意网络按比赛方的顺序压测——两次预检、并发 Add 阶段、并发
  Search 阶段——报告各状态码计数、p50/max 与连接错误。出现非 200 就以退出码 1 结束，可用于开跑前的门禁。
- `/admin/status` 报出当前嵌入端点、模型、索引身份以及约束一次请求的四个超时，让「这版在打哪个端点」
  不再靠延迟推断。
- 检索与写入各有显式预算（25 秒 / 45 秒），每次 COS 往返都有 20 秒超时，于是卡住的上游会让一个请求失败，
  而不是吃掉整个上限。

## Lessons

- **健康预检会把任何可用性问题变成零分。** 最该保护的请求是第一个，不是平均水平。
- **当写路径按用户串行时，并发不是免费的。** 它放大的是尝试次数而不是吞吐，而代价恰好落在那批与竞争无关的
  请求上。
- **必须从客户端所在的网络测量。** 三轮诊断花在经代理取到的数字上，而那些数字既产生了真实客户端看不到的失败，
  也掩盖了它看到的失败。
- **一次部署就是一次中断。** 两次端点失败都在部署之后一小时内发生。评测期间冻结部署不是谨慎，是测量的一部分。
- **清理里的静默部分失败，看的时候不花钱，推理的时候要命。** 分批删除让清理更健壮、让残留更难观测；正确的做法是
  记录删不掉的键，而不是指望它没有。
