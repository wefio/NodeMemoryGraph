# 事件域语义与协作阶段

[English](collaboration-phase.md) · [使用的术语](collaboration-phase.terms.yaml)

**Status:** draft
**Related:** [事件记录](../board-event-records.zh-CN.md)、[原型概念参考](../../guides/board-concept-reuse.zh-CN.md)

## 目的与阅读边界

本草案汇总事件域扩展的设计方向：帮助协作 Agent 理解当前正在开展什么活动、
哪些工作可以推进，以及哪些想法还在等待决定。它是讨论基础，不是已接受的运行时契约，
也不固定 schema。下文的名称、操作和策略选择均保留调整空间；已支持行为仍由现有事件契约定义。

典型问题是：共享技术讨论中，A 还在提意见，B 已开始修改，C 又依据未确认的方案开发。
反过来，执行中出现整体重设计建议，也会让参与者不确定该继续还是停下来。
共享阶段语义使这条边界可见，不要求设置一个常驻管理者监督所有 Agent。

## 选择性吸纳概念

[概念参考](../../guides/board-concept-reuse.zh-CN.md#原型概念参考清单)保留完整一些的 DSH 词汇及来源。
Ticket、Assignment、Session 区分持续工作、一次具体分配与实际执行会话；
它们只是例子，不是全部模型，也不要求新增同名实体。
其他值得保留的区分包括：输入与责任、上下文关联与送达、授权与建议、自报结果与已接受成果。

总体方向是吸纳能填补具体事件域缺口的概念，复用已有消息、参与者、资源、历史和订阅基础。
其余概念留待真实需求出现。Phase 是这里提出的协作设计，不将其归因于 DSH 原型。

## 范围、关系与视图

事件空间可以承载协作范围。一个子范围可以因局部设计冲突进入讨论，而无关工作继续执行。
范围是否总与一个事件对应、共享资源如何关联多个范围，仍待确定。
父子关系本身不足以决定权限继承或暂停传播。

关系应保留各自含义：上下文关联、参与、订阅、父子关系与执行前置条件是不同的关系。
只有选定的执行前置条件子图需要 DAG 约束，整个语义图不必无环。
上下文关联不授权工作，也不调度依赖。已有 OoO 任务／run 语义可以作为执行基础；
它不是 InformationView 的前身。

InformationView 继续承担最终呈现与披露，可以在共享预算机制下投影范围、阶段、
待处理请求以及来源／版本信息。渲染不决定授权，也不提交阶段切换。

## 阶段与参与者活动

先考虑两个主要阶段：

| 阶段 | 典型活动 |
| --- | --- |
| Discussion（讨论） | 分析、计划、协商、复盘、形成决策 |
| Execution（执行） | 实现、修改、测试、验证、交付 |

阶段约束活动，不约束每句话。执行期间可以讨论实现细节；推翻共同方案可能需要切换。
计划和复盘可以作为讨论目的，不一定增加顶层阶段。允许反复切换，每次保持可见边界。
阶段与事件开启／结束状态、工作结果分别表达。

共享阶段属于范围；参与者活动是提出方案、等待、实现或验证等观察信息。
同一个 Agent 可以参与处于不同阶段的多个范围。互相发现的列表可以显示这些关联，
不必给每个 Agent 分配唯一的全局阶段。参与者自报状态不改变共享阶段。

## 暂存非当前阶段的信息

记录想法不等于授权行动。优先考虑复用黑板消息，补充目的、范围和可见处理状态，
再判断是否需要独立队列。

| 当前阶段与新活动 | 可考虑的处理方式 |
| --- | --- |
| 讨论中请求立即编码 | 暂存执行请求，或提议切换 |
| 讨论中需要小规模实验 | 请求该实验的有限执行许可 |
| 执行中发现新优化方向 | 暂存为讨论候选 |
| 执行中发现原计划严重错误 | 报告阻塞，提出暂停／切换 |
| 执行中的普通实现交流 | 在现有范围内继续 |

待处理项在被处理、延期或撤回前应保持可发现。具体目的分类和处理状态词汇仍开放。
参与者停止自己的不安全操作，与暂停其他参与者或改变共享阶段，是不同的行为。

## 提议、确认与切换

三个概念操作描述切换过程，暂不固定 API 名称：

1. **Propose（提议）：**说明范围、目标阶段、原因、受影响工作，以及提案依据的当前阶段版本。
2. **Agree（协商确认）：**受影响参与者依据范围内的协作约定确认。确认针对具体提案；
   实质改变提案后，可能需要重新确认。
3. **Switch（提交切换）：**Harness 检查适用条件，提交共享阶段变更，通知相关参与者。

不默认要求全员投票。单个已获授权的参与者可以独立切换；共同修改需要协调受影响者。
如何识别这些参与者、处理缺席或分歧，以及接受用户直接授权，需要结合场景确定。
不应无意中把沉默当作同意。

## 版本一致性与执行边界

范围需要可识别的当前阶段版本。独立的 `phaseRevision` 是一种候选设计，
使普通消息更新不必导致执行许可失效。以下仅示意语义，不是存储或传输格式：

```text
scope: interface-change
phase: discussion
phaseRevision: <当前版本>
pending: [执行请求, 讨论候选]
pendingTransition: <若有则为切换提案>
```

执行阶段本身不授予无限资源权限。执行许可仍受工作分配与资源权威约束。
讨论期实验可以按参与者、操作、资源、阶段版本和有效期限定，无需切换整个范围。

只在工具启动时检查版本还不够：执行期准入的操作可能在切到讨论后才写入。
强约束因此需要处理在途工作。候选方式包括停止新操作准入、等待安全检查点、
在支持时取消，以及在可控制的提交点再次验证许可。
不可逆外部副作用需要自己的边界，版本号不能撤销它们。

`pendingTransition` 可以披露正在协商或等待在途操作收尾，而不增加第三个业务阶段。
切换是否等待相关操作结束，或限制它们后续提交，仍是集成选择。
显示阶段有助于协调；声称强制约束，需要实际执行入口和在途操作支持。
通知本身不能证明具备这种支持。

## 范围内输入批次与唤醒协调

草案在阶段协商之外增加输入送达层。一次协作回合可以共同处理同一范围内已到达的多条回复，
以接收者的一份有界输入批次组织。批次大小、调度等待时间和存储结构保留调整空间。

批次按接收者与协作范围分组，同一事件内保留频道边界。源消息保留 ID、作者和原 owner 定义的顺序。
可考虑的批次签名包含接收者／会话、范围、选中消息 ID、源游标或修订的读取上界，
以及准备时观察到的阶段版本。频道游标与事件修订分别保留各自含义。
签名描述有限观察范围，越过上界的新消息留待后续批次。

### 合并与调度

合并后的提醒可以保留待展开的源消息范围。准备输入时，按读取资格展开其中的原消息并应用共享预算。
这样即使旧提醒被合并，连续到达的回复仍能共同被发现。
历史已过期或不可用时显示缺口，接收者可以据此判断是否需要补充上下文。

对同一接收者与范围，Agent 忙碌时由一个待处理唤醒累积更新，Harness 在下一个支持的处理边界准备批次。
批次准备／入队后保留固定身份和内容，后续到达消息进入后继工作。
宿主能力决定能否在该边界前更新排队中的唤醒。
空闲时可以处理当前已到达的消息，无需等待全部参与者回复。

范围分组继续遵守点名、订阅与抑制规则。独立范围可以分别推进。
工作项认领与串行交接保留原有 owner 和顺序规则，普通讨论的多条消息可以按批次共同读取。

### 预算、收据与阶段边界

共享来源 owner 选择有资格读取的记录，InformationView 在一个批次预算内准入带来源标签的内容。
多条消息共用宿主外层包装时，仍保留逐条身份。
预算未容纳的内容继续待处理，并在预算允许时提供续读信息。

准备完成、宿主入队、确认已读与实际处理分别记录。
收据只关联实际准入且被宿主接受的源条目。读取目录或仅发送范围提醒不能越过尚未展示的消息。
确认一条消息不能顺带消耗其他回复、后到消息或整个范围。
重试沿用源身份并复核当前投递资格，入队失败的条目保留重试资格。
重启后的恢复范围受现有保留规则约束。

批次显示当前范围的阶段和版本。源消息已有发出时阶段版本时保留它，旧消息可以标为阶段来源未知。
准备期间发生切换，需要重新检查阶段，再明确选择重建批次或在行动前披露过期上下文。
批次送达本身不产生阶段确认或执行许可。

这些机制减少割裂处理与重复唤醒请求。参与者仍可依现有通知契约发布新回复和显式通知，
新消息是否需要回应等语义判断继续由协作约定处理。

## 建议收敛范围与待验证问题

首轮设计可以聚焦范围级阶段、切换提案、确认、版本检查、请求暂存、范围内输入批次和 InformationView 披露。
不必同时引入通用调度器、新管理角色或全部 DSH 实体。
执行约束可以按宿主能力逐步接入，并显示其边界；本草案不确定默认约束强度或迁移策略。

用具体协作场景收敛剩余选择：

- A、B 讨论时，B 的编码请求在得到许可前保持待处理。
- 执行时 C 提出的优化方向保持可见，但不自动改变 A 的工作方向。
- 子范围进入讨论时，无关执行继续进行。
- 过期提案或许可可以被识别；普通消息不无谓地使有效工作失效。
- 获准实验保持范围限制；切换时在途操作有明确去向。
- 参与者离开、重启或提出相互竞争的切换时，不把缺失确认变成授权。
- B、C 在 A 的下个处理边界前回复，预算允许时 A 在同一批次收到两条带来源的合格回复。
- 合并旧提醒后仍可发现原回复，预算遗漏与历史过期分别显示。
- A 忙碌时，同范围多次更新累积到一个待处理唤醒，准备边界后的消息留待下批。
- 入队失败、重试、确认单条回复或退订，不错误消耗其他有资格的回复。
- 准备批次时切换阶段，接收者仍可识别适用阶段版本和过期的来源上下文。

这些是设计验证场景，不是冻结的验收套件。开放问题包括范围身份、权限继承、
确认规则、提案替换、许可有效期、批次组装边界、部分收据恢复、重启恢复，以及不支持强约束的宿主如何参与。
先从这些案例提炼最小有用语义，再固定 API 和存储结构。
