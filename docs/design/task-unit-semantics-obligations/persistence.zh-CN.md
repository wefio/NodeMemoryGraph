| B1 | 两个 run 使用相同 `taskId` 时互不冲突 | 已证明 | `tests/integration/ooo-run-namespace.test.ts` 的用例 `two runs in one store do not collide, do not see each other, and cancel separately` 分别断言各个部分：一个 run 中的 claim 不影响另一个 run 中相同 task id 的原始 row；取消按 run 隔离；按名称重新打开时读到正确记录。命名空间实验记录说明为何需直接读 raw row。tooth `claim-is-not-scoped-to-its-run` 在该用例明确规则后于 2026-09-24 退役（[实验记录](../../experiments/execution/ooo-run-namespace-2026-09-13.md)、[决策](../../decisions/implemented/2026-09-24-mutants-are-derived-not-anchored.md)）。 |

| B3 | 事务失败不能留下没有关联的 verdict | 已证明 | `tests/integration/ooo-transition-atomicity.test.ts`；mutant `swallowed-failure-still-commits`。两项用于固定事务边界的 tooth（`a-method-opens-its-own-transaction`、`nested-write-transaction-is-allowed`）于 2026-09-24 退役：用例 `a write entry reached inside a transition without a port is refused, not nested` 断言拒绝，`the store runs its transaction boundary in exactly one place` 检查 Store 源码只有一个 `BEGIN`、一个 `COMMIT` 和一个 `ROLLBACK`，且都位于 `writeTransaction`。用例 `the round's own publication rolls back with the transition that made it` 覆盖发布边界：发布使用调用方事务签发的 port，因此事务失败会同时回滚发布；若发布另开事务，它就会存活。该规则由用例明确后，tooth `round-publication-opens-its-own-transaction` 于 2026-09-24 退役。 |
| B4 | TTL 不会清除被保留的 board 条目 | 已证明 | `tests/core/task-board-retention.test.ts`；mutants `prune-ignores-retention`、`bounded-pin-never-expires`。`evals/ooo-execution/patch-cycle.test.ts` 的 `cancelling a round releases the pins it held, so nothing it referenced leaks` 覆盖另一侧：运行期间 pin 保留，取消后列表为空；交给后继的 handoff 与接受补丁 verdict 的条目都随其保护的值释放，避免已结束运行留下永久 pin。该用例明确规则后，tooth `round-never-releases-its-pin` 于 2026-09-24 退役。 |
| B5 | status 查询与依赖解锁调用同一谓词 | 已证明 | `tests/integration/ooo-acceptance-one-predicate.test.ts` 的 `acceptance has one home, and both readers reach it` 直接计数：`src/` 中一个谓词定义、两个读取方各有一个 `acceptedFact({` 调用、`ooo-board.ts` 中没有 `verdict ===` 比较。因此，断开调用或在调用方增加第二套判定都会使计数失败。两个 tooth（`the-board-read-path-stops-calling-the-predicate`、`the-board-decides-acceptance-on-its-own`）在计数明确规则后于 2026-09-24 退役。 |
| B6 | 通用 board 写不能改变受管理 run 的状态、抢走它持有的有效 claim，或绕过采用该条目的 run 转移 | 已证明 | 状态归属由 `tests/integration/ooo-managed-fence.test.ts` 断言：通用 claim 不改变 run 自己的 owner、attempt、acceptance 或 terminal reason。claim 不能被抢不是结构事实；移除 holder 必须是 claimant 的 CAS 条件后，第二个读取者会成功，因此原 tooth `a-live-claim-can-be-taken-by-another-agent` 于 2026-09-24 退役。设计要求——受管理条目的通用写入必须处于协调事务内，`judge`/`resolve` 不能绕过 run fence——由 `tests/integration/ooo-managed-write.test.ts`（6 个用例）证明：直接操作采用条目会被拒绝且条目不变；未被采用的条目仍走旧路径；协调写入把 board 转移和 run 事实写在同一事务中，board 写后失败会同时回滚；取消后的 run 不再接受生命周期写；错误 run 或未被采用的条目在写入前被拒绝；daemon 自己的 `claim` 也经协调转移并写入对应事实。Mutants：`a-managed-entry-ignores-the-coordinated-scope`（Store guard）、`the-daemon-verb-skips-the-coordinated-path`（路由）、`a-coordinated-write-skips-its-run-fact`、`a-cancelled-run-still-accepts-writes`、`a-coordinated-write-skips-the-binding-recheck`。daemon managed path 已采用条目并围栏直接生命周期写入；剩余接入是研究驱动：`plan-driver` 与 `live-continuation` 仍使用研究侧 store，而非 daemon `taskRun`，因此其写入尚未通过此协调器。不要把 managed-path 的证明误当成这些 runner 已接入。 |
| B7 | JSONL 导出失败不会改变终态 | 不适用 | 当前没有 board/`taskRun` JSONL 导出路径；研究侧 `run.jsonl` 是文件产物，不是该导出 API，也不是终态权威。 |
| B8 | 字段映射检查可捕获三种混淆 | 已证明 | A4：由离线编译器负责此检查。 |
| B9 | 已取消任务既不会被派发，也不会被当作已结束输入读取 | 已证明 | 由 A5 枚举发现。接受谓词原先已经拒绝已取消任务（它读取 `cancellations`），但资格规则看不到取消，因为 `DispatchTask` 没携带该事实，因此已取消任务仍可被选为下一项派发。现在 `DispatchTask.cancelled` 携带同一记录事实，`nextTask` 会在 `ready()` 和 `valid()` 中拒绝它。用例 `a cancelled task is not dispatched, and nothing reads one as a closed input`、`nextTask refuses a task marked cancelled, whatever else the caller set` 和 mutants `a-cancelled-task-is-still-dispatched`、`the-dispatch-does-not-require-a-cancelled-input-to-be-closed` 覆盖该规则。范围：研究 `plan-driver` 路径仍只有 run 级取消，且其 `recordedFacts` 不提供 `cancellations`；daemon `taskRun.cancel` 能记录任务级取消，但这些事实还未接入此派发派生逻辑。因此此证明覆盖设计中“取消后的有效性”的共享派生部分。 |
