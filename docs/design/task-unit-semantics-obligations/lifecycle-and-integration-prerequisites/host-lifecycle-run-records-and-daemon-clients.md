## Host lifecycle, run records and daemon client boundaries

| Node | Obligation | State | Evidence |
| --- | --- | --- | --- |
| D7 | A run borrows an operations port and never closes the owner's Store | Not applicable | The round-specific subject (`OooRoundOperations`, `openRoundStore()`, `CycleOptions.operations` and constructor-installed specs) was retired on 2026-09-18. The current owner/borrower contract is in [run-record ownership](../../../design/task-unit-semantics/run-record-ownership.md); see the [retirement decision](../../../decisions/implemented/2026-09-18-retire-the-round-instrument.md). |
| D8 | Shutdown stops new work, drains accepted work and closes once | Proven | [`src/cli/service.ts`](../../../../src/cli/service.ts): `close()` refuses while calls are in flight, `drain()` is awaited, and `inFlight` counts accepted work. [`tests/cli/service-drain.test.ts`](../../../../tests/cli/service-drain.test.ts) covers a held call and requires `drain(0)` to fail; [`tests/cli/service.test.ts`](../../../../tests/cli/service.test.ts) and [`tests/cli/archive-shutdown.test.ts`](../../../../tests/cli/archive-shutdown.test.ts) cover close behavior. |
| D9 | A post-commit notification failure is recorded, not thrown as a rollback | Proven | `tests/integration/ooo-post-commit-notification.test.ts`: a throwing `afterCommit` still leaves the artifact accepted and board-owned, while `lastNotificationFailure()` reports the message. The notification callback runs after the commit; its failure cannot undo the stored result. |
| D10 | The early-cancel branch in `runCycle` is reachable or dead | Not applicable | The branch and `runCycle` were removed with the round on 2026-09-18; the earlier regression is historical, not a current runner proof ([decision](../../../decisions/implemented/2026-09-18-retire-the-round-instrument.md)). |
| D11 | Run records use Store schema and typed writes join its transaction | Proven | `migrate()` creates `task_run_manifest`, `task_run_tasks` and `task_run_facts`. `registerTaskRun`, `freezeTaskRunTask` and `appendTaskRunFact` accept the transaction port. `tests/core/store/task-runs.test.ts` covers atomic board/fact writes and rollback, idempotent retry and sequence, per-run isolation, frozen-plan refusal, binding ambiguity and side-effect-free reads; `tests/core/store/schema.test.ts` checks the tables. Registered and retired tooth details are owned by the [mutation-anchor decision](../../../decisions/implemented/2026-09-24-mutants-are-derived-not-anchored.md). |
| D12 | A task-to-entry binding is a run fact, and one routing rule decides whether an entry is managed | Proven | `bindRunEntry()` records `entry-bound`; the Store fence refuses direct lifecycle writes to an adopted entry outside its coordinated transition. `tests/integration/ooo-managed-adopt.test.ts` covers atomic create-and-bind, idempotent retry, duplicate/cross-run refusal and named refusal reasons. `coordinatedEntryWrite()` centralizes daemon routing. Mutants cover bypassing the fence, stale binding, cancellation and skipped run facts in `tools/mutation-teeth.ts`. |
| D13 | Another process reaches run facts through daemon `taskRun` only | Proven | `src/cli/protocol.ts` routes `taskRun` to `registerRun`, `freezeRunPlan`, `bindRunEntry`, `cancelRun`, `taskRunStatus` and `createBoundEntry` in `src/integration/task-coordinator.ts`. `tests/cli/task-run-surface.test.ts` exercises the service wire and `hello.methods` advertisement. Freeze order follows the request array; dangling/self dependencies and cancelled-run writes are refused; adoption creates and binds in one transition. `status` is read-only, and the CLI exposes `nmg run status` / `nmg run cancel`. |
| D14 | Evidence drivers reach their research board through a daemon client and open no database | Proven | `round-client.ts` resolves the store's daemon lease and refuses by name when no host is available; `round-host.ts` serves the existing research store. `board-worker.ts`, `board-deliver.ts` and `board-judge.ts` use protocol board verbs rather than opening the Store. `tests/integration/ooo-evidence-drivers.test.ts` spawns separate clients and checks the recorded `entry-bound → board-claim → board-deliver → board-judge` facts, no-daemon refusal and no direct-store fallback. Calls are bounded and a client refuses its own serving PID; the tests also cover lease release. |

D14 does not cover the research runners: `plan-driver.ts` constructs `BoardAdmission` with its research database path, while `live-continuation.ts` opens `NmgStoreBase` directly. Neither uses daemon `taskRun`; this is a separate integration gap, not a failure of the evidence-driver boundary above.
