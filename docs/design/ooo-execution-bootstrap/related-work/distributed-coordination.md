# Distributed communication: established mechanisms already have names

[中文](distributed-coordination.zh-CN.md) · [Terms used](distributed-coordination.terms.yaml)

**Status:** draft; these are design analogies, not evidence of current product-runtime integration.
**Authority:** [Parent scope](../related-work.md).

## Mechanism mapping

- **Fencing token.** The probe design's `attempt` plus `inputDigest` acts as a fencing identity: the attempt generation advances on re-claim, while the digest binds the input. A resource must reject a stale generation itself ([Kleppmann, How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html): “requires the storage server to take an active role in checking tokens, and rejecting any writes on which the token has gone backwards”). The coordinator's `submit()` rechecks `bound()` inside the transaction before writing an artifact. This follows the rule that the resource checks at the commit point, rather than glancing at the state before a write. Kleppmann's GC-pause case (a holder does not know its lease expired and resumes writing) matches the intended stale-worker case: work continues after lease expiry, but the artifact is rejected. That is a published correctness argument for the boundary, not a proof that every product writer uses it.
- **Failure detector.** In an asynchronous system, one cannot distinguish “crashed” from “merely slow” without an additional failure-detector assumption ([FLP](https://homes.cs.washington.edu/~arvind/cs425/doc/fischer.pdf), [Chandra–Toueg](https://dl.acm.org/doi/10.1145/226643.226647)). Therefore a check host that never reports yields `undecidable`, never success; a failed check may release a repair task but cannot accept the result. This is the textbook choice at that boundary, not a novel contribution.
- **Exactly-once as at-least-once plus an idempotent receiver.** This is the outbox/inbox pattern with message-ID deduplication ([delivery guarantees](https://event-driven.io/en/outbox_inbox_patterns_and_delivery_guarantees_explained/)). In the probe design, repeated terminal evidence returns `duplicate`, and resubmitting the same artifact is inert. “Automatically retry only checks declared re-entrant” follows the same model; it is not an exactly-once transport guarantee.
- **Saga/compensation.** A failed check may release a later repair task without accepting the failed result: compensation replaces rollback.
- **Structured concurrency.** Each task has an owner and bounded lifetime; children cannot outlive their parent scope ([Swift proposal](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0304-structured-concurrency.md)). This is the rationale behind “at most one waiting and one executing task,” “worker does not outlive the round,” and “do not artificially expire a rejected claim”; it is also an S2 invariant to preserve.
- **Durable execution requires determinism and replay.** Systems centered on log replay require deterministic orchestration code, side effects isolated into activities, and their results recorded ([Temporal](https://learn.temporal.io/tutorials/go/background-check/durable-execution/), [determinism and replay](https://jack-vanlightly.com/blog/2025/11/24/demystifying-determinism-in-durable-execution)). The design's “freeze the interface + worker returns only an untrusted artifact for host application” follows that separation (the model call is the nondeterministic activity), but it **lacks replay** in the snapshot described here: round state lived only in the SQLite coordinator and JSON report, so it could not be replayed after process exit. S2 recovery should use a log-and-replay model.
- **Blackboards and tuple spaces.** A classic blackboard weakness is the lack of a control structure, requiring an explicit control component ([Hayes-Roth](https://www.semanticscholar.org/paper/A-Blackboard-Architecture-for-Control-Hayes-Roth/c79a41dc13c796c26388f8cbf599c67126374e39)); Linda abstracts shared coordination as a tuple space ([Linda](https://en.wikipedia.org/wiki/Linda_(coordination_language))). Here the board handles cross-process handoff and claims; control stays in the fixed plan and coordinator selection function, addressing that weakness.
