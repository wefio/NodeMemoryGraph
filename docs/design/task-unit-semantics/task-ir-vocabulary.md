## Task IR and existing vocabulary

Task IR is a read-only view computed from existing declarations and records. It accepts neither a second `inputs/outputs/effects/accept` JSON nor a separately editable IR. Concept names below explain analysis results; inputs and validation continue to use existing fields. When new semantics are needed, extend their owner rather than adding synonymous fields.

| Analysis concept | Existing fields and sole type owner | Compilation and boundary |
| --- | --- | --- |
| identity / intent | [BoardTicket, PatchTaskSpec](../../../src/integration/ooo-board.ts): `runId/taskId/revision/attempt/inputDigest`, `instruction`; [PatchWork](../../../src/integration/ooo-patch.ts) | Reuse current identity and `instruction`; add no `id/contractRevision/intent` aliases. A board entry ID is not a logical `taskId`; the binding key includes `runId` |
| inputs | `PatchTaskSpec.files` → `FrozenPatchTask.files`; `ProbePlan` dependencies → `BoardTicket.dependencies` | File content is frozen; the host binds prerequisite artifacts at claim time. The view derives references and digests; there is no multi-port input language today |
| outputs | [PatchSubmission, ConclusionKind](../../../src/integration/ooo-patch.ts); `PatchTaskSpec.admittedConclusions`; board `deliverableDigest/Ref` | Reuse patch/conclusion and single delivery. `cannot-complete` is not success merely because its shape is valid. Multi-output ports and arbitrary artifact kinds are unsupported and cannot be smuggled into instruction text |
| effects | `ProbePlan` effect / [DispatchTask.effect](../../../src/integration/ooo-execution.ts); `PatchTaskSpec.visible/editable` | Existing effects are coarse categories, `read-only/isolated-artifact`. Worker read scope comes from `visible`; proposal write scope from `editable`; host validation also consumes complete `files`. These are not full semantic read/write sets. Treat opaque tool effects as conflicts |
| accept | `PatchTaskSpec.verify`; [Requirement](../../../src/integration/task-semantics.ts) (formerly co-located with `CycleOptions.checks` and `CaseRule` in the retired `ooo-cycle.ts`); board's separate `verdict/judgedDigest` | Reuse host verification and board judgment; add no second `accepted`. `verify` is an in-process function and cannot be persisted. A serializable verification description needed for recovery must be frozen from existing checks/cases/mutations configuration and rebuilt by the shared host; do not store functions or arbitrary checker strings |
| budget | [PatchBudget](../../../src/integration/ooo-patch.ts): `perFile/output` | Limits output bytes, not tokens; remove the separate `outputs.maxBytes` alias. To enforce a model-token budget, extend its owner and execution protocol first; the current view must not claim it supports one |
| limits | `PatchLimits.turns/reads/timeoutMs` → `FrozenPatchTask.limits` | Preserve units and execution timeout; add no `deadlineMs`. These are not the board-claim lease or a round-wide budget |
| placement | No equivalent field exists | Shared scheduling policy produces only a transient fusion/assignment suggestion. It does not enter the current ticket or affect acceptance; `visible/editable` do not carry placement semantics. Persist execution associations as task/attempt/executor references in run records, not duplicated task declarations |
| deps / requires | `ProbePlan` dependency list; `CycleOptions.requires: Requirement[]` | `deps` are dispatch and artifact dependencies. `requires` are cycle conditions over recorded artifacts: `verified/mutant-killed/test-title`. They are not equivalent, and current `requires` is not a general authorization or branch-predicate registry |
| external fact / assumptions | `ProbePlan` wait event, [external check ticket](../../../src/integration/check-ticket.ts); no general assumptions type | Keep check-event identity. Bounded factual speculation from the parent design still requires an explicit shared-protocol extension; do not disguise missing support as `requires` or an existing ticket field |
| refinement | [RefinementSpec](../../../src/integration/task-semantics.ts): parent-obligation-to-output mapping and explicitly named `constraints` | A read-only model declaration, not persisted task text. `within-parent-writes` compares normalized proposed write resources, not the patch envelope. The protocol defines its name; its presence enables it, including an explicit empty list. A parent permission obligation cannot disappear by omitting a constraint |

The sole owner of board `kind` is [TaskBoardKind](../../../src/core/types.ts). It describes collaboration-message purpose: `handoff`, `result` or `decision`; it is not a patch/conclusion type or an effect. OoO patch/snapshot `kind` is an internal task category. Do not convert among them or add a `task-ir` kind, tool or channel to carry duplicate definitions.

The data flow is: existing RoundSpec research entry → shared normalization/validation → existing task contract and plan → derived analysis view → `BoardTicket`. Parsing rules needed for product integration belong in shared owners, called by research entry points and harnesses; research A/B/C input format must not become a general language. Default patch consumers use `preparePatchWork` to produce a complete frozen declaration rather than copy a field subset. Tickets and shared cycles carry it as an opaque, digested `declaration`; not every consumer's declaration needs patch fields, and the consumer owns freezing, interpretation and acceptance. See the [declaration-boundary decision](../../decisions/implemented/2026-09-21-mechanism-not-policy.md).

Compilation must explicitly reject unsupported mappings; it must not silently drop fields or degrade them to free text. The first version analyzes only existing patch/snapshot contracts and does not reimplement validators, budgets or access rules. Add semantics to their owner, identity digest and checks before exposing them in the derived view.

Field checks can prove an acyclic plan, existing references, compatible current artifact shapes, non-expanded permissions and bounded budgets. They cannot prove complete intent, truthful read-set declarations or sufficient tests. Read-set truth depends on actual tool-access restrictions; when ordinary shell access is unconstrained, treat the task as opaque work.
