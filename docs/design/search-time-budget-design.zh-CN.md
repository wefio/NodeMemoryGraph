# 一次检索怎么花掉它的时间

**Status:** draft
**Created:** 2026-10-31

本文负责一次 `/search` 请求在时间上的**机制**：阶段、顺序、每个阶段的界归谁约束，以及由此
推出的不变量。它不含任何数值。设计理由见
[2026-10-30-search-is-a-read](../decisions/implemented/2026-10-30-search-is-a-read.zh-CN.md)
与
[2026-10-30-search-degrades-on-unreadable-partition](../decisions/implemented/2026-10-30-search-degrades-on-unreadable-partition.zh-CN.md)；
事故归因见 `postmortem/`；每个旋钮的当前取值由代码负责。

**调参不得改动本文件。** 若某次事故迫使这里改动，那是机制变了——按设计事件处理，而不是参数
更新。本文只写了一次，起因是一轮调参被两次误读成机制变化。

## 阶段

| #   | 阶段         | 由什么界定                                                                           | 归属                   |
| --- | ------------ | ------------------------------------------------------------------------------------ | ---------------------- |
| 1   | 读取请求体   | 它自己的 body 截止                                                                   | `readJson`             |
| 2   | 读取用户清单 | 一次对象读取，无专门界定                                                             | `readManifest`         |
| 3   | 读取分区     | **每个分区开始前**评估的门槛；触发时跳过其余分区，并把回答标记为不完整               | `readSearchCandidates` |
| 3a  | 单个分区下载 | 对象存储的单次调用超时                                                               | `openPart`             |
| 4   | 读取查询向量 | 构造嵌入客户端时启动的**独立时钟**（写路径为写时钟），外加调用方对每次调用强制的截止 | `embeddingClient`      |

有两个阶段不在这张表里，因为它们根本不由我们界定：平台的调用上限，以及客户端的耐心。两者都是
外部事实，归 [edgeone-runtime-mechanism](edgeone-runtime-mechanism.zh-CN.md) 负责并测量。

## 不变量

以下各条与旋钮取什么值无关。每一条都至少被一次善意的补丁破坏过。

1. **没有任何旋钮是请求的界。** 上表中每个界都只作用于一个阶段。请求的最坏情况是这些界的组合，
   并且**总是**大于其中任何一个——这是构造使然，不是意外。
2. **门槛在分区之前，因此第一个分区必定执行。** 已经耗尽的预算仍要付掉门槛尚未看到的那一个分区。
   这就是"把预算设得极小"并不会让请求变快的原因。
3. **一个分区的开销由下载超时界定，而不是由剩余预算界定。** 一个慢分区花掉自己的界，门槛是在
   之后才知道的。
4. **嵌入阶段不继承读取阶段的时钟。** 它自建一个，于是两个阶段是相加而不是嵌套。
5. **短了的回答必须说自己短。** 只要有分区被跳过——无论被门槛截住还是读不出来——响应就带
   `partial`；读不出来还会额外贡献 `degraded: <code>`，即第一个读不出来的分区的错误码。
6. **不是"依赖缺失"的错误必须外抛。** 只有超时、连接重置、中止和被替换的快照会让回答降级；
   其余仍然作为失败暴露，好让 bug 保持可见。
7. **写路径有降级，读路径也必须有。** 写路径先落一条日志条目，把昂贵部分推迟；读路径没有对应的
   推迟机制，所以它唯一体面的失败方式是更短的页面。`/search` 返回 5xx 会搭上整次尝试。
8. **取消信号本身不是界。** 每个依赖调用除传输层对信号的反应之外，还必须有一层由调用方自己强制的
   截止。传输层自带的兜底是**分钟级**的——undici 的 `headersTimeout` 与 `bodyTimeout` 默认都是
   300 秒，且其文档并不承诺精确触发——所以一个没有如期结算的信号，背后只剩平台掐断调用。忽略、
   延迟或丢失 abort 的依赖，仍然只允许花掉一个有界的时长。
9. **阶段名不是证据，它的"年龄"才是。** 任何标出阶段的报告都要同时给出已经在该阶段停留多久；
   请求结束时记录它离开时所处的阶段。没有年龄，"卡在 embedding 58 秒"和"第 58 秒才进
   embedding"是同一行日志；而一个滞后于代码的标签，看起来和一个正确的标签一模一样。这条不变量
   存在的原因就是：在打印出年龄之前，错的标签和正确的标签无法区分。

## 不靠猜地读一行日志

每个请求都会写一行，含路由、状态、耗时以及 SQLite 当时是否就绪。失败记录额外带阶段与错误码。

| 你看到的                         | 它支持什么                                       | 它排除什么                               |
| -------------------------------- | ------------------------------------------------ | ---------------------------------------- |
| 完全没有请求行                   | 处理函数没有跑完——看阶段 1 与平台侧              | 上面任何阶段                             |
| 200，且耗时超过最小的那个旋钮    | 门槛又放了一个分区过去，或嵌入阶段花掉自己的时钟 | 单个阶段撞上单个界                       |
| `stage` 指向下载，配一个依赖超时 | 阶段 3a                                          | 嵌入提供商；该记录里嵌入字段是故意缺席的 |
| `partial` / `degraded`           | 回答被缩短了，以及原因                           | 存储是健康的                             |

有两个日志字段常被读成互相矛盾，其实**作用域不同**：就绪标志是写日志那一刻评估的，而数据库
high-water 是**整个容器**的峰值。一个什么都没加载的请求，待在一个此前加载过东西的容器里，报出来
的正是这样一对值。

## 改动一个界时

从请求出发，不要从阶段出发。按上面的不变量算出新的组合，把它写出来，然后才改旋钮。只压低一个
阶段却不重算整个请求，正是"声称 25 秒、实际长得多"这种分歧的由来；它的代价是一位操作者正确地读了
一份正确的日志，却得出了错误的结论。

若这次改动逼得本文件必须修改，说明不变量已经不再成立——在一条决策记录里说清哪一条破了、为什么，
然后让本文跟随。
