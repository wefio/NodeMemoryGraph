# 一次检索怎么花掉它的时间

**Status:** draft
**Created:** 2026-10-31

本文负责**机制**：一次 `/search` 请求把时间花在哪些阶段、哪个旋钮约束哪个阶段、由此得到的
最坏情况是什么。它不负责理由（见
[2026-10-30-search-is-a-read](../decisions/implemented/2026-10-30-search-is-a-read.zh-CN.md)、
[2026-10-30-search-degrades-on-unreadable-partition](../decisions/implemented/2026-10-30-search-degrades-on-unreadable-partition.zh-CN.md)），
也不负责事故归因（`postmortem/`）。

改动任何超时之前先读这里。下面每个常量都是**阶段**上界，没有一个是**请求**上界；把两者混为一谈，
已经在这个项目上产出过一次错误结论。

## 阶段，按顺序

| #   | 阶段         | 由谁上界                                                                                       | 在哪检查               |
| --- | ------------ | ---------------------------------------------------------------------------------------------- | ---------------------- |
| 1   | 读取请求体   | `BODY_TIMEOUT_MS` = 30 秒（`NMG_BODY_TIMEOUT_MS`）                                             | `readJson`             |
| 2   | 读取用户清单 | 无独立上界；一次对象读取                                                                       | `readManifest`         |
| 3   | 读取分区     | **每个分区开始前的门槛**：`Date.now() - started > SEARCH_DEADLINE_MS` → 停止，`partial = true` | `readSearchCandidates` |
| 3a  | 单个分区下载 | `COS_TIMEOUT_MS` = 20 秒（`cos-bucket.mjs`）                                                   | `openPart`             |
| 4   | 读取查询向量 | `EMBED_QUERY_BUDGET_MS` = 25 秒，**独立时钟**                                                  | `embeddingClient`      |

## 由此产生的结论

`SEARCH_DEADLINE_MS`（25 秒）**不是请求的截止时间**，它是每个分区**开始前**评估的门槛。三条推论：

1. 第一个分区必定执行，即使预算已经用完。把预算设成 1 毫秒，仍然会完整读一个分区。
2. 一个慢分区由 `COS_TIMEOUT_MS`（20 秒）界定，而不是由剩余预算界定。
3. 嵌入阶段自建 25 秒时钟（客户端构造时的 `Date.now() + budgetMs`），不扣减读取阶段已花掉的时间。

所以读取阶段大致可到 `20 秒 ×（门槛触发前读到的分区数）`——实际是两个分区各卡一次约 40 秒——再叠加
嵌入阶段的 25 秒。**于是一次 `/search` 可能耗时约 65 秒，而每个旋钮都写着 25 秒。** 这个数字是对上面
常量的算术推导，不是测量；没有观察到过这么长的请求。

## 响应字段的含义

| 字段                           | 含义                                                                                                                  |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `partial: true`                | 回答比存储短：分区被跳过，或是被门槛截住，或是读不出来                                                                |
| `degraded: <code>`             | 第一个读不出来的分区的错误码（`snapshot_changed`、`dependency_timeout`…）                                             |
| `sqlite_loaded`（日志）        | **写日志那一刻** SQLite 是否就绪                                                                                      |
| `high_water_databases`（日志） | **整个容器**的峰值，不是本次请求——它等于 1 而 `sqlite_loaded` 为 false 时，意思是"本次没加载；这个容器某个时刻加载过" |

最后两个是最常被读错的一对：它们的**作用域不同**。

## 已确立、已测量、未知

| 说法                                       | 状态                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 门槛在每个分区之前评估，不在分区内部       | **代码确立**——`worker.mjs` 的 `readSearchCandidates`                                              |
| `COS_TIMEOUT_MS` 约束单次下载              | **代码确立**——`cos-bucket.mjs`                                                                    |
| 嵌入预算用独立时钟                         | **代码确立**——`deadline = Date.now() + budgetMs`                                                  |
| 1 毫秒预算仍完整读一个分区                 | **已测量**——本地探针、三个标记、单分区：耗时 27 ms，所有标记都返回。环境：Miniflare，无嵌入提供商 |
| 连续两个分区读不出来即停止                 | **测试确立**——`test-backend.mjs` 删掉分区对象后断言 200 / `partial` / `degraded`                  |
| 生产环境分区下载为何卡 20 秒               | **未知**                                                                                          |
| 平台 120 秒掐断是停滞 body、嵌入、还是排队 | **未知**                                                                                          |

被复现的机制只是候选原因，不是原因。2026-10-30 有两条记录正是这样被误判的：`partition_download`
超时被读成嵌入故障，因为失败记录无条件附加了 `embedding_host`（已修）；19:34 那个窗口被读成业务逻辑，
其中五行其实是根本没收到 body 的请求。

## 不靠猜地检查一次慢请求

每个请求都有一行 `nmg_request`：`route`、`status`、`elapsed_ms`、`sqlite_loaded`、`execution`。
失败记录带 `kind`、`stage` 和错误码。

- **完全没有 `nmg_request` 行** → 处理函数没跑完，时间不在上面任何阶段里。去看阶段 1（body）和平台侧。
- **状态 200 且 `elapsed_ms` > 25 秒** → 门槛又放了一个分区过去，或嵌入阶段花掉自己的预算。`partial` / `degraded` 能区分。
- **`stage=partition_download` 且 `dependency_timeout`** → 阶段 3a。这类记录里嵌入字段是**故意缺席**的。

## 改动上界时

改这里任何常量，都必须移动**最坏情况**而不是只移动一个阶段：写出整个请求的新上界，并说明它来自哪个阶段。
只压低某个阶段的上界却不重算请求上界，正是"声称 25 秒、实际 65 秒"这种分歧的由来。
