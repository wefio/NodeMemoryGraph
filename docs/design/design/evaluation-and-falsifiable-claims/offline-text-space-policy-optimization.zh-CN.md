## 离线文本空间策略优化

训练来源（provenance）是闸门的一部分，不是散文约定。常规 Pi 反馈记为 `collectionOrigin=natural`；可复现的无头探针固定为 `controlled`，字段引入之前的遗留事件仍为 `unknown`。只有标签完整的自然结果可以进入控制器标定或正式的 SkillOpt 切分。受控结果仍是有效的工程冒烟数据。

NMG Lab 可以使用 SkillOpt 优化一个**仅针对控制器的召回决策策略**，但绝不可优化可变的记忆内容。当前适配器从 `nmg-prompts.yaml` 的 `memory_policy` 字段生成该制品的初始值，然后评测一个严格的机器可读决策契约。那个控制器制品与回答 Agent 使用的全局自然语言策略不是同一个东西。历史、证据、事实、STG/LTG/AG 状态、节点身份与边身份仍是不可变的评测输入。

第一个适配器只学习下一次渐进召回决策（`answer`、`expand` 或 `stop`），以及是否应根据显式影子标签折叠噪声。它使用按时间顺序的整任务 train/validation/test 切分。一次 SkillOpt 验证胜出只产生一个候选：匹配的 Pi+NMG 答案、证据、污染、token、工具调用与延迟闸门也必须通过，此后采用还要求一个专用的控制器调用/策略边界，它不能把协议泄漏进用户答案。采用仍是回写到 YAML 事实来源中的一次经评审编辑。运行时的 NMG 从不自动加载 `best_skill.md`。首次官方运行改善了离线验证与测试分数，但匹配的 Pi 闸门从 canonical 6/6 回退到候选 4/6，因为 `recall_action` JSON 出现在用户答案里；候选被否决，canonical YAML 未被改动。协议与当前就绪度见[SkillOpt 策略优化边界](../../skillopt-policy-optimization.md)。

第二个独立候选制品是 `memory_maintenance_policy`。它把已经观察到的控制器与反馈信号翻译为**经评审的维护提案**，而不是在推理期间变更记忆。它的归因必须区分：

- **内容缺陷**：某条 statement 是错的、过时的或含糊的；
- **作用域缺陷**：一条有效的 statement 被挂得过宽或过窄；
- **检索缺陷**：内容有效，但选择或时机错了。

只有前两类可以提出内容/作用域维护。检索缺陷仍属选择策略的证据。候选维护策略需要它们自己的长时程结果定义、留出闸门与匹配的 Pi+NMG 提升测试。每个提案把经评审的策略 ID、修订与来源哈希绑定到其最低可接受长时程分数与留出或匹配重放评测引用。任何被接受的策略仍是一次经评审的 YAML 编辑；单个 rewrite、supersede、split 或 merge 提案必须保留证据，并在支持时使用既有 journal。

提案评审被有意与驱动分离。接受一个维护提案只记录一个人类/Agent 决定，永不编辑记忆。评审者随后必须调用既有的显式 rewrite/supersede/split/merge 操作，保留该操作自身的校验与回滚边界。这防止离线策略悄悄获得写入能力。

**实现状态：** 显式反馈收集、natural/controlled 来源、带日志的节点合并回滚、召回策略的 SkillOpt 适配器、形式化数据闸门、首次官方优化与匹配否决闸门均已实现。专用的控制器运行时策略通道已实现，并默认为仅影子运行；受控评测要求 controlled 来源，而生产驱动要求一个哈希绑定的三闸门批准 receipt 与回滚制品。把任何候选提升为 active/default 运行仍需要真实的匹配证据。维护策略身份、三分类归因、长时程闸门、持久提案存储与显式评审通道已通过 Core、daemon RPC 与 CLI 实现。自动提案生成、SkillOpt 优化与驱动保持禁用，直到自然标签通过其提升闸门。STG/LTG 上下文组合已实现，但它不是可逆的持久 STG 合并。

当前的 Pi 回归、七类别不变量套件、受控拓扑消融与严格七题 LongMemEval 匹配样本证明了集成与机制行为。完整的匹配 BEAM 100K 运行还展示了在一个固定的数据集/模型/裁判配置下相对空检索上下文的实质增益。它尚未证明跨套件、跨模型或重复运行的普遍能力提升。LongMemEval 样本确实为每道选定题目摄入了全部 haystack 会话，但其零配置 FTS/哈希路径漏掉了七个必需证据集中的五个。更广的主张仍需要跨套件的匹配外部 embedding 运行与重复模型运行。

公开评测组合被有意设计为互补而非单一复合排行榜：

- LongMemEval 仍是抽取、多会话推理、更新、时序推理与弃答的主要开发闸门；
- PersonaMem 评测自动事实/偏好/约束写入、演进的用户画像、作用域与当前状态选择；
- LoCoMo 评测时序/因果关联、多跳证据，以及从语义节点到叶子证据的扩展；
- BEAM 是后期规模与缓存压力测试，在任何 1M 或 10M 运行之前先从 128K 与 500K 开始。
- OmniMemEval 是首选的外部用户记忆评测 harness，因为它把那些套件（外加 HaluMem）统一在一个 `add`/`search` 客户端契约之后。NMG 只维护一个精简的 OmniMemEval 适配器。OmniMemEval 在强制检索下度量后端；本地匹配的 Pi runner 仍是度量召回触发与实际证据使用的必要手段。只有在达到对等之后才应退役重复的公开数据集解析、重放与打分。
- OmniMemEval 的 AgentBench/OpenClaw agent 记忆赛道在本阶段不被 Pi 采用。Pi 运行时行为仍由本地扩展与 RPC 测试覆盖，除非比较证据支持，否则不引入第二个 agent harness。

这些套件必须分开报告。匹配臂共享同一 reader、提示词、问题 ID、来源历史、证据 token 预算与裁判。答案质量与证据召回、注入 token、读取的后端记录数、图/层级深度、端到端延迟及索引/维护工作量一并报告。完整的适配器契约与推出顺序见 `evals/README.md`。

2026-08-11 的严格 LongMemEval 匹配回归使用了七个类别各一道固定问题。独立的协议评分器给出：无记忆 `2/7`、确定性 NMG `4/7`、带非排序影子遥测的 NMG `4/7`；通用诊断评分器给出 `1/7`、`4/7` 与 `4/7`。两个 NMG 臂通过了同样的四个类别、也在同样的三个上失败，因此在这道有界闸门中，遥测路径没有表现出答案质量回退。然而精确的官方证据 `recallAll` 是 `3/7` 对 `2/7`，因为随机性的 Agent 在排序策略相同的情况下选择了不同的 search/get 序列。因此一次重复的答案打平是回归检查，不是检索或成本等价的证明。完整参数、延迟、上下文与 token 记账记录在 `evals/longmemeval/README.md`。

本报告的 2026-08-11 七题结果与[评测总览](../evaluation-and-falsifiable-claims.md)中的另一份严格三臂快照（1/7、2/7、3/7）不同。现有记录无法确定样本、模型/裁判运行或评分流程是否不同；应将两者保留为独立历史报告，不要把分数差异归因于影子遥测。

完整的 Namesakes 拓扑审计还包含一个只读的流式反事实。在哈希阈值 0.5 时，94.74% 的传入非锚点提及会发出提案，错误提案会在 3,975 个实体中的 2,307 个上把 6,450 条外来记录错误共置。阈值 0.7 仍影响 1,479 个实体与 3,003 条外来记录，而正例召回降到 30.39%。这量化了在线提案的普遍程度与结构性污染，但不量化纠正事件或下游答案损害；自动身份变更保持关闭。

首次钉住的 OmniMemEval LongMemEval 仅检索冒烟使用了与 Pi 运行相同的七道固定问题。强制的 NMG 检索起初让五个用例变得可合理回答。失败轨迹暴露出两处简单的排序缺陷：未被核验的 assistant 回复与用户事实竞争，以及英文疑问词/功能词抬高了无关的词法分数。可选的来源-行动者过滤加上停用词感知的词法项，救回了那两条时序记录，保住了更新、偏好与 assistant 证据，并把计数结果从重复的 boot 提及改为互补的 boot 与 blazer 证据。计数用例相对官方证据列表仍为 2/3。检索保持在约 126–166 ms；普通上下文为 2.8–4.1k 字符，其中一条长的 assistant 日程为 7.5k。

在那两个欠缺用例上启用混合 FTS 没有救回任何额外必需证据，把上下文扩大到 7.2–7.9k 字符，并把一次时序检索抬到 2.04 s，因此该改动被否决。这支持针对性的来源/provenance 过滤与聚合，而不是更宽的候选扩展。

首次钉住的 OmniMemEval LoCoMo 冒烟暴露出一个上游集成细节：LoCoMo 维护一张 benchmark 本地的检索分发表，而不是使用共享 dispatcher。幂等的适配器安装器现在会同时打补丁。修复之后，官方摄入与检索阶段完成了全部 272 个会话与 1,540 道类别 1--4 题目且无失败。十 worker 检索耗时 54 秒；单次后端延迟均值为 329 ms、P95 为 619 ms，平均返回 4.15k 字符。至少一个官方证据 ID 的精确规范化证据文本出现在 61.8% 的题目中，全部 ID 都出现的为 49.6%。这些是检索诊断，不是答案质量主张；官方答案/打分阶段与匹配的无 NMG 基线仍然必需。本处报告的 1,540 道摄入题数尚未与[检索质量基线](../../../experiments/retrieval-quality/baseline-2026-08-16.md)中的 1,532 道计分题分母对账；不应将两种计数视为可互换。

一次全新命名空间的 LoCoMo 预算消融在 K=5、10、20 与 40 下分别得到 32.7%、39.0%、45.0% 与 46.6% 的精确带标签证据召回。平均上下文从 1.0k 增长到 2.1k、4.2k 与 4.9k 字符。因此 K=20 被保留为默认的拐点：K=40 只增加 1.6 个召回点，而多跳与开放域召回即便在更大的预算下仍然很低。这否决了更宽的默认上下文扩展，并把后续工作指向证据组合与查询感知排序。

同一次冒烟还在适配器边界暴露了一处表示丢失：NMG 存下了每个 LoCoMo 轮次的事件时间，但返回给 reader 的文本把它丢掉了。因此包含相对表达式的时序证据不足以推导出带日期的答案。Omni bridge 现在只对有时序信号的查询包含事件时间。在一次全新的 K=20 运行中，该子集中 450 条被检索到的带标签证据轮次每一条都有日期锚点；证据排序未变。新增成本为：663 道受影响的题目共 691 个字符，其余 877 道为零。这被保留为无损的、查询相关的渲染，而不是更大的检索预算。
