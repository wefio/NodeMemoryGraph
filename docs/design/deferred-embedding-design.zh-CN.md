# 延迟文档嵌入

[English](deferred-embedding-design.md) · [Terms](deferred-embedding-design.terms.yaml)

**Status:** draft

## 问题

现在一次 Add 离不开向量服务：accept 路径写日志条目，紧随其后的折叠要把这一批嵌入完才重写分区，
所以**上游一慢，写入就变成跑到平台杀掉为止的请求**。2026-10-29 那 220 次调用正是死在 120 s 上限；
现在加的"单次超时 + 批量调用"只是给这条路径**设了上限**，没有解耦——上游慢仍然让每次 Add 多花
约三十秒，并且仍然可以让它失败。

这件事比听起来重要，因为评测是串行的：所有 Add 结束后才开始第一次 Search。**Add 阶段是唯一会
因为失败而终止整轮的阶段**，而且一次 Add 失败就够了。检索丢一个向量只丢一道题的证据；Add 失败丢
整轮。

最直觉的答案——响应之后再嵌入——在这里不可用。部署里没有任何定时或后台触发（`edgeone.json` 只有
`maxDuration` 和 `regions`），而函数平台不承诺响应返回后继续执行。

## 目标

让写入路径依赖**持久化写入**，而不是依赖上游：

- 条目提交即算 Add 成功，上游在做什么都不影响；
- 质量按**单条记录**降级，绝不按轮次降级；
- 上游**拒绝**请求时仍然立即响亮地失败——否则整轮用词重叠打分，那是一个"看起来像检索能力问题"
  的错误结果，而不是一个能看见的错误；
- 不引入新故障态、不丢条目、积压有界。

## 设计

### 条目格式 v2

日志条目新增可选的 `vectors`，与 `messages` 对齐：

```jsonc
{ "v": 2, "generation": "...", "messages": [ { "role": "user", "content": "...", "indexText": "..." } ],
  "vectors": [ null, [0.1, ...] ],
  "vector_model": "<model>:<dims>:<profile>" }
```

`vector_model` 是向量空间的标识，和分区用的是同一个。它一旦与配置不一致，条目就当作"无向量"重新
嵌入——和分区标识过期同样处理：半个迁移会留下无法与查询向量比较的向量。

条目本身已经带了嵌入所需的全部输入（`indexText` 与消息时间），这正是"晚一点嵌入"可行的前提：
**原请求不需要还活着**。

### accept 路径

1. 提交条目，`vectors: null`（一次 PUT，与今天相同）。
2. **尽力而为的即时嵌入**，独立截止时间 `EMBED_INLINE_MS`（默认 8 s）：本条消息一次批量调用。
3. 及时返回 → 重写条目一次，写入向量。
4. 超时 → 保持 `vectors: null`，返回 200。条目已持久化，欠的只是一个向量。
5. 上游**拒绝**（不可重试状态，或可重试状态已用尽）→ Add 以 `embedding_unavailable` 失败。
   拒绝不是"慢"，它是运维必须看见的状态；否则代价是整轮无向量。

健康路径比今天多一次 PUT，批量调用次数不变。

### 排空

响应之后没有执行机会，所以积压必须由**后续请求**带走。任何触达某个用户的请求都可以替它排空：

- 按条数（`DRAIN_ENTRIES`，默认 2）与按时间（`DRAIN_MS`，默认 4 s）双重约束；
- **取最老的无向量条目**：折叠要最老的，检索要最新的，而排空的目标是"最接近被折叠的那批"；
- 被排空的条目合并成**一次**批量调用，然后逐条 PUT；
- 排空失败（超时以外的原因）只在本请求内停止，把条目留给下一次，**绝不让承载它的请求失败**。

Add 在自身 accept 前顺带排空（它本来就在写）；Search 只在预算允许时排空，并且第一次未命中之后
不再排空，避免阶段边界把一次慢检索放大成好几次。

### 折叠

折叠优先使用已存向量，其余与今天一样在同一次批量里补齐。它**从不等待排空**：折叠本身被允许作为
执行嵌入的那一方。

这也给出了积压的上界：折叠阈值（一批 8 条）加上上次折叠以来新到的部分。这正好是读窗口本来就要
覆盖的范围，所以无向量记录不会活得比持有它的日志条目更久。

### 读路径

pending 记录有向量就按向量打分，没有就按词重叠打分——两条路径都已存在。没有新的读行为、没有新的
短路：两种情况下条目都可见，这正是引入日志时要求的性质。

## 冻结接口（切片 1）

```js
// append-log.mjs
export function putLogEntry(bucket, key, entry)             // 已有
export async function listVectorless(bucket, key, options)  // {limit, generation}: 最老优先
export async function attachVectors(bucket, key, name, vectors, model)  // 重写单条

// worker.mjs
async function drainBacklog(env, ctx, budgetMs)             // 返回 {drained, remaining}
```

`attachVectors` 是 `vectors` 的唯一写入者，且必须**同名声重写**，让条目保持原来的到达位置：重排日志
会改变折叠先应用谁。

## 不变量（每条都要变成测试）

| id  | 不变量                                        | 缺了它会失败的测试                    |
| --- | --------------------------------------------- | ------------------------------------- |
| E1  | 条目已提交的 Add，即使嵌入超时也返回 200      | 永不响应的上游桩；条目必须立刻可读    |
| E2  | 上游拒绝时 Add 失败且不存任何东西             | 返回 400 的桩；不得留条目、不得留回执 |
| E3  | 无向量记录仍可按词重叠被检索到                | 关闭排空后检索仍返回该记录            |
| E4  | 无向量积压不超过"折叠阈值 + 一个到达窗口"     | 关闭排空后的突发写入                  |
| E5  | `vector_model` 过期一律重新嵌入，绝不参与比较 | 用不同模型写入的条目不得按向量打分    |
| E6  | 排空绝不让承载它的请求失败                    | 对着坏桶排空，请求仍 200              |
| E7  | 折叠用的是排空写下的那个向量，而不是再算一个  | 排空后折叠不得调用上游                |

## 失败矩阵

| 上游        | 桶   | Add 结果                            | 检索                |
| ----------- | ---- | ----------------------------------- | ------------------- |
| 正常        | 正常 | 200，向量即时写入                   | 完整                |
| 慢（> 8 s） | 正常 | 200，向量延迟                       | 排空落地前按词重叠  |
| 拒绝        | 正常 | 5xx `embedding_unavailable`，不入库 | 不变，且可见        |
| 正常        | 慢   | 写入提交后 200（COS 超时兜底）      | 完整                |
| 慢          | 慢   | 200 延迟；若写入本身超时则 5xx      | 同上                |
| 不可用      | 正常 | 5xx，不入库                         | 该 Add 缺失，且响亮 |

## 迁移

`v === 1` 的条目继续可读：没有 `vectors`，即"无向量"，会被排空或被折叠时即时嵌入。升级不需要重写；
一个从不排空的部署与今天的部署行为完全一致。与 pending 计数同一条懒规则：日志排空后 `vectors`
不存在，所以排空后的日志与旧部署写下的日志仍然**逐字节相同**。

## 工作量分解

| 切片 | 内容                                                  | 验收                                        |
| ---- | ----------------------------------------------------- | ------------------------------------------- |
| 1    | 条目 v2 + `attachVectors` + 即时截止 + E1/E2          | 面对永不响应的上游 Add 仍成功；拒绝仍然失败 |
| 2    | 排空（`listVectorless`、预算）+ E3/E4/E6              | 积压有界，且被后续请求带走                  |
| 3    | 折叠使用已存向量 + E5/E7                              | 已排空的条目在折叠时不再调用上游            |
| 4    | 文档、`/health` 计数（`vectorless`、`drained_total`） | 运维可见积压                                |

## 未决问题

- **检索要不要排空？** 花掉一次计分检索最多 4 s 去改善"这次检索自己会用向量打分"的记录。另一种
  选择是检索永不排空，把阶段边界的积压留给词重叠。
- `EMBED_INLINE_MS = 8 s` 是猜的。正确值应该是健康批量调用的 p99，而这个数没有按阶段测过。
- 每条被写入向量的条目多一次 PUT，在单用户 16 并发下是否明显？manifest 的 CAS 不参与，但桶会多看到
  一次写。

## 被否决的替代方案

- **响应后 fire and forget。** 平台不承诺响应之后继续执行；"以后会写"的向量等于永远不来。
- **只在折叠里嵌入（今天）。** 任何触发折叠的 Add 都继承上游延迟，而折叠就在 accept 路径上，这正是
  那次整轮失败的原因。
- **向量存旁路对象**（`vectors/<name>`），每条一次 PUT。写次数与重写相同，但写失败后条目与向量会
  互相矛盾，折叠还要合并两个列表。重写保持单一事实来源。
- **定时任务。** 部署里没有触发器；引入外部 cron 会多一个移动部件，而它的故障态是"永久无向量"。
