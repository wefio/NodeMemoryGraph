[English](verification-claims.md)

**Status:** draft  
**Authority:** 本文描述「声称账本」的形态。它引出的规则住在决策记录里，工作流住在

## 今天的「绿」是什么意思

`rtm:check` 打印 `12 verified`。照字面读，是说十二条性质都成立。证据真正支撑的比这弱：

```
bound    = 每条声明过的断言都绑定到一个在这份 commit 上通过了的命名测试
verified = 该性质在其范围内的所有情况都成立
```

测试通过只是一个**见证**：它说明性质在它跑过的那几个输入上成立，不覆盖断言所声称的
范围。2026-09-09 之前没有任何地方写过那个范围是什么——定义域从来没被写下来，所以这个缺口
看不见，只能被默认掉。

## 形式

```
∀ x ∈ D,  A(x) ⇒ P(x)
```

| 符号         | 工件        | 家                 |
| ------------ | ----------- | ------------------ |
| P            | `statement` | 契约断言           |
| D            | `domain`    | 契约断言           |
| A            | `assumes`   | 假设册里的具名条目 |
| 证据         | `check`     | 测试、检查或过程   |
| 证据买到多少 | `strength`  | 契约断言           |

### strength

| 取值       | 含义                                 | 例子                                                   |
| ---------- | ------------------------------------ | ------------------------------------------------------ |
| `decision` | 对 D 内每个 x 都有确定性过程判定 P   | `testOutputPassed(output)`、`validateReceipt(receipt)` |
| `witness`  | 样本通过；D 是被声称的，不是被覆盖的 | 大多数 `node-test:` 断言                               |

`documented-only` 是第三种状态，但在另一个轴上：它意味着**完全没有证据**，住在
`documentedOnly` 里，不在 `strength` 里。两个字段说同一件事，就多了一个。

本仓库里够得上 `decision` 的只有两处，都很小。**而且今天没有任何一条契约断言绑定到它们**，
所以账本报 `0 proven` 对 12 条 `witness`——这个缺口是可见的，不是被默认掉的。`witness` 不是
没用：它是我们手里最便宜的证伪工具，只是被误读成了证明。

## 五个工件，各自一个家

| 工件       | 文件                           | 它回答什么                             |
| ---------- | ------------------------------ | -------------------------------------- |
| 声称账本   | `.rcp/contracts/*.yaml`        | 声称了什么、在什么域内、依赖什么假设   |
| 假设册     | `docs/design/assumptions.yaml` | 什么被当成理所当然、谁负责、怎么被证伪 |
| 反例账本   | `.rcp/counterexamples.yaml`    | 对某条声称提出过什么，用的哪个输入     |
| 收据       | `.rcp/receipts/*.json`         | 实际跑了什么、在哪个版本上             |
| 未覆盖范围 | PR 的 `## 未验证项`            | 什么被声明为射程之外                   |

今天已有的：声称账本、收据、未覆盖范围。假设册与反例账本是提案。

## 闭环在哪里合上

把 D 写下来并不会让 D 变诚实。做到这件事的仪器是变异测试，而且它属于这本账，不是旁边另一件事：

```
账本声明 D / A / P
  → rtm 把证据绑到声称上
  → 变异测试测量证据有没有判别力
  → 存活的 mutant 就是模型里的反例
      → 语义上不可能（不在 D 内）？ → 改的是 domain 那条声明，不是测试
      → 在 D 内？                  → 修证据，或者承认 P 不成立
```

第一支就是 CEGAR 的动作：伪反例精化的是抽象模型，不是产品。这里的「模型」就是那三行声明，所以
精化就是对 `domain` 的一次修改。

2026-09-09 那次变异实验找到一个真缺口（`changedPaths` 排序）并修了测试。能预先指出这个缺口的
那条 domain 声明从来没被写下来，所以那次修复**没有地方**被记成一条声称——这是缺那一列的代价，
不是变异实验的失败。

## 检查能强制什么，不能强制什么

能强制（每条都只断言结果的性质，绝不看工具身份）：

- 非 `documented-only` 的断言都有 `domain`；
- 每个 `assumes` 条目都能解析到假设册；
- 每个 `open` 反例都带 reproducer；
- `rtm:check` 分别报告 `bound` 与 `proven`，并给出 strength 分布。

不能强制，也不声称：

- D 是完整的；
- A 是合理的；
- P 是我们真正想要的。

这三个曾经是开放式问题。现在它们变成**可以争辩**：假设有 owner 和证伪路径，定义域可以被一个
存活的 mutant 攻击，P 在决策记录里被辩护。

## 停止条件

```
closed(改动) =
    scope 内每条断言都被绑定
      或显式 documented-only 且列入 PR 的 未验证项
  ∧ scope 内没有 open 反例
  ∧ 改动触及的每条假设都在册
```

## 它为什么保持很小

- 两个 `decision` 强度已经存在，它们的代码不改。
- 三个新字段都是可选的，旧契约仍然合法，回填可以增量做。
- 没有新工具、没有新入口：检查扩在 `rtm:check` 与 `docs:check` 上，二者本来就跑在每条路由上。
