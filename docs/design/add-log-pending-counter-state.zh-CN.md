# pending 计数器：状态、迁移与不变量

**Status:** draft
**Created:** 2026-10-28

属于 [Add 写不可变日志条目](add-append-log-and-fold-design.zh-CN.md) 的一部分，设计由那篇负责。
本页只负责一个部件：`manifest.pending`——决定"一次检索要不要看日志""一次请求要不要折叠"的那个计数。

## 为什么需要一张表

日志路径上线时，计数器是"加一、然后祈祷"的值。四轮复核在同一部件里找出六个缺陷，每一个都是
**没有人写下来的那次迁移**：

| 缺陷                                         | 形状                                     |
| -------------------------------------------- | ---------------------------------------- |
| 折叠把 `{name, entry}` 当字符串迭代          | 条目从不被应用，删除也不发生             |
| 计数只减"已应用"的条数                       | 回执已存在、跨代的条目永不退休           |
| `Object.assign(manifest, withPending(m, 0))` | 归零永远写不进 manifest                  |
| 删除失败时计数已扣                           | 同一批被扣两次                           |
| 先写条目、后提交计数                         | 盘上有条目而计数不含它，被搜索短路藏起来 |
| 把"抛错"当成"没落盘"                         | 为一条已在盘上的条目释放了预留           |

这些一旦画在纸上都不算难。这一页存在的意义就是这个。

## 状态

`pending` 与日志是同一件事的两个观测，所以状态是"对"：

| 状态               | `manifest.pending` | 日志             | 由什么到达           |
| ------------------ | ------------------ | ---------------- | -------------------- |
| **C** 干净         | 缺键               | 空               | 所有路径最终汇合于此 |
| **P** 正常积压     | `n > 0`            | `m` 条，`n >= m` | 受理快于折叠         |
| **D** 折叠中       | `n > 0`            | `m` 条正在被折   | 一次折叠在途         |
| **R** 计数偏高残留 | `n > 0`            | 空               | 预留了但写入从未落地 |
| **G** 跨代残留     | `n > 0`            | 上一代的条目     | reset 与折叠竞争     |

**刻意不存在"计数偏低"状态**（`pending` 缺键而日志非空）。在"先写条目、后提交计数"的顺序下它
可到达；改成**先留位、再写**之后它不可到达——这正是那个顺序的理由。**看到它就说明有 bug**：
检索会跳过日志并藏起数据。

## 迁移

`E` = 当前代可读条目集合，`pending` = 存下的计数。每行都写明这次迁移必须留下什么。

| 从          | 事件                                  | 到   | 必须留下                                                                |
| ----------- | ------------------------------------- | ---- | ----------------------------------------------------------------------- |
| C           | 受理                                  | P    | 计数**先于**条目持久化提交（`acceptAdd`）                               |
| P/D         | 受理                                  | P/D  | 计数 +1，登记预留（`acceptAdd`）                                        |
| P（已预留） | 写失败且 `logEntryLanded` = **true**  | P    | 条目已在盘上 → 按成功返回                                               |
| P（已预留） | 写失败且 `logEntryLanded` = **false** | P    | 计数 −1（`releasePending`）                                             |
| P（已预留） | 写失败且 `logEntryLanded` = **null**  | P    | 计数不动，抛出原错误                                                    |
| P/D         | 折叠应用一条                          | D    | 回执与分区在同一次提交里写入                                            |
| D           | 折叠吸收一批                          | P/C  | 退休 `S` = 已应用 ∪ 回执已存在 ∪ 跨代；计数 − \|S\|；**提交之后**删 `S` |
| D           | 删除失败                              | P    | 回读日志重算（`reconcilePending`），不再用减法                          |
| R           | 任意折叠/排空一轮                     | C    | 每轮释放一格（`releasePending`），并作为进展上报                        |
| C/R         | 计数为 0 的排空轮                     | C    | 不写、不 CAS                                                            |
| G           | 折叠                                  | C    | 跨代条目随批次退休，绝不应用                                            |
| G           | 检索                                  | G    | 其他代的条目被过滤掉（`pendingForSearch`）                              |
| 任意        | reset                                 | C    | 先立代际屏障，再 `clearLog`（I4）                                       |
| 任意        | 容量读取                              | 不变 | 只报告计数，不写                                                        |

## 跨代遮蔽（状态 G 且计数为零）

状态 **G** 只在计数大于零时才安全。两条独立机制会破坏它，只修任一条都不成立：

- **读取窗口。** 带过滤的列举必须在**读取时**过滤。先按键截断再过滤，会让少量旧代
  条目占满整个窗口，`pendingForSearch` 返回空，而当前代的条目明明躺在日志里。
  因此 `listPending` 在给定 `generation` 时列举全部键（不给时仍保持有界）。
- **reset 的交接。** reset 提交的空清单原本会丢掉 `pending`，于是一次失败的日志清理之后，
  遗留的旧代条目**有对象、无计数**。随后折叠会把这些从未计入的条目退休并从计数里减掉，
  把计数推向零；一旦到零，`pendingForSearch` 的短路就会把 reset 之后受理的一切藏起来。
  现在 reset 把计数**带过去**，并且只在 `clearLog` 成功之后才归零，且以"计数未变动"为条件，
  因此不会吃掉并发受理的预留。

只落第一条，计数仍会漂到零；只落第二条，读取窗口仍被饿死。两条都在服务同一条 T1：
计数不得低于当前代可读的条目数。

### 读取窗口是"有界"而不是"消除"

带过滤的列举会扫描 `SCAN_FACTOR * limit` 个键（读取路径是 4 × 8 = **32**），所以遗留条目
超过 32 条时，当前代的条目仍可能被挤出单个窗口。它会**自愈**而不是永久失效：reset 交接把
遗留条目的数量带进了计数，折叠触发器因此看到积压并退休这些条目，之后窗口重新由当前代条目填满。

## 不变量

- **T1 —— 绝不低于真值。** 每次提交都满足 `manifest.pending >= |可读条目|`。反向意味着
  一条已受理的条目被每次检索挡住，因为 `pendingForSearch` 在计数为 0 时直接短路。
- **T2 —— 每个偏高都有回程。** 偏高是安全方向，但不是终态：写失败释放（`releasePending`）、
  删除失败回读（`reconcilePending`）、排空时空日志每轮释放一格。没有 T2，低于
  `FOLD_TRIGGER` 的偏高没有任何触发器会注意到它。
- **T3 —— 有界收敛。** 反复调用 `POST /admin/fold` 能在 `ceil(pending / FOLD_BATCH) + 1`
  次内到达 `C`，且最后一次之前的每次调用都返回 409。
- **T4 —— 缺失即零。** `pending` 用删键表达，不存 0；格式仅在有条目待处理时是 v4，因此排空后
  的存储与"从未有过日志"的部署逐字节相同。
- **T5 —— 幂等由名字承载，不由计数承载。** 重放靠条目名与回执守卫，不当依赖计数，所以计数错了
  最多多花一次列举，不可能重复写入。

上表每行都点名了执行它的函数，每条不变量都点名了破坏它时会失败的那条断言：

| 不变量 | 由谁保证                                           | 失败时红的断言                                      |
| ------ | -------------------------------------------------- | --------------------------------------------------- |
| T1     | 先留位后写、落地三态判定                           | `an accepted but unfolded entry must be searchable` |
| T2     | `releasePending` / `reconcilePending` / 空日志释放 | `a single residue slot must report clean`           |
| T3     | `foldRoute` 的 8 轮上界 + 409                      | `one slot is left after a full pass`                |
| T4     | `setPending` 归零删键；`manifestFormat`            | `test-manifest-pending.mjs` 的字节一致性断言        |
| T5     | 条目名 + 回执                                      | `replay must survive folding`                       |

## 这张表没有覆盖什么

- **真实的写失败。** 三态判定用假 bucket 测过；让它被选中的条件（真实存储上对象 PUT 抛错）
  没有端到端跑过。
- **同一用户的并发折叠。** manifest CAS 把它们串行化，所以表里假设一次只有一个提交；CAS 落败
  时整次迁移从头重跑——表依赖这一点，而不是证明它。
- **代码之外被改坏的计数。** `loadManifest` 会把非整数计数判为 `storage_corrupt`，其余
  "手工写成别的值"不在范围内。
