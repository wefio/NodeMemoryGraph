# 受限 OoO 的自举开发

**Status:** draft
**Related:** [选择理由](../decisions/proposed/2026-09-09-ooo-bootstrap.zh-CN.md)、[实验依据](../experiments/ooo-admission-2026-09-08.md)

## 目标与适用范围

用乱序执行开发乱序执行，让真实开发任务决定下一步能力，而不是先构建完整调度平台再寻找用途。本文定义候选契约与阶段验收，不表示运行时已经具备这些能力；实现证据由上面的实验报告承载。阶段顺序是依赖计划，不是进度台账；实际接手与阻塞使用 Task Board。

首版保持固定顺序、显式依赖、最多一个等待任务和一个执行任务、不抢占、不自动重规划；推测只允许宿主侧不花 token 的那一类（规则见推测盈亏平衡决策），靠猜测掩盖等待不做。只有真实外部等待允许越过队首；输入失效、依赖失败或权限不足不算等待许可。没有独立任务就顺序执行，不加入 sleep 或人为延迟制造乱序。

共享层负责宿主无关的计划、选择、任务版本与验收状态；黑板负责跨进程交接。Pi 负责模型循环、工具与执行进程，适配器保持薄层。NMG 不在这项工作中自建通用 shell、沙箱或 Agent harness。

## 最小引导边界

现有精确快照任务不能直接生成开发补丁。允许一次普通开发引导，只补齐下面三个能力，然后立刻进入真实自举轮次：

1. 输入绑定冻结源码、显式文件集合和任务说明；Pi worker 返回有大小上限的补丁产物，不直接修改共享工作区。扩展限定的开发任务契约，不伪装成现有 heading/join 操作。
2. 宿主启动明确允许的后台检查，将启动身份、终态和有界日志作为外部事件。任务进入等待后释放执行占用；等待检查进程不算第二个 Agent 执行者。worker 不获得任意命令权限。
3. 宿主把补丁送到独立候选目录验证，按事先固定的检查给出接受、拒绝或无法判定；只让接受结果解锁依赖。最初可由操作者批准应用和提升，不必先实现完整 CLI。

先复用已有黑板、协调器和 Pi SDK 边界；不以“先搬完全部实验代码”为引导前提。引导所需的最小协议收进共享层，研究启动器可以暂时保留。隐藏入口的引入或改动遵循[隐藏能力登记](hidden-features-registry.md)，本文不新增开关。

引导结束的检查：一个真实 Pi worker 能针对冻结的 OoO 源码返回补丁；补丁只能在指定候选目录被验证；后台检查能提供真实退出事件；过期输入与错误尝试不能被验收。未达到这一步时，报告“引导”，不报告“自举”。

## 第一轮真实开发任务

优先用“后台检查身份与失败恢复”作为开发需求。先冻结接口和检查命令，再固定计划 A、B、C：

| 任务 | 输入和职责                                                                                               | 依赖与允许输出                                            |
| ---- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| A    | 等待真实的引导集成检查；根据结果修复检查身份、退出处理或已暴露的缺陷。没有缺陷则返回有依据的无需修改结论 | 外部检查事件；仅指定实现文件的补丁或结论                  |
| B    | 基于同一冻结接口，为过期事件、重复事件、取消后晚到结果补充缺失的回归检查；先检查是否已有覆盖             | 不依赖 A 的日志或补丁；仅指定测试文件的补丁或无需新增结论 |
| C    | 对 A/B 的已接受产物做组合检查，形成可供提升的候选版本                                                    | 依赖 A、B；组合补丁与验证证据                             |

接口若不能提前冻结，就先解决接口，不能声称 B 独立。B 不得使用尚未验收的 A 产物；A 也不能在执行中悄悄改掉 B 绑定的契约。接口必须变化时，作废受影响产物，结束本轮并显式建立新计划。

预期过程是 A 等检查、B 越过 A 运行、A 消费检查结果、C 验证组合。若检查在选择 B 前就结束，本轮是顺序完成；若在 B 运行中结束，不抢占 B。两种情况都保留真实时间线，不强凑 B→A→C。

第一轮成功不要求凭空发现 bug：补丁或无需修改结论都须有可检查依据。但宣称“开发自举完成”至少需要一个对 OoO 本身有用的变更由该执行链产出、独立验收并被下一轮实际使用；纯标题任务、模拟 worker、无变更演示不满足这个标准。

## 必须能检查的契约

### 结论的可检查依据

无需修改不是一个可以凭叙述成立的结论。宿主在轮次开始前冻结每个任务需要的用例清单，每个用例是一个显式声明：用例名，以及（补丁路径下）新增测试标题必须包含的词元。该清单随指令原样打印给 worker，不存在未告知的验收规则。

- 无需修改结论必须按用例名引用标题，宿主在冻结源码中解析该标题是否存在；引用不存在、标题不符、缺少用例或凭空多出用例一律拒绝。
- 补丁路径按词元解析：新测试标题必须包含对应词元。
- 无法完成是阻塞报告，不是完成：它阻止后继任务被解锁，不释放依赖。

标题解析只能证明“存在一个对应标题的测试”，不能证明该测试真的断言了这个用例。这个领域已有的机械判据是变异测试：一条新增测试只有在“在原实现上通过、且在至少一个存活变异体上失败”时才被保留（[Mutation-Guided LLM-based Test Generation](https://arxiv.org/abs/2604.01518v1) 的保留规则），它同时挤掉了空洞测试与重复测试。要证明某个用例未被覆盖，应当用这个判据，而不是标题匹配：先用变异确认“破坏该行为后冻结检查仍然绿”，再把已证明的缺口交给修复任务。

worker 失败、超时或输出被截断都不是完成：它被记为一次失败尝试及其原因，本轮不自动重试，也不解锁后继。给 worker 的格式契约必须把 digest、可编辑路径和两种合法 JSON 形状预先填好；让 worker 自己复述身份信息是已知的失败模式。

- 计划和执行票据绑定任务 ID、计划/输入摘要、依赖产物摘要、尝试编号与租约。外部事件还绑定检查运行身份；仅有 PID 或任务名不足以认定归属。- worker 提交产物不等于完成。共享协调器验收时重新检查版本、尝试、取消状态及租约；迟到、重复、失效结果不能解锁后继。语义要求不必照搬某种特定状态枚举。
- 外部检查失联或重启后无法确认结果时，返回无法判定或显式重新执行，不把“进程不在了”当成成功。仅自动重试已声明可重入的检查。
- 取消与验收竞争必须有确定终态；取消后不再接纳该尝试的产物。检查与模型调用有时限、日志/产物上限及清理责任人。
- 补丁应用前检查基线摘要和路径许可，拒绝越界、路径穿越及符号链接逃逸；验证器和运行中协调器不属于候选补丁的可修改执行面。
- worktree 是文件协作隔离，不是安全沙箱。执行候选测试会运行代码；首轮仅针对获准的仓库代码与固定检查，不声称能够安全运行任意不可信代码。若任务需要更强隔离，先由宿主提供隔离再开放该任务。

安全验收至少覆盖：重复/晚到事件、旧版本补丁、租约转移后的旧 worker、取消竞态、worker 退出、协调器重启、检查失联、产物越界，以及 A/B 分别通过而组合失败。复用已有检查，新增只覆盖真实缺口。

## 按真实阻塞推进

| 阶段          | 交付切片                                                           | 离开该阶段的证据                                               |
| ------------- | ------------------------------------------------------------------ | -------------------------------------------------------------- |
| S0 引导       | 上述三个最小能力；记录允许执行的工具与检查                         | 真实补丁与真实等待事件可通过受限边界；安全负例拒绝             |
| S1 第一轮自举 | 执行 A/B/C，收集阻塞和无需修改结论                                 | 时间线证明合法越过；有用开发产物经独立验收，下一轮采用         |
| S2 恢复自举   | 用 S1 基线开发本轮实际暴露的恢复、取消或预算缺口                   | 故障注入后无重复完成、错误解锁或无限等待；重启可恢复或明确终止 |
| S3 可用入口   | 只为重复出现的手工动作添加提交、查询、取消入口；稳定共享持久化契约 | 不修改研究脚本即可重复完成受支持任务；作用域回归通过           |
| S4 对照评估   | 对同一冻结计划比较顺序执行和 OoO                                   | 报告质量、耗时、tokens、失败与人工干预，不预设收益             |

每轮开始先复核上一轮暴露的问题，再固定本轮计划。遇到缺口，记录任务、预期、实际现象、最小复现和阻塞能力；选择影响下一轮最小闭环的问题修复。调查细节和时间线放实验记录，不复制进本设计。没有证据的通用平台能力继续留在范围外。

## 旧版本驱动、候选版本受测

每轮开始固定协调器、Pi adapter、验证规则和输入基线的版本或内容摘要；未提交内容也必须冻结，不能引用继续变化的共享目录。任务可以产出下一版调度器补丁，但运行中进程不能热加载它。

验证器与执行产物分离：Agent 不能通过改掉测试命令或验收条件让自己通过。新增测试可以作为产物，但不能替代本轮预先固定的安全检查。涉及验证器本身的变更由本轮之外的评审批准。

仅在组合验收和独立批准后，把候选提升为下一轮基线；保留上一轮可运行版本。失败就丢弃本轮执行环境、保留证据并回到旧基线，不在失败版本内无限修复自身。独立评审提供有界可信度，不是任意代码正确性的数学证明。

## 与公开工作的相对位置

这一节记录外部对照，不重复本文自己的契约。[五级自改进分级](https://d2i-ai.github.io/awesome-recursive-self-improving-agents/)把“能提议、能应用、能验证”与“能改写改进机制本身”分开：L1 手工、L2 辅助（系统可提议候选与诊断证据，人负责验证与应用，改进机制由人维护）、L3 程序化自改进（自主提议、应用并验证运行组件，但改进机制固定或外部维护）、L4 有界 RSI（连自己的改进机制一起改写）、L5 通用 RSI。

按这个标准，本工作当前在 **L2**：每轮的指令、清单、验证器和提升都由人预先写好并人工批准，没有任何一轮自动把候选变成下一轮基线。S1 的出口条件（一个有用变更被独立验收并被下一轮采用）正是从 L2 迈向 L3 的那一步，目前未达到。

对照的是同一条战线的已发表系统，它们都在 L3 且有可测增益：

| 系统                                                        | 自改范围                                         | 验收方式                                                                                         | 报告增益                                                     |
| ----------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| [MOSS](https://arxiv.org/html/2605.22794v1)                 | harness 层：路由、状态、派发、钩子、会话生命周期 | 计划评审 + 代码评审 + 短命试验容器重跑任务，结论收敛后仍需使用者显式执行 `moss evo apply` 才提升 | 四任务均分 0.25 → 0.61                                       |
| [DGM](https://arxiv.org/html/2505.22954v3)                  | 自身 Python 代码库，经验证据代替可证明改进       | 在编码基准上实测，能编译且保留编辑能力的版本才入档                                               | SWE-bench Verified 20.0% → 50.0%，Polyglot 14.2% → 30.7%     |
| [SICA](https://arxiv.org/abs/2504.15228)                    | 自身实现，用基础编码工具                         | 基准实测                                                                                         | SWE-bench Verified 子集 17% → 53%                            |
| [AHE / 可演化 harness](https://arxiv.org/html/2608.08466v1) | prompts、tools、memory、状态、执行策略           | 外部奖励信号，runs 目录、tracer、验证器与模型配置只读                                            | BabyAI +39.3、Crafter +33.0、TextWorld +25.0、MiniHack +15.0 |

本设计与它们的重合部分是已经形成共识的做法，不是本工作的新意：验证器与奖励信号必须在自改进回路之外（[harness 自改进综述](https://lilianweng.github.io/posts/2026-07-04-harness/)：“The evaluator and permission control should likely sit outside the loop”），被测面之外的目录、跟踪器、验证器、模型配置只读，以及提升需要人显式批准。DGM 记录了绕过验证的实际案例：其 agent 删除了标记工具调用的日志，从而绕开了幻觉检测函数，而检测函数对该 agent 是不可见的——本设计用“worker 不能改验证器、不能自批、不接受 worker 的通过标记”在结构上排除这一路径。

三个可以指认的差别：

- **对象**。已发表系统优化的是提示、技能、记忆、工具或整个代码库，或者如 [HarnessX](https://arxiv.org/abs/2606.14249)、[自演化 harness](https://jxzhangjhu.github.io/blog/2026/self-evolving-agentic-harnesses/)那样做整块 harness 的演化。本工作把**等待结构本身**当作开发对象：固定顺序、显式依赖、最多一个等待任务与一个执行任务、不抢占、不推测；越过队首的许可来自真实外部检查这一事件，而不是推测未来调用。harness 自改进的讨论里，并行与后台任务是被建议的能力（“make parallelism explicit and inspectable”），不是自改进维度。
- **对等待的处理**。把工具延迟变成收益的已发表做法是推测执行，例如 [PASTE](https://arxiv.org/html/2603.18897v1) 用离线挖掘的模式在空闲资源上预跑可能用到的调用，任务完成时间平均降 48.5%，但它的预测量依赖于对下一步的预测（Top-1 约 27.8%），并且必须能抢占推测工作。本工作不做预测也不抢占：它用等待时间跑一个本来就必须做、且与 A 无依赖的任务。这是设计空间里另一个点，不是同类方法的改进版。
- **验收语义**。已发表系统用基准分数或评分器作为唯一信号；本设计要求每个用例解析到可核对的依据，并把“无法完成”与“无需修改”区分为阻塞报告与已解决结论。

本工作**缺**的也正是这个领域的证据标准：可测增益、重复试验（MOSS 用多轮短命容器暴露 flakiness）、留出任务集与跨模型检验。目前 S1 只有单轮、单模型、单检查的记录，因此即使出现被采纳的变更，也不能据此声称速度或质量收益，S4 的对照必须按重复试验和留出任务集来设计。

### 乱序执行：真正的对应物是“乱序执行 + 顺序提交”

处理器里与本工作同构的不是“并行”，而是**乱序执行 + 顺序提交**：指令乱序进入功能单元，但通过 reorder buffer 在 retire/commit 阶段按程序顺序生效，从而得到可精确恢复的状态（[Out-of-order execution](https://en.wikipedia.org/wiki/Out-of-order_execution)、[Reorder buffer](https://wwang.github.io/teaching/slides/Comp_Arch/Reorder_Buffer.pdf)）。本设计的位置与之几乎逐个对应：worker 乱序运行（B 先于被阻塞的 A），计划与票据充当 reorder buffer，协调器是唯一的 retire 阶段，A 的输入只在检查终态事件之后绑定。验收规则（接受/拒绝/无法判定）就是“什么算提交”的定义。

差别在推测。经典 OoO 的收益很大一部分来自推测执行和回滚（分支预测、squash），代价是必须能丢弃错误路径的状态。本设计**不推测也不回滚**：它只重排本来就必须做的工作，越过队首的许可来自真实外部事件。所以它不需要 squash 机制，但收益上限也明显更低——这个取点必须诚实保留，不能在对照中把它当成“同类的更快版本”。

### Agent 乱序执行：领域默认是无界并行，本设计更严

把计划当 DAG 做依赖感知调度已是主流做法：plan-as-DAG 先把整个依赖图规划出来再并行执行（[LLMCompiler](https://www.agentpatternscatalog.org/patterns/llm-compiler/)），生产口径的 fan-out 报告把墙钟时间降低 36–50%，依赖感知 DAG 相对串行约 1.35×，而“忽略依赖全并行”会牺牲正确性（[DAG 编排](https://particula.tech/blog/dag-agent-orchestration-fan-out-fan-in-latency-parallel-execution)）；工具延迟的另一条路是猜测下一步调用（[PASTE](https://arxiv.org/html/2603.18897v1)，平均完成时间 −48.5%）。本设计比这些**都更严**：固定顺序、最多一个等待任务与一个执行任务、不抢占、不推测。因此本轮的价值主张只能是验收语义（可证明的缺口、宿主验证、不能自批），不是并行吞吐；对照时必须按这个定位设计。

后台委派、持久会话快照、断线重连与人工暂停恢复在今天的 harness 框架里已是常规能力（[Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/concepts/harness)、[Mastra durable agents](https://mastra.ai/docs/harness/durable-agents)、[Inngest durable agents](https://www.inngest.com/docs/learn/durable-agents)）。S3 若要加提交/查询/取消入口，应当直接对这些已有形状对齐，而不是重新发明一套轮次脚本。

### 分布式通讯：现有机制都有既有名字

- **fencing token**。本设计的 `attempt` + `inputDigest` 就是 fencing token：一个每次重新认领就递增的值，而**资源方必须自己拒绝倒退的 token**（[Kleppmann, How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)：“requires the storage server to take an active role in checking tokens, and rejecting any writes on which the token has gone backwards”）。协调器的 `submit()` 在事务内重新校验 `bound()` 后才写入产物，符合“检查必须由资源在提交点执行”这一要求，而不是在写之前顺手看一眼。Kleppmann 的 GC 暂停案例（持有者不知道租约已过期，回来继续写）正是本设计里“worker 在租约失效后继续工作、其产物被判 stale”的情形，这给了那条规则一个已发表的正确性论证。
- **失败检测器**。异步系统里无法区分“已经崩溃”与“只是很慢”，一致性因此需要额外的失败检测器假设（[FLP](https://homes.cs.washington.edu/~arvind/cs425/doc/fischer.pdf)、[Chandra–Toueg](https://dl.acm.org/doi/10.1145/226643.226647)）。所以“检查宿主永不上报”只能得到无法判定、绝不能算成功，而失败的检查可以释放修复任务却不能接受它——这是该边界上的教科书选择，不是本工作的新意。
- **exactly-once 是 at-least-once 加幂等接收方**（outbox/inbox 与消息 ID 去重，见 [delivery guarantees](https://event-driven.io/en/outbox_inbox_patterns_and_delivery_guarantees_explained/)）。本设计里重复的终态证据返回 duplicate、同一产物重复提交是惰性的，属于同一模式；“只自动重试已声明可重入的检查”也该按这个口径解释。
- **saga/补偿**。失败的检查释放后续修复任务而不接受它，是把回滚换成了补偿动作。
- **结构化并发**。每个任务都有明确所有者和有界生命周期，子任务不得超出父作用域（[Swift 提案](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0304-structured-concurrency.md)）。这正是“最多一个等待任务和一个执行任务”“worker 不超出本轮”“拒绝的认领不被人为过期”背后的口径，也是 S2 应该保持的不变量。
- **持久执行需要确定性与重放**。以日志重放为核心的系统要求编排代码确定、副作用隔离到 activity 并记录其结果（[Temporal](https://learn.temporal.io/tutorials/go/background-check/durable-execution/)、[确定性与重放](https://jack-vanlightly.com/blog/2025/11/24/demystifying-determinism-in-durable-execution)）。本设计“冻结接口 + worker 只能产出不可信产物、由宿主应用”已经符合这个分割（模型调用就是不确定的 activity），但**缺重放**：轮次状态目前只存在于 SQLite 协调器与 JSON 报告里，进程结束后无法重放，S2 的恢复能力应当采用日志+重放模型。
- **黑板与 tuple space**。黑板架构的经典缺陷是没有控制结构，需要显式的控制组件（[Hayes-Roth](https://www.semanticscholar.org/paper/A-Blackboard-Architecture-for-Control-Hayes-Roth/c79a41dc13c796c26388f8cbf599c67126374e39)）；Linda 把这一点抽象成共享元组空间（[Linda](<https://en.wikipedia.org/wiki/Linda_(coordination_language)>)）。本设计的黑板只承担跨进程交接与认领，控制留在固定计划与协调器的选择函数里，正是该缺陷的对应处置。

### 由此得到的改进清单

1. S2 采用日志+重放的轮次记录，把模型调用作为不确定 activity 记录其结果，使重启可恢复，而不是只留一份报告。**部分完成**：重启恢复已成立（状态全在 SQLite，后继进程从存储继续：活认领不被偷、尝试号与票据身份保留、重复产物幂等），但**重放仍缺** —— 模型调用的结果只存在于 JSON 报告与 `accepted-*.json` 里，无法从日志重建。
2. 审计每一处写入路径是否都在提交点校验 token；当前 `submit()` 已做到，`cancel`/`issue`/已接受结果的等价性需要逐项确认。**已做**：`submit()` 在提交事务内重校 `bound()`；新增的 `cancel()` 以推进尝试号围栏整个轮次，因此迟到产物得到 `stale` 而非被接受；`abandonCheck()` 只认签发的票据（伪造票据无效）。
3. 增加显式的本轮取消路径，保证取消后没有孤儿 worker 或检查进程。**已做**（机制层）：`cancel(reason)` 推进每个任务的尝试号、撤销未决 handoff、把检查表置为终端，`next()`/`claim()`/`issueCheck()`/`externalReady()` 一律拒绝，取消原因跨重启保留。孤儿进程的**实测**仍缺（尚未在真实多进程下取消一次运行中的轮次）。
4. S4 的对照必须回答“本设计会不会更慢”：变异复检与候选目录都是本轮新增的宿主开销，不能只报收益。

S2 的退出条件“故障注入后无重复完成、错误解锁或无限等待；重启可恢复或明确终止”现由
`evals/ooo-execution/recovery.test.ts` 的 8 个确定性测试覆盖：崩溃后继者不偷活认领、重复提交为
`duplicate` 且不二次释放依赖、被撤认领的产物为 `stale`、租约失效是新一代而非静默成功、永不回报的检查以
`undecidable` 显式终止、伪造票据不能终止等待、取消围栏迟到产物且跨重启保留、存储按列增量迁移且保留既有状态。5. 统一术语：协调器=retire/commit 阶段，接受=commit，拒绝=squash，attempt digest=fencing token。

### 推测的落点（规则由决策记录拥有，本节只列可落地的位置）

是否启用、以及启用条件，由[推测盈亏平衡决策](../decisions/proposed/2026-09-11-ooo-speculation.md)拥有；本节只回答“哪些点适合”。该决策仍为 proposed，所以上面“不推测”的现行规则继续有效，直到它进入 implemented。按**猜错花掉什么**分三类，这一点决定了一切。

**已有前提**。安全推测需要的三件事已经就位：（a）错误的推测产物必须能丢弃且不得生效——补丁契约只允许产出提案、由宿主应用，worker 没有不可逆副作用，所以 squash 无需回滚任何状态；（b）提交点必须能廉价判定猜测对错——真实检查终态带检查身份与 digest，正好是那个判定点；（c）提交顺序不变。`inputDigest` 会把假设绑定进输入，因此**猜错的产物自动失效**（fenced）而不是被误接受：这正是 ROB 保证精确状态的那件事在我们这里的对应物。

**当前数据**。最新一轮：检查 1.92 s，B 56 s，重叠 1.92 s，等待只占轮次约 3% 且已被必修任务填满。本仓库正常外部等待的上限是整轮验证的 134.5 s（收据实测）。在今天的输入下只有 A 类值得做；B 类不采纳，理由见决策记录。

**一个反向判断**。我们的检查几乎每轮都 passed。若某个依赖的假设命中率长期接近 100%，正确做法通常是**取消这个依赖**而不是推测它，因为等待本身没有信息量。

**先要知道数字**。门控依赖每轮的 token、分步墙钟、被掩盖的等待与白跑成本，而现在的轮次报告只有检查结果、没有 token 字段——这是开始推测之前的第一个小改动，否则“有没有适合的点”无从判断。

### 状态机、LLM 猜测与 LLM 打回

### 状态机、LLM 猜测与 LLM 打回

**任务登记状态机：采纳。** 每个任务声明自己的状态与就绪条件，转移由宿主根据已记录的事实计算。这正好解决黑板架构“没有控制结构”的老问题（需要显式控制组件），也是 S2 缺失的重放能力的前提：持久任务编排用事件源（append-only 历史）表示状态，崩溃后靠重放恢复决策，并要求编排代码确定、副作用隔离在 activity 并记录其结果（[Durable Task 重放](https://github.com/Azure/durabletask/blob/main/docs/concepts/replay-and-durability.md)、[编排代码约束](https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-code-constraints)）。因此：**转移只能由宿主规则对已记录事实求值，LLM 永不得直接写转移**；模型只能产出制品或声明，由宿主规则消费。

**让 LLM 猜任务：分两种，一种不允许。** 猜“计划本身”（下一步该做哪些任务）是自动重规划，它同时破坏两件东西：固定计划带来的可验收性，以及“宿主先证明缺口再派任务”的闭环；不出现在本设计中。可允许的只有猜“已声明条件的结果”（即上节的受门控推测），并且假设必须写进冻结信封，使 digest 绑定它。

**另一个 LLM 打回：只能做建议，不能做裁判。** 这不是我的个人偏好，而是已发表立场：自改进 agent 应把评判者从 oracle 降为 advisor，其结论只能是多个输入之一（[LLM-as-a-Judge Is Not an Oracle](https://arxiv.org/abs/2609.02246v1)）；实测中评判者的成对偏好平均有 13.6% 会翻转（[The Coin Flip Judge?](https://arxiv.org/html/2606.13685v1)）；而无参考评判者打的是**像不像对**，不是**对不对**，这正好留下“貌似有理但错误”的假阳性盆地供策略利用（[Self-Play Reward Hacking of Reference-Free LLM Judges](https://arxiv.org/html/2607.05904v1)）。本工作自己就量到过同一个现象：第 2 轮 B 的引用看起来像覆盖，实际语义成立性未被证明。

因此定下一条不对称规则：**建议者只能说“不”，只有宿主能说“是”。** 第二个 LLM 的打回可以作为廉价预过滤（早退、省一次宿主检查），但任何时候都不能把“打回”当作接受依据，也不能让它取代已存在的确定性检查——在已有确定性检查的任务上，用一次 20–50 s 的付费、概率性判定去替代一个本地、免费、几秒内确定结论的检查是降级。它只在**没有确定性检查**的断言上才值得付费（设计是否自洽、意图是否匹配、结论是否有依据），而且应优先要求**宿主能解析的引用**（第 3 轮已经建立的机制），而非再买一个模型的意见。

顺带一条外部印证：代码 RL 环境里，28.5% 的任务其测试套件弱到让 Docker 验证过的错误补丁能通过（[Auditing Reward Hackability](https://arxiv.org/pdf/2606.16062)）——这正是第 3 轮改用变异证明的理由。

### 输出格式服从与验证成本：实况结果的外部对照

**“分析型角色回散文、目标型角色回 JSON”不是本工作独有的现象。** 已发表结果给出了更准确的机制，而且指向的修法与我最初猜测的“改措辞”不同：

- 显式推理会**降低**指令服从度：在 IFEval 与 ComplexBench 上评估 15 个模型发现，CoT 式推理会显著损害对格式约束的服从（[When Thinking Fails](https://huggingface.co/papers/2505.11423)）。A 的推理发生在答案通道里，而不是在答案之外。
- 约束**叠加**会非线性劣化服从率：把 24 条可验证指令从 1 条堆到 20 条时，服从率下降曲线是非线性的（[Instruction Stacking Collapse](https://arxiv.org/html/2608.02639v1)），其建议是“提示编译”——收敛成更少、不重叠的约束。而我们前前后后把同一格式规则重述了四处（patchPrompt、系统提示、检查工具返回、回推提示），这正好是反方向。
- 格式代价取决于**剩余容量**：约束本身的开销与模型有多少余量相关，余量足够就能吸收（[Capacity, Not Format](https://arxiv.org/html/2606.09410)）。A 的任务更重（要先判断、要先看检查结果），余量更少。
- **改角色/人格措辞不是修法**：系统提示里的人格对客观任务表现没有改善，专家人格甚至会损害准确率（[Personas in System Prompts](https://doi.org/10.18653/v1/2024.findings-emnlp.888)、[Expert Personas Damage Accuracy](https://doi.org/10.48550/arxiv.2603.18507)）。

**可用的架构级修法：把交产物变成带约束采样的工具调用。** 产业口径的结论很直接：不要把“请返回 JSON”写在提示里，而是用提供方的结构化输出，在解码层把不符合模式的文本变成不可达（[结构化输出与约束解码](https://sesen.ai/blog/structured-output-llm-constrained-decoding)）。本仓库用的 SDK 已经支持这一点：`Tool.constrainedSampling` 接受 `{type:"json_schema",strict:"prefer"|"require"}`，且 `defineTool` 会透传。因此正确形态是：新增一个提交产物的工具，其参数模式就是产物形状，并请求约束采样；模型仍然可以推理，但答案必须在工具调用里。

同时保留宿主校验：约束解码几乎消除语法错误，但结构性与语义错误依然存在（[Empirical Study for Structured Output Control](https://arxiv.org/html/2606.09395v1)）。所以它只能消灭“解析失败”这一类，不能取消验证。

**验证成本主导也是已发表结论，不只是我们的账单。** 本轮的账是：宿主本地检查 21.9 s，模型 11.7 万 token，而被掩盖的外部等待只有 1.6 s。文献里对应的是：

- “生成复杂候选不再困难，可靠地验证它们才是更难的问题”，且每个验证器都只是人类意图的代理（[The Verification Horizon](https://doi.org/10.48550/arxiv.2606.26300)）。
- 验证成本随输出复杂度恶化，生成是多项式而识别“貌似有理但错误”接近 NP 难（[Verification Scarcity](https://www.jimmont.com/ai-model-agentic-verification)）。
- 校准审计存在“验证税”：模型越强，验证其校准在统计上越难（[The Verification Tax](https://doi.org/10.48550/arxiv.2604.12951)）。
- 交付面的收益会在“写得出代码”与“发得出可靠软件”之间急剧衰减，审查、集成与测试成为瓶颈（[Beyond Code Generation](https://arxiv.org/abs/2609.04681)）。

对本工作的含义：验证开销不是调度器的副产品，而是这条路线的主要账项；因此“用推测加载等待”的价值上限，必须对着验证开销而不是对着等待时长来评估。另外，多轮工具使用的成本主要由每轮重送的上下文决定（输入 token 常占轨迹的绝大多数），所以 B 的 7.8 万 token 更应该去看快照被重送的次数，而不是看生成量。

### 交产物用工具、不用提示

格式约束不在提示里堆，而是做成一次工具调用：`submit_artifact` 的参数模式就是产物契约，并请求提供方约束采样（`constrainedSampling: {type:"json_schema",strict:"prefer"}`）。模型仍可推理，但答案必须在工具参数里；工具体在记录产物后立即结束本次尝试，以免后续文字与提交矛盾。

宿主校验不变。约束解码只能消除语法失败，结构性与语义错误依然存在，所以共享契约仍是最终判据。提示里只保留**一处**约束陈述（指向该工具），不再重述形状；实测中把同一条规则重述四处正是“约束叠加”导致服从率下降的模式。

工具化本身还不够，round 6 暴露了它的下一层：**不要提供宿主一定会拒收的选项**。两个真实失败都属于这一类：

- 信封只查字段**存在**，所以 `kind:"no-change"` 加一段散文结论被原样送到宿主，得到一个结构错误；
- 工具模式对所有任务开放全部三种结论，于是必须提交文件的任务答了 `promote-candidate`（那是组合任务才有的合法答案）。

修法是让 schema 从**冻结的接受规则**派生，而不是从一个全局枚举派生：任务的 `admittedConclusions` 连同可见集一起进入摘要，工具只在运行时开放该任务真正可被接受的通道；判别符是工具自身的形状（有 `files` 即补丁），不是模型填的字符串。

### 可见集与票据

**按任务裁剪可见快照**。整份基线原本每轮重发（round 5 基线 59,874 字节，三万多 token 每轮）。可见集由宿主声明并进入摘要（`visible`），可写路径绝不可隐藏（否则是自相矛盾的规则），而**冻结但未显示**的文件名写进提示，因此缩小视野不是隐藏规则；宿主仍按完整基线验证。

**票据携带冻结的 work 本身**。票据原本手写列举字段，于是每加一个字段就会静默漏掉一个，驱动器与协调者的摘要不一致 —— 连续两次都是这么坏的。现在票据直接展开冻结的 work，驱动器从票据重建，摘要不一致时错误里列出**差异字段**。两个摘要不一致其实都由摘要本身抓住（默认可见集按输入键序排列、默认结论集只排序显式分支），这正说明摘要绑定在做它该做的事。

成本测量必须记录提供方的缓存账目（`cacheRead`/`cacheWrite`）。实测该提供方确实缓存前缀（B 177k 里有 132k 是 `cacheRead`，A、C 约一半），忽略缓存会系统性低估 worker 的花费。

## 证据与停止条件

每轮记录：基线/计划/验证器摘要、两个 worker 的身份、尝试和输入版本、真实等待的开始/结束、任务选择与验收时间、拒绝原因、产物摘要、检查结果、tokens、人工介入及最终是否提升。不要存凭据；日志按任务预算截断并保留可追踪引用。

区分四种结论：顺序回退、合法乱序但无有用变更、自举变更完成、对照中观察到收益。后台操作与 B 的时间重叠才是等待被利用的证据；B→A→C 的输出列表本身不足以证明这一点。

对照使用相同输入、模型设置、检查工作与验收标准；记录缓存和外部负载差异，重复运行并保留失败样本。没有稳定收益不等于调度错误，但不能宣称提速。

发现越权、错误解锁、不能定位的输入漂移或候选能改写验收时停止自举，退回普通开发修复最小阻塞并重新验证。人工兜底必须显式记入证据；不扩大权限绕过问题。

本计划不要求 AG 迁移、同会话暂停恢复、多执行者并行、推测执行、自动重规划或不可逆外部操作。今后的扩展由具体任务证明需要，再另行评审。
