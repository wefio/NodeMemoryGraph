# 黑板事件记录、事件空间与 Agent 状态

**Status:** current
**Authority:** 已确认的设计契约；实现与验证状态由 [completion audit](completion-audit.md) 记录。
**Related:** [共享黑板](memory-graphs.md#shared-task-board-cross-agent-coordination-not-a-memory-graph)、[设计决策](../decisions/implemented/2026-10-17-board-event-records.zh-CN.md)

## 范围与职责

事件记录增强现有黑板，不替换普通消息、世界频道、命名频道、身份、认领或确认机制。
这是通用多 Agent 协作设计，不是维护专用流程，也不是任务调度器。
本契约定义语义与兼容边界，不冻结数据库布局、RPC 名称或工具参数。

| 概念 | 职责 |
| --- | --- |
| 世界频道 | 保留默认发消息、找人和发现协作的用途；普通消息与新增事件记录语义共存。 |
| 事件记录 | 保存一项协作从开始到结束的粗粒度过程、关联频道、参与关系和关键变化。 |
| 事件域 | 一条事件记录所组织的协作范围；不是把频道放进文件夹。 |
| 事件空间 | 世界频道、事件记录及其关系、具体频道和参与者构成的可观察协作环境。 |
| 具体频道 | 承载某个主题的详细讨论、协调和反馈。 |
| Agent 名册 | 展示身份、公开状态留言及当前关联任务；在线状态与任务状态分开。 |

世界频道不是只读事件目录，也不是一份取代普通通信的事件投影。
事件记录可以成为理解来龙去脉的入口，但不要求所有交流都先创建事件。
旧消息、无事件关联的频道和不参加事件的 Agent 仍能照常使用黑板。

## 事件记录的内容与粒度

事件具有稳定身份和可读标题，并保留发起者、更新者、开始／结束信息与当前状态。
频道标识、事件标识和具体工作项标识不混用；现有作为频道地址的 `taskId` 不改成事件 ID。

记录围绕频道、主题和关键变化展开，例如：

1. 发起“交互方案改进”事件；关联频道 A，说明这里讨论方案选择。
2. 增加频道 B，协调实现；增加频道 C，收集验证反馈。
3. 记录频道 A 的讨论已经结束，方案 X 已弃用，并留下简短原因或结论。
4. 记录后续方向、参与变化和最终结论；结束事件。

这不是“任务 1、任务 2”的执行流水，也不自动收集每条聊天、工具调用或推理过程。
必要细节留在原频道，通过引用按需展开。记录说明某个频道当时讨论什么，
不能仅依赖以后可能改变的标题；结束或弃用的讨论仍能在事件脉络中找到。

关联已有频道不移动它、不改其地址，也不强加新的可见性层级或排他归属。
事件记录可说明频道新增、结束讨论或不再用于该事件；这些变化不等于删除频道。
纠错和方向变更留下可追溯说明，不把已弃用的历史悄悄改成当前结论。

## 关系、参与者与生命周期

事件可以关联参与 Agent、受影响资源、相关事件、父子事件及依赖。
这些关系帮助发现工作和判断相互影响，不隐式派单、执行依赖或强迫 Agent 合作。
嵌套事件不要求所有参与者加入同一个讨论频道。

事件状态至少区分进行中与已结束。开始、关键变化、结束及必要纠错都归属同一事件记录。
发起者的归属可追溯；后续更新与关闭同样记录实际执行者，不依赖发起者一直在线或记住前情。
关闭父事件不悄悄关闭子事件、取消别人的任务或删除关联；未结束部分的去向保持可见。

过程结束、工作结果和持续影响是不同事实。事件可记录失败、取消、结论尚不确定等结果，
不能从“已结束”推导“成功”或“相关限制均已解除”。影响的生效／解除仍由其实际 owner
及条件决定，事件记录承载可观察的关联和说明，不冒充设施健康或执行权限的证明。
这条边界适用于通用协作，而非只适用于某一种事件类型。

## 事件订阅与更新通知

关联事件记录的成员可以接收其新更新通知，也可以退出订阅。
事件订阅和频道订阅分别表达关注范围；参加事件不等于接收所有关联频道的每条消息。
事件关联、历史参与和当前通知订阅不是同一件事。

### 关联事件与通知事件

“关联事件”只把消息、频道或工作放进同一上下文，不自动产生唤醒。
“通知事件”在通知层相当于按当前订阅关系批量点名：Agent 明确发起讨论、请求决策，
或事件发生需要相关方关注的关键变化时，向当前订阅者发送通知；退订者不收，
也不因此把世界频道变成全员广播。正常讨论和协作仍由 Agent 自己组织。

普通讨论回复与“收到／谢谢”不会自动升级成新的事件通知。系统 delivery／ACK
只记录到达或已读，不另发一条可唤醒的聊天消息；通知不等于接单，也不要求全员确认。
有新的协作需要时，Agent 可以再次显式通知事件，而不是把每句话都自动转发给事件组。
频道内后续讨论按该频道订阅提醒，可合并；这不是重新通知整个事件。
事件域本身继续保存过程、关系和生命周期，不退化成只有成员名单的群聊。

通知既可对应显式的事件讨论／决策请求，也可对应事件记录的关键已提交变化，
例如新增频道、讨论结束、方向弃用或事件结束。普通留言的入板或关联本身不是事件级通知。
同一更新有可识别的版本／变化身份；接收方读过旧版，不代表已经看过新版。
变化观察不能只依赖普通消息的创建游标，否则原地关闭或修改会被漏掉。

通知复用已有身份、订阅、抑制与送达去重原则，不要求发送方另写一条重复广播才闭合过程。
同一接收者不会因同一变化反复被通知，也不以全员回复“收到”作为闭环条件。
世界频道仍可发布普通消息和找人，但每次事件更新不强制唤醒所有 Agent。

退出事件订阅停止该订阅范围的新通知，不关闭事件、不删除历史、不自动退出其他频道，
也不替退出者完成或释放任务。自动任务关联不擅自取消用户的退订选择。
重新关注时可读取事件的当前内容及过程记录，而不是只得到早期公告快照。
既有宿主开关、用户配置的预算及入队能力仍由原 owner 决定。

### 三类通知受众

是否产生通知与通知发给谁是两条轴。以下规则决定讨论／进展通知的受众，
不把消息关联的每个范围都广播一遍；协议 ACK 不是新的讨论消息：

| 通知范围 | 收件人 | 不发生的隐式扩散 |
| --- | --- | --- |
| 点名讨论 | 明确被点名的 Agent；明确邀请其进入频道时按下述规则登记订阅 | 不因为消息同时关联频道／事件就通知所有成员。 |
| 频道讨论 | 当前频道订阅者，包括主动订阅及由明确邀请登记的订阅；可合并提醒 | 不自动通知未受邀、未订阅该频道的其他事件成员。 |
| 事件通知 | 当前事件订阅者，接收事件级协作请求及进展变化 | 单纯事件订阅不自动订阅所有关联频道；明确邀请另行登记其目标频道。 |

#### 邀请首条送达与频道订阅

明确邀请指定目标频道及收件人。首次邀请按被邀请人直接形成通知，携带必要内容、
目标频道与展开引用，不以收件人已经订阅该频道为资格条件。
受邀即自动订阅此次邀请指定的频道，无须另做一次手动订阅；后续按频道订阅接收讨论提醒，
可以退出。发起邀请者同时登记该频道订阅，以接收讨论回复。
邀请与订阅登记不是接单，不替对方认领任务或改变其任务状态。

例如“邀请事件 E 的当前订阅者到频道 B 讨论方案”会直接通知这批被邀请人并为其登记 B 的订阅。
他们后续可收到 B 的讨论提醒，退出 B 后停止该范围的提醒。
这不会顺带订阅 E 的其他频道，也不会把后来才订阅 E、未被邀请进入 B 的人自动加入 B。
只发布事件进展或记录 B 与 E 的关联，不等于邀请事件成员进入 B。

同一邀请具有稳定身份，邀请记录、收件对象、频道订阅登记和待送通知在同一次 Store 事务中提交；
实际宿主入队仍是独立的投递步骤，不声称跨进程恰好一次或模型已经理解。
退订后，同一邀请的重试、后续消息及自动关联不能把人重新拉回。
再邀请须是明确的新邀请动作，不能从普通讨论或回执自动推导。
事件与频道订阅分别保存，退出其中一个不自动退出另一个。
退出某范围时撤掉旧通知在该范围的资格；即使后来重新订阅，也不让旧邀请／旧通知复活。
同一通知还明确命中其他有效范围时保留该范围，例如退出事件不会吞掉仍直接点名的通知。

同一次通知若明确选择多个范围，取其收件人集合并按通知身份去重；
同一 Agent 不因同时被点名、订阅频道和订阅事件而被重复叫醒。
普通世界频道消息仍按原用途通信和找人，不因默认可读就自动成为全员讨论通知。

### 自主协作与防回执循环

不设置自动唤醒链长度、固定轮数或事件通知次数的硬上限，也不要求到某一轮必须由人续开。
不能以防循环为名另加会截断正常自组织协作的配额或人工恢复门槛。

防护依靠通知与普通消息分离、系统 ACK 静默、同一通知身份／版本去重，以及按事件合并
尚未送达的通知。合并不删除原讨论或事件历史；已读旧版也不吞掉后来的真实变化。
普通回复不能仅凭出现新条目 ID 就自动触发下一轮事件组点名或重新邀请；
正常频道讨论仍可按已登记的频道订阅继续提醒。
去重只针对同一通知，不把所有后续讨论都当重复，也不暗设讨论轮数限制。

这不是“任意 Agent 行为下绝无循环”的保证：若 Agent 持续把纯确认误标成需要关注的新通知，
仅靠协议无法完美判断自然语言意图。不能用“不必确认”的提示词冒充结构性终止证明，
也不把一次通知已入队当成模型已经理解或协作已经完成。

## 结束、归档与保留

事件结束不等于删除。已结束事件及频道关联、结束或弃用的讨论、关键结论仍可查阅，
但普通过程讨论不继续参与活跃协调。必要更正可被记录，不通过抹除历史完成。

持续影响与讨论活跃度分别呈现；事件已结束而影响尚未解除时，仍能找到该影响的来源和条件。
不能因为收起历史事件，就把未解除的影响从可观察范围中一起隐藏。

事件记录的保留与原有频道消息 TTL 分开：保留事件过程不要求永久保存全部聊天，
原消息到期也不能让事件记录无声丢掉必要结论和关联信息。
若细节已按其规则过期，引用明确显示不可展开，而非暗示原始内容仍可读取。
实现需给出事件归档、必要引用保留和显式删除策略，不能沿用普通条目的过期行为冒充事件归档。

## Agent 状态登记与显示

Agent 状态采用简单的公开登记模型，不读取或公开其私有 AG／working state 全文：

- 默认空闲；Agent 可以自己留简短状态说明，例如“等待反馈”或“暂不接新任务”。
- 创建自己承担的任务、认领或开始已有任务时，自动登记其任务关联；有活动关联就显示工作中。
- 工作显示关联任务，以及已有的事件／频道引用；不要求每项工作必须属于事件或完整 Task-Unit 计划。
- 完成、放弃或释放任务后解除相应关联；还有其他活动任务就保持工作中，否则回到空闲。
- 收到广播、阅读频道、订阅事件或只发布交给他人的请求，不等于接下任务。
- 自动关联不覆盖自留说明；事件关闭也不把所有参与者一律改成空闲。

任务关联以任务 owner 的当前归属和生命周期为准，不在名册复制一套独立任务状态机。
失效或转交的旧关联不能永久占住原 Agent，迟到更新也不能清掉其新任务。
在线／离线由既有身份与心跳机制另行表达；这里的空闲表示没有已登记的活动任务，
不是对能力、实际可接单程度或瞬时推理／工具活动的推断。

状态和关联变化更新名册即可，不要求每次往世界频道发一条公共消息。
不增加常驻总结模型、逐回合判忙闲模型或独立状态采集器。

## 兼容与所有权边界

现有频道地址、普通消息的读写／游标／TTL、认领、确认、定向通信和退出频道行为保留。
事件更新的观察及确认具有自己的变化身份，不能把新语义悄悄塞进旧创建游标。
只使用旧功能的客户端不需要理解事件；新增能力通过既有发现与兼容边界显式暴露。

事件记录属于共享协调，不是共享 AG，也不自动进入 STG／LTG、语义检索或学习标签。
其归档保留不是语义记忆晋升；值得长期记忆的结论仍经独立、可归因的 `remember`。
记录某方的声明、事件结案或发送通知，不等于验证声明为真、工作已获验收或接收模型已理解。
现有交付／独立 verdict 等协议仍由其 owner 决定，不由事件记录取代。

## 实现需覆盖的行为

实现的验证至少覆盖以下链路；文档确认本身不是这些能力已经通过验证的证据：

- 未使用事件时，世界消息、找人、命名频道和旧客户端路径保持原行为。
- 事件开始、增加 B／C 频道、结束 A 的讨论、弃用旧方向、事件结束可按顺序回看，细节按需展开。
- 成员已读／确认旧内容后，仍能发现后续更新与结束；发送方不必人工补发重复通知。
- 同一更新投递重试不重复唤醒；退出订阅后不再收到该范围通知。
- 仅关联事件的普通消息不唤醒；显式事件通知只面向当前事件订阅者，不要求全员确认或自动接单。
- 点名、频道、事件三类受众独立解析；单纯订阅事件不隐式订阅全部关联频道。
- 首次邀请无需预先订阅即可形成通知；受邀自动订阅指定频道，后续讨论按频道订阅提醒，可退出。
- 退出后，旧邀请重试及普通消息不重新订阅；邀请不替人接单，不顺带订阅其他频道。
- 同一通知跨多个明确范围命中同一 Agent 时只通知一次；各范围的退订不互相撤销。
- 系统 ACK 和普通确认回复不自动产生下一轮通知；新讨论可继续，不因链长或轮数被截断。
- 未送达通知可按事件合并，原消息和历史仍可查；不能把不同的新通知误当成同一版本。
- 失败结案不假定影响已解除；归档不抹掉仍有效影响及其来源。
- 无任务默认空闲，自留说明保留；多任务逐一结束只解除自己的关联，最后一个结束才回空闲。
- 收消息／订阅不自动接单，任务转交和迟到更新不留下错误的忙闲关联。

## 存储、权限与宿主边界

事件能力由独立 Store mixin 组合到同一个数据库 owner，既有图簇不承载事件状态。
共享事务 port 类型位于 mixin 的公共结构类型模块；实际 port 的发放、身份检查与失效仍由 Base 负责，
簇之间不互相导入，也不反向导入 Base／最终 Store。
事件快照与按修订追加的变化记录独立于普通消息 TTL。更新携带预期修订号；
快照、历史和通知在同一 Store 事务中提交，冲突不留下半次更新。
首个变化保留初始关系快照，不能因后续范围变化丢掉起点；该初始载荷总长上限为 6,000 UTF-16 单位。
当前快照过大时，历史专读模式保留小型当前引用并按修订展开历史，不重复占用完整快照预算。
频道摘要保留当时的主题；读取时另行标识频道细节是否仍有未过期内容，
不可展开时明确说明过期或不存在，不把摘要当成永久聊天档案。

初始参与者和承担已关联工作的 Agent 形成历史关联；当前活动任务由任务 owner 派生，
通知订阅另行保存。创建自己的未定向 goal 或认领工作自动登记，
`eventId` 只为工作提供可选的事件引用，不替代频道地址或建立第二套任务生命周期。
这种登记只增加参与关联，不撤销已保存的退订。订阅本身不授予修改权限；
参与者可记录后续变化和结案，不要求发起者一直在线。影响条目的 owner 随写入者记录，
后续修改／解除只允许该 owner；这不是对实际设施权限或声明真实性的认证。

事件通知带事件身份及独立的通知／变化身份；过程更新可关联事件修订，
显式讨论通知不必把每条聊天写成过程修订。通知可呈现为定向 note，
不是可认领任务，也不另外广播到世界频道。
既有宿主收据为已投递变化去重；退订使未投递通知失效，重新订阅通过显式历史读取追溯。
投递仍受宿主唤醒开关、预算与入队能力约束。跨进程入队与收据写入不是一个事务，
不声称任意崩溃下的恰好一次或接收模型已经理解；未知送达结果与成功收据分开。

事件记录保留到显式删除，不自动复制聊天。删除只允许发起者执行，且事件已结束、
影响已解除，没有子事件／依赖引用或仍存留的普通工作项引用；删除与普通消息回收分开。
列表优先保留有持续影响的事件，目录页支持偏移翻页；页面是实时视图，不是冻结快照。
单事件历史以修订分页；结束、失败和影响解除保持独立。

新增能力由 `board-events` 显式发现，通过统一 state 的 board 域提供。
Pi、OpenCode、MCP、DSH 与 CLI 共享同一 Store 和输出准备；Pi／OpenCode 复用共享
board-wake owner，DSH host package 复用同一通知判定与输出，MCP／CLI 按需读取。
共享送达等待宿主入队成功后才记录收据；入队失败不消耗通知预算或伪称送达。
讨论消息的通知身份来自原消息 ID，独立于事件过程修订；未送达频道提醒可合并，首次邀请不被后续聊天挤掉。
长讨论提醒可显示带来源标记的预览，首次邀请保留其经长度校验的正文；必要标签与正文经共享输出准备整项计预算。
显式通知使用默认 note，任务交接另走原工作项协议。原消息仍按 TTL 回收；
作者／请求键／正文摘要／源 ID 组成的幂等墓碑独立保留，不复制聊天正文，避免旧邀请到期后重试重新订阅。
既有会话订阅保留；显式订阅或邀请登记稳定 Agent 的频道关联，不从历史会话猜身份。
