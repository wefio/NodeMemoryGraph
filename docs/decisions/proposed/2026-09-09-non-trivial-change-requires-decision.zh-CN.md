# 非平凡改动必须携带决策记录

[English](2026-09-09-non-trivial-change-requires-decision.md)

**Status:** proposed
**Date:** 2026-09-09

## 问题

决策记录已经存在，但没有任何规则说明**什么时候必须写**。唯一的常设触发条件是
元规则：改动常设规则、Skill 约定或决策约定时需要一条决策。其余全靠自觉——删除
一个声明了却无人读取的字段、迁移一个 CI job、重定义一个检查种类，都可以不留任何
「放弃了什么」的记录就落地。

仓库就是这样长出与代码不再匹配的设计散文的。2026-09-08 那轮需要三条决策，而
没有任何规则要求它们：可追溯性矩阵、术语索引、chaos job 迁移。它们各自改变了
一项常设约定，所以被元规则**按类别**接住了——靠运气，而不是靠体量。

DeepSeek Harness 把规则写得很直接：每个非平凡改动必须在**同一个 PR** 里新增或
更新至少一条决策笔记，只有纯机械或局部编辑豁免。NMG 有记录格式和生命周期门禁，
却没有这项义务。

## 提案

每个非平凡改动在同一个 PR 里新增或更新至少一条决策记录。更新已经拥有该决策的
记录即满足规则；同一次细化不另建重复记录。

当改动改变了行为、跨文件或跨包的契约、包或模块结构、流程或工具链、测试策略，
或者任何落盘/线上/配置格式时，它就是非平凡的。纯机械或局部编辑豁免：格式化、
注释措辞、错别字修正，以及无行为后果的依赖升级。

规则住在 `skills/repo-development/SKILL.md`，紧挨交付流程；PR 模板把它作为一条
核对项。

这条规则**不设机械门禁**。「这个改动需不需要一条决策？」是关于改动含义的判断，
任何路径清单都回答不了：`src/` 下一行改动既可能是契约变更，也可能是注释修正。
DeepSeek Harness 是现有最强的机械化案例，它同样把这一条留给审阅，只用门禁管
笔记的格式与分类。

## 考虑过的替代方案

**按改动路径设门禁。** 可以规定：`src/**`、`.rcp/contracts/**`、`agent-context.yaml`
或 `skills/**` 发生变化却没有 `docs/decisions/**` 变化时失败。它会在每次重构和
注释修正上触发，而它所需的逃生口——`Decision-exempt:` 尾注——会被反射式地写上，
把规范变成橡皮图章。

**只在常设规则变更时要求决策。** 这就是当前的元规则，也是 2026-09-08 那三条决策
存在的原因。它漏掉了「改变契约但不碰规则文档」的行为性改动，而那恰恰是未来读者
最需要重建的部分。

**每个 PR 都要求一条决策。** 统一且数文件即可检查，但它会为错别字修正产出记录，
训练审阅者忽略它们。

## 验收标准

- `skills/repo-development/SKILL.md` 定义「非平凡」、列出豁免类别，并要求记录与
  改动在同一个 PR。
- `.github/pull_request_template.md` 把该要求作为核对项。
- 下一个改变行为、契约、结构、工具链、测试策略或格式的改动，引用它所新增或更新
  的决策记录。
- 不新增门禁，并在决策中写明原因：该判断不可机械化，设门禁只会测到措辞而不是
  工作本身。

## 风险

**记录过度。** 如果审阅者接受为每个琐碎改动都写记录，决策树会被噪声填满。豁免
清单是配重，而对记录本身的审阅就是检查。

**习惯性漏记。** 没有门禁，忘记写的 Agent 不产生任何信号。缓解办法是 PR 核对项
出现在审阅者本就会读的同一处，而且该遗漏本身也是一条可审阅的声明——见
[显式声明「没验证什么」](2026-09-09-declare-what-was-not-verified.zh-CN.md)。
