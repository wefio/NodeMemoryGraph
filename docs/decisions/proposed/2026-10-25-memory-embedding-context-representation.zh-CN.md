# 给记忆检索表示补上日期与上一轮对话

[English](2026-10-25-memory-embedding-context-representation.md) · [术语](2026-10-25-memory-embedding-context-representation.terms.yaml)

**Status:** proposed
**Approved:** explicit

## 问题

记忆的检索文本是 `${canonicalName}: ${statement}`。记录里存着 `event_time`（在我们测过的 LoCoMo 库里 100% 填充），它来自的那一轮话就躺在 `history_records` 里、紧挨着它的前一轮——两者都不在嵌入文本里。于是"去年开始的，后来每周都去"这样一条记录，被编码时既没有日期、也没有归属、也没有它实际回答的那个问句。

在 LoCoMo 全 1,977 道可答题上实测（纯 BGE 余弦、页 20 条、无重排、不调参）：

| 聚合方式                |  原文 | 日期＋上一轮 |   变化 |
| ----------------------- | ----: | -----------: | -----: |
| 标签级微平均 recall@20  | 58.7% |    **65.8%** | +7.1pp |
| 按题数加权的类别 recall | 63.5% |    **71.8%** | +8.3pp |
| 完整证据覆盖率          | 60.0% |    **68.1%** | +8.1pp |

两个成分不可互换：日期贡献多跳题的大部分增益，上一轮贡献单跳 +5.3pp、对抗 +21.3pp。时间类上整套损失 1.4pp，这是下一件要修的事，但不是扣住其他四类的理由。

## 提案

`memoryEmbeddingText` 接受可选的 `eventTime` 与 `previousTurn` 上下文，向量身份增加表示版本。

- 文本为 `[YYYY-MM-DD ]<节点>: <statement>[\nprevious: <轮次>]`。只取 `event_time` 的日历日；解析不出的值不贡献任何内容，而不是塞一段随意字符串。上一轮做空白折叠并截断到 240 字符。
- 不提供上下文时输出与旧文本**逐字节相同**，因此无上下文的调用方不会悄悄改变自己的向量。
- 身份变为 `memoryEmbeddingModelId(embedderModel)` = `<embedder>@rep2-date-prev`。这不是装饰：`memory_embeddings` 以 `(memory_id, model)` 为键，索引器只重编码"该 model id 缺失"的行，检索侧又用 `memory_embeddings ve ON ve.model = ?` 连接。在旧 id 下改文本，会留下读起来完全正常的旧向量。

### 接线需要什么

1. **定位上一轮。** 记录的来源轮可通过 `memory_evidence_links` → `history_records` 找到；上一轮是同 `session_id` 下 `source_message_id` 小于当前值的最大行。不需要新字段。
2. **把 `event_time` 串进三个写入点与一个读取点**——`embeddingDocuments`、`refreshEmbeddings`、`rebuildVectorIndex`、`memoryText`。
3. **身份必须一次换完，不能分两步。** 写侧与检索连接必须同时切换：只做一半，要么旧向量仍被当成有效使用，要么所有向量从检索里消失。
4. **重编码。** 身份切换后由 `rebuildVectorIndex` 生成新行；旧 id 下的行留在原处并被忽略。一个库不能同时在新旧两个 id 下可读。
5. **真实路径验收。** 通过产品路径重新 ingest LoCoMo，确认页面仍返回 20 条原始记录且增益保持，参照已测的 65.8% 微平均 / 68.1% 全覆。

## 验收标准

- 通过产品路径重新 ingest 的库，每次查询仍返回 20 条原始记录（绝不是上下文窗口），并且在本记录所依据的 LoCoMo 协议上，标签级微平均 recall@20 不低于实测的 **65.8%**、完整证据覆盖率不低于 **68.1%**。
- 旧表示 id 下写入的向量，绝不与新文本产生的向量混用；同一库在新旧两个 id 下同时可读属于缺陷，不是回退方案。
- 既无 `event_time`、也定位不到前一轮的记录，保持与今天完全相同的文本（单测已钉死）。

## 风险

- **迁移只做一半。** 只改写入侧不改检索连接（或反之）会要么继续用旧向量，要么把向量通道清空。身份切换必须作为一次改动落地。
- **时间类退化。** 整套表示在时间类上损失 1.4pp；在下面的细化之前采用它，是用那一处小损失换别处的大收益。这是有意的取舍，且可通过表示版本回退。
- **上下文可得性。** 上一轮依赖 `history_records` 仍保留前一条；历史被裁剪处文本退化为"只有日期"，是更小的增益而不是错误。
- **重编码成本。** 全量重编码与记录数成线性，每个表示版本付一次，不是每次查询。

## 考虑过的替代方案

- 把上下文存到记录上（为上一轮加列）：重复了 `history_records` 里已有的对话，且历史被裁剪时副本会过期。
- 查询时现算文本：被比较的段落会是连接的产物而不是已存表示，而且每次查询都要付这个代价。
- 保持一个身份、原地重写向量：会让库在一段时间里处于"向量与文本不一致"的状态，且无法分辨哪些行是当前的。

## 后果

表示从依赖一个字段变成依赖三个字段，因此记录的日期或前一轮发生变化时它的向量需要重算——维护流程本来就按 memory id 重编码。

时间类问题在该表示下目前损失 1.4pp。已记录的下一步是**更窄的上下文**（"读懂这一条记录所必需的实体、指代与事件时间"），而不是更长的窗口；已测的整套是细化必须超过的基线。

## 实现状态与首轮复测（2026-10-25）

已按方案接线：`memoryEmbeddingText` 接收 `eventTime` 与 `previousTurn`；上一轮由一条相关子查询从 `history_records` 解析（共享为 `MEMORY_PREVIOUS_TURN_SQL`）；身份在三个写入点与唯一读取路径（`search()` → `searchWithVector`）上统一为 `memoryEmbeddingModelId(embedderModel)`。两条测试钉住它：重编码产出带日期、带前一轮的文本且落在带版本号的 id 下；之后检索仍能命中该记忆——这次改动可能引入的失败模式是"向量通道静默清空"，所以这一半被显式测了。

用**出厂构造器 + 产品默认嵌入器**（确定性 hashing，256 维）复测，1,978 题、页 20 条、全语料：

| 臂                 | 标签级微平均 recall@20 | 完整覆盖 |
| ------------------ | ---------------------: | -------: |
| 原始文本           |                   37.0 |     40.3 |
| 加日期             |                   37.0 |     39.8 |
| **加日期＋上一轮** |               **37.9** | **42.4** |

即 **+0.9pp recall、+2.1pp 全覆**，不是实验记录里的 +7.1/+8.1。差别来自嵌入器而不是接线：记录里的增益是用 `bge-small-en-v1.5` 测的，而 hashing 嵌入器对新增词基本不敏感——它的特征是哈希化的词片段。

**对验收标准的影响。** 65.8%/68.1% 这条线只能在 BGE 档案的库上达到；在产品默认档案下，这次改动大约只值四分之一。因此关闭本记录所需的复测必须用基准框架跑 BGE 档案的库（本地嵌入服务或部署档案），不能用默认嵌入器。在那之前本记录保持 proposed，且不得把这个改动引用为"七点增益"。

## BGE 档案的真实路径复测（2026-10-25）

这次走产品路径而不是旁路：每个 LoCoMo 库拷贝一份、清掉同 id 的旧向量、由 `syncRecordEmbeddings` 写入 `memoryEmbeddingText` 现在产出的文本，再从产品存储的向量上排出 20 条页。两臂用同一个客户端（`bge-small-en-v1.5`、`bge-en` 档案）、同一批 1,978 题。

| 臂（同路径、同文本形状）       | 标签微平均 recall@20 |   完整覆盖 |
| ------------------------------ | -------------------: | ---------: |
| 旧文本 `${node}: ${statement}` |                 58.1 |       59.8 |
| **日期＋上一轮**               |             **60.8** |   **64.3** |
| 变化                           |           **+2.7pp** | **+4.5pp** |

两件事要分开看：

1. **方向在产品路径上成立，幅度不成立。** 离线同一改动值 +7.1pp / +8.1pp；这里是 +2.7pp / +4.5pp。
2. **差额来自节点名。** 产品文本是 `${canonicalName}: ${statement}`，而这些库里的 canonical name 是 `Conversation batch-<hash>`——每一臂都带同一段噪声前缀。它对较难的类别伤害最大：多跳在真实路径上是 40.7%，离线是 49.0%。

因此上文设定的验收线（65.8% / 68.1%）在当前文本形状下**未达到**：60.8% / 64.3%。记录保持 proposed。

下一个杠杆现在很具体也很便宜：嵌入文本里的节点名对检索是噪声（它是对话批次标识，不是主题），把它从被嵌入的字符串里去掉是一行改动，上面两臂都会受益。在继续做表示工作之前应当先测它，因为它解释了 60.8 到 65.8 之间的大部分距离。

## 去掉节点名（2026-10-25，表示版本 `rep3-no-node`）

嵌入文本不再包含节点名。节点名仍留在词法索引（`ftsIndexedText`）里，精确名称匹配照旧可用；它只是不再稀释稠密表示。同一产品路径复测：

| 臂                             | 标签微平均 recall@20 | 完整覆盖 |
| ------------------------------ | -------------------: | -------: |
| 旧文本 `${node}: ${statement}` |                 58.1 |     59.8 |
| 日期＋上一轮，带节点名         |                 60.8 |     64.3 |
| **日期＋上一轮，去节点名**     |             **62.9** | **65.5** |

去节点名在上下文之上再值 **+2.1pp recall / +1.2pp 全覆**，相对旧文本合计 **+4.8pp / +5.7pp**。

本记录此前"节点名解释了 60.8 到 65.8 之间大部分距离"的估计**过于乐观**：它只找回约三分之一。验收线（65.8% / 68.1%）在真实路径上**仍未达到**——62.9% / 65.5%——记录保持 proposed。

余下约 3pp 差距有三个已定位的候选，都很便宜：

1. **日期形状。** 离线表现最好的变体带的是数据集里的完整会话时间戳（`2:32 pm on 29 January, 2023`，外加会话序号）；产品只写 `YYYY-MM-DD`。其中会话序号离线值 1.1pp，产品没有对应物，所以这部分差距属于预期不可回收。
2. **上一轮形状。** 离线变体给轮次加了 `previous turn — Speaker:` 前缀且不截断；产品用 `previous: …` 并在 240 字符处截断。
3. **排序路径。** 离线是对全部记录算余弦；此处的产品路径同样是对存储向量算余弦，所以这一项不是差异——列出来是为了记录它被核过。
