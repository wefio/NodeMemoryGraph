# 用实测收益为推测设门，并且不靠推测掩盖等待

[English](2026-09-11-ooo-speculation.md)

**Status:** proposed
**Relates to:** [用真实开发引导受限乱序执行](2026-09-09-ooo-bootstrap.md)

## Problem

引导设计直接禁止推测与抢占，理由是只有真实外部等待才允许越过队首。这条规则安全但过粗：它同时禁掉了唯一一类"猜错不亏"的推测，也没给出区分"赚钱的推测"与"亏钱的推测"的方法。

CPU 的乱序执行让推测产生收益有一个具体原因：猜错浪费的是本来就要花掉或本来免费的资源，猜对能掩盖一次停顿。由此产生两个问题，它们在本系统里的答案不同：这里有没有"猜错免费"的落点？用猜测掩盖长等待到底是不是真机会？

## Proposal

采用免费那一类，拒绝靠猜测掩盖等待那一类，并保留让猜测显式且可逆的机制。

**采用：宿主侧不花 token 的推测。**预先建好下一步要用的候选目录、预先跑两分支都要跑的检查、预先算好变异矩阵、预先为依赖任务在两种假设下拼好冻结信封。它不提交任何东西、结果可丢弃，收益非负。

**采用：把假设绑定进信封。**每个被接纳的推测都在冻结指令里写出假设（`assumed outcome (unverified)`），使输入摘要绑定它；与假设矛盾的真实终态会使该产物失效，而不是被接受。这个机制另有独立必要：下游回推那条边需要它——依赖任务的拒绝会重签上游任务，并使绑定旧摘要的一切失效。

**拒绝：消耗 token 的事件结果推测。**它在本系统的前提不成立。以本仓库自己的协调收据为证（`.rcp/receipts/` 中 23 次带计时的运行），最大的正常外部等待就是整轮验证：中位数 80.7 秒，最小 15.9 秒，最大 134.5 秒。二十分钟等待是历史最大值（134.5 秒）的九倍，那更像是程序挂住了，而不是值得掩盖的工作量；本系统产生的等待都是普通量级，而普通等待应当用必修任务填满。在最大正常等待下盈亏平衡的命中率会是 0.25，但唯一高概率的命题是"冻结检查会通过"，它近乎确定——而近乎确定的前提意味着该依赖应当被**移除**，而不是被绕开。因此任何长得足以让猜测划算的等待，要么是异常，要么应该被**解耦**成异步任务、稍后收集结果，而不是用猜测掩盖。

**禁止**：值推测（猜另一个任务的产物内容——命中率远低于猜事件结果，误判会污染整条依赖链）、猜测"存在哪些任务"、抢占。

## Alternatives considered

- **维持全面禁令。**最安全，本提案对"等待"仍然维持它；它唯一放弃的是免费那一类，这也是本提案没有全盘保留它的原因。
- **对所有等待都做推测。**会为盈亏平衡为负的猜测付费，并去掩盖必修任务已经填满的等待。
- **长外部工作改为解耦，而不是掩盖。**这是对长等待的选定答案：把作业提交出去、稍后收集，从而把等待从关键路径上移除，而不是猜它的结果。正是这个替代方案让"掩盖等待"那一类变得不必要。
- **推测计划（让模型选择下一步做哪些任务）。**去掉了让验收有意义的固定计划，并把猜测者放到权威位置。
- **让第二个模型判定猜测是否成立。**二手判断替代不了证据：评判者的成对偏好中有可测比例会翻转，无参考的评判者打的是"像不像对"而不是"对不对"，正是本项目在早前一轮已经量到过的假阳性盆地。顾问可以说"不"，只有宿主可以说"是"。

## Acceptance criteria

- 每轮记录 worker 的 token、各步骤墙钟时间、以及任何被丢弃的推测及其成本；没有这些数字，任何收益主张都无法核对。
- 宿主侧推测要测量净省时间，并且猜错时不得拉长关键路径。
- 猜错的产物永不被接受：有测试证明与假设矛盾的真实终态会使受影响任务回到一次新尝试，并使绑定旧摘要的下游产物失效。
- 以被丢弃的推测结束的轮次必须显式报告这次亏损。
- 超过已观测最大验证运行时长的等待按"可能挂住"处理并如实报告，而不是当作推测的空间来利用。

## Risks

免费那一类成本低但收益也小，可能测不出可感知的改善；假设机制会给轮次增加一个状态维度，而恢复工作尚未完成。记录等待还会带来一种压力——把长等待当成机会，本记录明确拒绝这一点。最后，某个被猜测的前置条件如果命中率很高，那也说明该依赖应该被移除而不是被绕过，测量要求不能变成保留"不含信息的等待"的理由。
