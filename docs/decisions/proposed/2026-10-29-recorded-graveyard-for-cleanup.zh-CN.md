# 用可记录的 graveyard 收尾提交完成不了的清理

[English](2026-10-29-recorded-graveyard-for-cleanup.md) · [Terms](2026-10-29-recorded-graveyard-for-cleanup.terms.yaml)

**Status:** proposed

## 问题

被取代的分区快照的清理只能发生在 manifest 的比较交换**成功之后**——只有"不再引用它的 manifest 已经持久化"
这一条成立，键才可以删。于是有三种情况会留下**没有名字**的孤儿：

- 提交之后、删除之前函数被杀（平台上限、重启）；
- 删除失败，调用方的 `.catch(() => {})` 把它吞掉；
- 删除现在按 provider 的 1000 键上限分批，后一批失败时前一批已经成功——**部分清理**，既不报错也不留名。

这三种从 manifest 都看不出来，而 manifest 是后续请求唯一读取的东西。真正关心的不变量——`parts/` 下的每个键都被
manifest 引用——只在"无崩溃、且每一批删除都成功"的静默期成立，而那正是事故破坏的条件。

## Proposal

在删除之前把待删的键记进 manifest，让失败的删除有一个能活过本次请求的名字。

1. **顺序：先记后删。** 键在"不再引用它们"的那一次 CAS 里追加进 `manifest.graveyard`。旧 graveyard 的删除发生在
   该 CAS **之前**，且只删"既不在新 `parts`、也不在新 `graveyard`"里的键——**绝不删本次提交刚写进去的键**，
   否则 drain 会吃掉自己刚记下的东西。
2. **删失败的留在名字里。** 删不掉的键留在新 `graveyard` 里，被顺路带到下一次提交，没有任何额外往返。重试幂等，
   对手不可能引用我们的 graveyard 键，所以重删安全。
3. **绝不在 CAS 之前删待删键。** 看着安全（它们不在新 manifest 里），但重试的内容指纹仍可能指向其中之一，
   提交后的 manifest 就会引用一个已不存在的对象。CAS 之前的 drain 是形状相同、结论相反的另一件事，理由值得留住：
   graveyard 里的键来自**更早的请求**，因此永远不可能出现在本次请求的 `reuse` 里；而 staged 键**属于本次请求**
   ——这正是"删掉 staged 键还必须同时从 `reuse` 移除"那条规则必要的原因。外观相同，结论相反，理由不同。
4. **有界、新键优先。** 字段有上限；超限丢**最旧**的、保留最新的——最新的恰好是某批删除刚失败的那批。
   无界会让 manifest 在争用时无限增长。
5. **坏 graveyard 永不阻塞服务。** 读侧遇到非数组、或长度超过读上限的值时**跳过**（本次不 drain）并计数，
   **绝不 slice**——截断等于把一部分键从清理清单里悄悄扔掉，正是本条记录要防的泄漏。写侧**用本次待删集合覆盖**
   它并计数，于是我们写出的每个 manifest 都是良构的。无论字段内容如何，`/add`、`/search`、`/capacity` 都正常服务。
6. **计数器走运维已经在看的那条通道。** `userCapacity` 按用户返回 `pending_entries`、`manifest_bytes`，并且已经有
   80% 触发 `warnings` 的机制，所以 `graveyard_pending`、`graveyard_dropped_unparseable`、
   `graveyard_dropped_cap` 应放进同一个对象，且后两者非零时在那里产生一条 warning（"leaking"），
   而不是放在没人有理由去查的新字段里。`graveyard_pending` 只度量**被记录过的**积压；机理上线前产生的孤儿
   它看不见，必须单独测。

## 这确立了什么、没有确立什么

- 给出的是**有界且自愈**的残留，不是**立即**收敛：静默期的最后一批要等下一次提交，所以不变量在"最后一次提交之后"
  成立，不是"任意时刻"。
- **不修复已存在的孤儿**。只有本地 memory bucket soak 或一次性 admin LIST 能看到它们，两个数字不能当同一序列比较。
- **不让卡住的桶变快**，只是让残留有名字。

## 回滚

回滚期间，旧写入者不认识这个字段，重写 manifest 时会把它丢掉——新写入者记录的那批键就此失去唯一的名字；
再前滚也不会恢复。存储不会因此下降，泄漏从"有名字"变成"没名字"。记在这里，避免以后被当成新缺陷重新排查。

## Acceptance criteria

- **空态逐字节相等**：graveyard 为空时 manifest 里**根本没有** `graveyard` 键，于是从未触发该机理的用户与今天部署写出的
  完全不可区分；`JSON.stringify` 里不得出现这个字符串。
- **坏字段下仍可用**：seed 一个 `graveyard: "not-an-array"` 与一个超长数组的 manifest，断言 `/add`、`/search`、
  `/capacity` 全部正常作答、值在下一次成功写入前被原样保留、且计数被报出。没有这条，将来把行为改回 503 没有任何东西拦得住。
- **先记后删**：一次失败的删除会把键留在下一个 manifest 的 graveyard 里，随后一次成功提交把它清掉。

## Risks

- **drain 删掉一个仍在使用的键。** 过滤条件是"既不在新 `parts`、也不在新 `graveyard`"。这里判断错就是删掉被引用的快照——
  那是数据丢失，不是残留。这也是为什么必须先把过滤条件写清并测过，再启用机理。
- **cap 丢掉仍被引用的键。** 新键优先就是为了避免它；但比较方向写错就会丢最新的。验收测试要钉住**方向**，不只是长度。
- **旧写入者把字段丢掉**（见"回滚"）：在飞的那批键失去唯一名字，且永不恢复。
- **争用下 manifest 增长。** 由 cap 约束，但 cap 必须足够小，让 128 个分区的待删键永远不会逼近 `MAX_MANIFEST_BYTES`。

## 考虑过的替代方案

- **超时启发式**（"删掉 `parts/` 下比 N 更老的"）：需要一个后台清扫，而这个平台没有后台执行；而且是猜阈值，不是知道
  哪些键已被判死。
- **在 CAS 之前删**以消掉失败窗口：破坏重试，见规则 3。
- **无界 graveyard**：恰在写入争用时让 manifest 无限增长。
- **只在删除时重试而不记录**：分批把"整批被拒"变成了"部分失败"，真正能收尾的是同一次请求内由重试驱动的清扫。

## 后果

- 新增一个 manifest 字段，只在有话要记时出现，所以排空后的 manifest 与今天的逐字节相同。
- 清理最多多花一次提交来收敛，线上没有任何额外往来。
- 运维得到 `graveyard_pending` 这个"已记录积压有多少"的数字。

## 边界

这**不属于**加法日志的 accept 切片，也不属于它的门槛判据。它改变 manifest 格式，因此有自己的决策条目（本条）与
自己的提交边界；不能悄悄落在加法日志那张票里，否则以后没人说得清"manifest 为什么多了个字段"。
