# 分区读不出来，页面变短，而不是整个答案失败

[English](2026-10-30-search-degrades-on-unreadable-partition.md) · [Terms](2026-10-30-search-degrades-on-unreadable-partition.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

20:18:31、20:19:40、20:20:21、20:20:57，`/search` 返回 **503**，`stage=partition_download`、`dependency_timeout`，耗时 29–31 秒。同一实例（uptime 3699 → 3731 秒、同一 user id）在 3 秒前的 `/add` 返回 **200**，耗时 24 秒。

三条推论：

| 事实                       | 含义                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------- |
| 503，不是 120 s            | 业务侧失败，不是平台掐断——与此前每个窗口都不是同一类                                |
| `stage=partition_download` | 对象存储的 body 下载超时，检索根本没跑（`sqlite_loaded:false`、`live_databases:0`） |
| 同实例同用户 `/add` 200    | 写路径会降级，读路径不会                                                            |

对评测而言，`/search` 的 5xx 等于整次尝试失败；短页面只损失一题的召回。两者代价不同，而读路径是唯一付高价的那个面。

同一批日志还把 `embedding_host`/`embedding_model` 挂在 `stage=partition_download` 旁边，这正是"两者共用依赖"的误判来源——那两个字段其实是对**所有**失败一律附加的。

## 决策

- `search` 把一个读不出来的分区当作缺失分区：页面标 `partial: true` 并带 `degraded: <错误码>`；**连续两次**失败后停止按分区逐个付超时，用已读到的内容作答。
- "读不出来"是一份明确清单——`snapshot_changed`、`dependency_timeout`、`embedding_timeout`、`operation_aborted`、`TimeoutError`、`AbortError`、连接重置。其余错误照旧外抛：我们自己代码的 bug 必须保持可见，不能被折进一个更安静的回答里。
- 失败记录只在**失败阶段属于嵌入时**附加 `embedding_host`/`embedding_model`。永远存在的字段等于没有信息。

## 证据

| 改前                                                    | 改后                                                                                            |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 删掉一个已折叠的分区后 search → 5xx（套件里表现为失败） | search → **200**、`partial: true`、`degraded: "snapshot_changed"`，已在 `test-backend.mjs` 钉住 |
| 2.5 分钟内 4 次 503、每次 29–31 秒，而 `/add` 返回 200  | 同样条件下只付一次分区超时，不再让请求失败                                                      |
| `partition_download` 失败也报 `embedding_host`          | 该字段只在嵌入阶段出现                                                                          |

## 这确立了什么、没有确立什么

- 它**没有**诊断出分区下载为何要 29–31 秒。写路径在上传快照、读路径在同一下载，同时嵌入调用跨境到 `ap-southeast-1`；出口带宽饱和与对象存储限流都符合，但都未被证明。这次改的是影响半径，不是病因。
- 它不会让降级的页面得高分。五个分区里两个读不出来，仍然只有三个分区的召回——比整次失败好，但不等于健康。
- "连续两次即停"是判断：把"N 个分区 × 超时"压成两次超时，这是让降级检索留在 25 秒截止之内的代价。

## 考虑过的替代方案

- **多retry 几次下载**：`cos-bucket.mjs` 已对 429/5xx 重试两次；超时是刻意不重试的（见 `2026-10-29-embedding-invocation-budget`），因为在一次调用里重试一个停滞依赖，乘出来的是失败耗时。
- **返回 503 + Retry-After 让评测端重试**：harness 把 5xx 记为这次运行的失败尝试；而 partial 页面至少进入评分。
- **在写路径与读路径之间缓存分区**：写路径已经上传过它；为读缓存同样的字节，会把请求已经付过的内存再翻一倍，而这个平台每请求一个新 isolate。

## 后果

- `search` 的响应里除 `partial` 之外可能出现 `degraded`。忽略两者的调用方仍拿到结构完整的页面。
- "两次即停"让最坏情况可预测：两次分区超时，而不是每个分区一次。
- 失败记录在非嵌入阶段不再带 `embedding_host`。这正是目的，但也意味着过去"处处都有该字段"的事故时间线，之后只在适用的地方有。
