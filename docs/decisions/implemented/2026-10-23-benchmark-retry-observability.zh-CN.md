# 每次基准运行都记录重试尝试次数

[English](2026-10-23-benchmark-retry-observability.md) · [术语](2026-10-23-benchmark-retry-observability.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

官方 OmniMemEval 客户端会把失败的调用最多重试 `max_retries` 次（默认 4，即最多五次尝试），而只有成功那次进入它的 token 追踪器。因此一轮运行的 token 总量无法区分"一次干净作答"与"被重复计费的作答"：provider 已经生成响应之后的客户端超时，或响应路径上的上游 502，都会消耗报告里看不到的输入与输出 token。在默认 600 秒超时下，一个慢端点可以在所有产物都看起来完整的情况下，把一整套跑批的真实花费乘上几倍。

启动器本来就在每轮旁边写一份资源报告，官方客户端本来也每次重试打印一行告警。只是这两者此前没有接起来。

## 决策

在 `runPlan` 中转发官方 runner 的 stdout 与 stderr，用一个纯函数模块（`evals/omnimemeval/retry-observability.ts`）统计 `⚠ [<MODULE>] LLM retry k/N` 行，并在 `resource_report.json` 旁写出 `<结果目录>/retry_report.json`。报告包含总重试次数、按模块的重试次数与见过的最高重试序号、前几条原始告警行，以及在调用方能提供成功调用数时的"每次调用尝试数"比值。

统计是文本级、观测性的。重试循环仍留在被钉住的上游检出中；启动器不改变任何请求、重试策略、超时或调度，采集或写报告失败也绝不使一轮已完成的运行失败。操作者看到的流式输出保持原样。

## 考虑过的替代方案

- 改上游客户端在重试循环内部计数：会修改被适配器安装视为外部的钉住第三方检出，且下次同步上游就会丢失。
- 从 token 总量反推重试：追踪器每次成功响应只记一次调用，被计费的重试恰恰就是缺失的那部分。
- 由启动器默认下调 `MAX_RETRIES` 或 `TIMEOUT_SECONDS`：改变基准行为，而且是在掩盖而非测量"用重试代替作答"的端点。
- 让发生过重试的运行失败：瞬时故障的重试是合理的；需求是可观测，不是禁止。

## 后果

现在一轮运行会说明它实际尝试了多少次，token 总量因此可以读作"作答量"，而不是"作答量加上未知的重试花费"。耦合点是打印出来的告警行，因此上游改写文案会让统计静默归零；集成测试用一个打印该原文的夹具进程断言按模块计数，把这个漂移变成可见的失败，而不是沉默的零。

该报告仅作诊断。它不把花费归因到某个具体故障，不证明某次重试确实被计费，也不建立答案质量结论。某个端点上的重试次数不能外推到另一个端点。下调重试或超时设置仍是操作者在读过报告之后的决定。
