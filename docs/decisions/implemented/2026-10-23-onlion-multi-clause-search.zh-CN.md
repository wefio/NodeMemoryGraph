# 一次请求内的多子句检索

[English](2026-10-23-onlion-multi-clause-search.md) · [术语](2026-10-23-onlion-multi-clause-search.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

`/search` 只接受一个 `query` 加 `options`，并把检索子句拼成 `query` 与 `query + ' ' + option`。这个形状适合多选型题目，**表达不了独立子句**——也就是文本不是"原问加后缀"的那种子句，例如只用原问的内容词，或实体名加属性词。

于是想同时用两种检索视角的调用方只能发两次请求、自己融合。这会把每请求的固定开销付两遍——打开 store、读 manifest、取快照——同时让服务端已有的融合能力空转：`AmlMemoryService.search` 本来就在循环子句并按 memory id 保留最高分。

## 决策

`/search` 新增**加性**字段 `queries`：1–8 条子句，每条是字符串或 `{text, name}`。**子句由调用方给出，服务端不发明检索维度**。响应仍按原样融合——同一 memory id 取最高 `combinedScore`、排序、按 `top_k` 截断——并新增每条子句一行：

```json
{"clauses": [{"name": "original", "index": 0, "contributed": 7, "exclusive": 2}]}
```

`contributed` 是该子句放进返回页的条数，`exclusive` 是只有该子句放进的条数。两者都只在返回页上统计，因此调用方能看出自己新增的维度**是否挣到了这次请求**。

`queries[0]` 是呈现子句：时态渲染本来就取第一个查询。完全相同的子句文本在检索前合并（保留第一个标签），使融合下标始终对应唯一子句。`queries` 与 `query` 或 `options` 同时出现会被拒绝，而不是猜测。旧形状保持可用，并获得一条单子句的 `clauses` 行。

## 考虑过的替代方案

- 每条子句各自的 `top_k`：实测候选深度超过约二十条后对返回页毫无增益，多一个数字只会多一个没测过的组合。
- 融合模式开关：同一 memory id 取最高分实测优于轮转交错（同一批题上 20.8% 对 20.1%）。
- 服务端自建子句：会把检索策略写进 wire 格式，使每个新维度都变成一次服务端发布。
- 把多条子句拼成一个查询串：子句的独有贡献是**原问排序里根本不出现**的记忆，拼接属于另一种机制，不假设等价。

## 后果

一次请求可携带最多八种检索视角，返回一个带逐子句归因的池子。请求内部的子句循环仍是顺序执行，所以省下的是**重复的每请求固定开销**，不是检索计算本身。响应大小仍受 `top_k` 约束。

子句实现仅支持文本；多模态 `query` 依然走原有的 content-view 路径。归因是描述性的：它不证明某子句改善了答案，也不替调用方给子句排序。
