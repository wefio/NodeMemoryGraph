# 预算按实际渲染的证据面板计费

[English](2026-10-25-evidence-budget-rendered-cost.md) · [术语](2026-10-25-evidence-budget-rendered-cost.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

`src/core/store/active-graph.ts` 的 `estimateResultTokens` 决定一次搜索页能容纳多少条记录，它按候选的四个字段求和：statement、节点规范名、节点摘要、evidence 全文。其中只有两项会到达读者。`renderEvidenceSurface` 完整输出 statement、一行 details 元数据，以及 evidence 中至多 `SOURCE_EXCERPT_CHARS`（320）个字符作为 `SOURCE=` 摘录；**节点摘要从不输出**。

在 LongMemEval 运行 `lme/nmg-longmemeval_20261025T095539Z`（500 用户，每用户一个 store）上实测，两项收费没有对应的渲染物：

- 节点摘要是节点级元数据，被该节点的每条记录共享——此语料中平均每节点 10.59 条记录——按条收费等于把一段共享的 1,483 字符字符串乘以该节点的记录数。
- evidence 平均 1,037 字符，被按全文收费，而实际只渲染 320 字符。

每条记录的估算为 **898 token**，实际渲染 **377 token**，虚增 **2.38 倍**，因此启动器配置的 6,000 token 信封（`topK × 300`）只容纳 **6.68 条**。实际交付的页面平均 **6.894 条**，范围 1–12，从没有达到请求的 20 条。

表面症状是：页面看起来是一页排序结果，实际却是被截断的页面——预算不是被相关证据用掉的，而是被读者永远看不到的文本用掉的。

## 决策

让估算只对实际渲染的面板计费。

`estimateResultTokens` 现在按 statement 全文、按该行实际打印字段（`memory`、`node`、`type`、`truth`、`scope`、`time`）构造的 details 行余量加固定分隔符余量、以及仅在 evidence 与 statement 不同时的 `min(evidence.length, SOURCE_EXCERPT_CHARS)` 计费。节点摘要不再计费：既不渲染，又被节点内记录共享。

`SOURCE_EXCERPT_CHARS` 由 `src/integration/agent-surface.ts` 导出，渲染端与估算端共用，二者无法再无声漂移。`tests/core/active-graph-budget.test.ts` 固化了此前被违反的三条性质：5 万字符的节点摘要不得改变估算；5 万字符的 evidence 必须与其 320 字符摘录等价；6,000 token 预算必须容纳至少 15 条渲染尺寸的记录。

## 实测结果

同一批 store、同一 500 题，只改估算器。搜索步骤从空的逐用户检查点重新执行，因此页面是真实检索结果，不是旧页面的回放。

| 页面属性           | 修正前 | 修正后 |
| ------------------ | -----: | -----: |
| 平均记录数         |  6.894 | 17.316 |
| 中位               |      7 |     18 |
| 最大               |     12 |     20 |
| 达到 20 条的题数   |      0 |    143 |
| 平均渲染上下文字符 |  8,143 | 23,107 |

答题阶段，reader 与 judge 完全相同（`deepseek-v4-flash`、`temperature 0`、答案预算 300 输出 token、判分预算 1,000、关闭服务端推理）：

| 指标         | 修正前 |     修正后 |
| ------------ | -----: | ---------: |
| LLM-as-Judge | 0.6480 | **0.7680** |
| F1           | 0.1500 |     0.1517 |
| ROUGE-L      | 0.1147 |     0.1115 |
| METEOR       | 0.2071 |     0.2109 |

按类别（LLM-as-Judge）：

| 类别                      | 修正前 | 修正后 | 题数 |
| ------------------------- | -----: | -----: | ---: |
| multi-session             | 0.3609 | 0.5714 |  133 |

判分在 500 题上提高 **0.1200**，即**净增加 60 题判对**。对照运行的管道状态为：search 500 成功、answer 500 成功、eval 500 成功，零失败用户、零跳过记录、零空答案——差异不是靠跳过产生的。

## 其余三套件的配对重跑

BEAM、HaluMem、PersonaMem v2 在同一批 store 上重跑，从检索步骤开始重执行，全部旧产物保存在各自目录的 `.baseline-v1/` 作为配对基线。reader、judge 与预算与 LME 对照一致。

## 两类结果反对"证据越多越好"

BEAM 的 `event_ordering` 本被认为最应受益，因为它问的是多条发言被提及的先后顺序，更满的页面应包含更多相关发言。它几乎没动：0.1215 → 0.1423（+2.1pp），而 `temporal_reasoning`（+10.0pp）、`information_extraction`（+6.9pp）、`preference_following`（+6.9pp）、`instruction_following`（+6.3pp）动得远多，`knowledge_update` 反而从 0.6000 降到 0.5750（−2.5pp）。

PersonaMem v2 的 `ask_to_forget` 本被认为有风险，因为更满的页面会把更多已失效内容带进 reader 的上下文。它确实退步：0.2605 → 0.2261（−3.4pp），而其他类别都在涨（例如 `health_and_medical_conditions` 0.2905 → 0.3944、`neutral_preferences` 0.3485 → 0.4138）。

两种读法都与"页面是边界而不是杆杆"一致：容量把排序本来已经找到的证据补回来了，同时也把排序从未标记为失效的旧证据补了回来。两个观察都没有定位机制，也都没有做逐题检验。

## 这证明了什么、没证明什么

**证明了**：预算误算压缩了证据页；在相同配置预算下修正它，恢复了证据容量，并在四套件上改善了答案判分，其中 LongMemEval 最大。这是同一个计费修正跨四个数据集、一个 reader、一个 judge 的端到端效果。

**没有证明** recall@k 提升。前后页面都没有计算召回指标；被计数的是交付页规模与判分准确率，不是对 gold 标签的证据覆盖率。

**不能与早前的表示结果相加**。LoCoMo 上下文表示改造与本次修正没有交叉测量，二者不可按"独立贡献"相加或比较。

**F1 与 ROUGE 的变化是观察，不是解释**。F1 升 0.0017、ROUGE-L 降 0.0032、判分升 0.1200。用来解释这种分化的说法——更长页面稀释 n-gram 重合、弱 reader 更受益于完整证据——是关于机制的假设，不是测量结果；要确认或否定它，需要逐题对照答案与 gold 片段，这一步尚未做。

**"仍在预算内"只在估算器自身的口径下成立**。平均 23,107 渲染字符按估算器的"4 字符 ≈ 1 token"口径约 5,777 token，低于 6,000 信封。实际模型输入更大：其上还叠加了 prompt 模板与指令，这部分未测量。

## 考虑过的替代方案

- 提高配置信封而不修计费：能交付同样页面，但掩盖 2.38 倍虚增，且下次摘要或证据字段变长时会以同样比例抬高真实输入 token。
- 只去掉节点摘要收费：evidence 仍按渲染尺寸的 3.2 倍计费，页面仍填不满。
- 缩小 `SOURCE_EXCERPT_CHARS` 让错误计费刚好放得下：在错误的预算下用证据内容换记录数，让摘录去约束页面。
- 渲染两次以求精确长度：正确但要在排序期间为每个候选付一次完整渲染成本，且把排序成本绑到格式化细节而非其声明的预算字段。

## 后果

这是后续检索工作共同的对照基线：自此，记录选择的改动要对一个"在配置预算下真正装满"的页面来读。上文的配对重跑取代了此前"其余套件不可比"的说法；四套件现在都在同一计费口径下测量，基线保留在各自运行目录的 `.baseline-v1/`。

两个类别界定了容量的价值边界：BEAM 的 `event_ordering`（+2.1pp）与 PersonaMem v2 的 `ask_to_forget`（−3.4pp）说明，装满页面既不能修正顺序，也不能把已失效内容挡在 reader 上下文之外。

估算器现在与渲染端耦合。如果 `renderEvidenceSurface` 开始输出估算器未计费的内容（例如更长的摘录，或把摘要也渲染出来），页面会无声超出预算；导出的 `SOURCE_EXCERPT_CHARS` 与守护测试让摘录这一项显式化，任何新增的渲染字段都需要同样处理。

同一名义预算下页面长度约为原来的 2.8 倍，因此每查询的延迟与输入 token 成本随页面容量上升。这一变化是修正的后果，不是关于检索质量的证据。

早前规划把事件图与跨会话机制排在前面。这个结果使该排序过早：实测能力损失中有相当一部分来自"预算压缩了实际证据页"，因此必须先有修正后的基线，剩余失败才能被归因于缺少某类新机制。下一处杠杆不是新机制，而是页面里装什么——`SOURCE=` 摘录目前仍是证据的前 320 字符，而不是与问题相关、保留来源的片段。
