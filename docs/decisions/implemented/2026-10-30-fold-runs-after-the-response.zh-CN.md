# 折叠在响应之后跑

[English](2026-10-30-fold-runs-after-the-response.md) · [Terms](2026-10-30-fold-runs-after-the-response.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

2026-10-30 14:09-14:15，对已部署构建的一次并发 16 Add 突发的实测：

| 观察                                            | 值                                                                |
| ----------------------------------------------- | ----------------------------------------------------------------- |
| 被杀请求（120 s 上限）                          | **5 个**（14 / × / × / × / ×，一个携带 707 MB）                   |
| 一般 Add                                        | 11-25 s 常态；尾部 40.8 / 62.8 / 76.4 / 84 / 100.7 s              |
| 60 s 慢请求自报（`queue.running:1, waiting:0`） | isolate **不拥塞**                                                |
| 每一条慢/失败的栈                               | `addRoute → foldPending → mutateUser → sqliteReady`——**全是折叠** |
| `last_embedding`（本地成功调用）                | 突发下每次文档嵌入 19-24 s                                        |

机制：accept 返回条目后**内联地 await 折叠**——触发有 20 s 预算，但预算只管"要不要开始"，管不了"跑到一半"。同一用户 16 个写者，折叠彼此撞上同一个 manifest CAS，输家整轮重读分区；提供商跨区在突发下一次 19-24 s，折叠每轮还要回填 32 条。**被撞穿的是调用时钟，不是折叠预算。**

本通告顺带修正：上一轮记录里说"accept 谷不动折叠是因为我们的入口收不到 execution"——**这句对平台的陈述是错的**。两类模型都有 `waitUntil`：Edge Functions 的 `event.waitUntil`（doc 52688）和 Makers Functions handler 的 EventContext（`request / params / env / waitUntil`，doc 162227908259442688）。入口（`edgeone-entry.mjs`）只是当时没解构它——这也导致可选项共享失败历史（`NMG_ERROR_HISTORY=1`，`monitoring.mjs`）在生产从没跑过。该论述由本记录取代。

## 决策

**响应先给；折叠在调用的延长生命周期内（`waitUntil`）跑。**

- accept 仍内联嵌自己的消息（8 s 竞速）并写日志条目：**写入先于折叠**是折叠幂等的前提，被杀在飞行中的折叠只损失一次回填，不损失这次评测。
- 排程触发（1/`FOLD_TRIGGER` accept）不变，20 s 折叠预算不变——过了预算积压留给下次排程。
- 有 `waitUntil`（生产），排程到的折叠**响应之后启动**；没有（测试、wrangler dev）则与以前一样内联，带预算。`NMG_FOLD_INLINE=1` 强制内联以供测试确定性。
- 入口把 context 的 `waitUntil` 适配成 `monitoring.mjs` 已认的 execution 插槽，共享失败历史随之打开。

## 证据

| 改前（本次部署）                             | 改后（本轮，部署后实测）                     |
| -------------------------------------------- | -------------------------------------------- |
| 16-way 突发里 Add 常态 11-25 s、尾至 100.7 s | 同形态突发：非折叠 Add ≈ 0.5 s，折叠在后台跑 |
| 突发 5 请求被杀 120 s，栈全在 `foldPending`  | 后置折叠被杀只损失一次回填，不产生 503       |

## 这确立了什么、没有确立什么

- 提供商在突发下 19-24 s 的文档调用**没有被处理**：`waitUntil` 是把工作挪出客户端等待，它不能让提供商变快。评测端并发（1-2）与提供商配额才是这层的做法。
- 宽用户的 search 仍可能几十秒（查询嵌入跨区、分区大小）。本轮也不触碰。
- 起在同一 isolate 的折叠之间仍争 manifest CAS——只是现在不再出现在客户端的前面。
- 一个折叠最大回填 32 条；更多无向量的记录留到下一轮——不变。

## 考虑过的替代方案

- **维持内联但加严预算**：就是改前状态。预算只是不开始，进行中的折移不了；折叠/CAS 争用加慢提供商同一次仍到 100 s、120 s。
- **把嵌入也 `waitUntil` 后置**（条目先行无向量，响应后再嵌）：否决。第一次会把文档嵌入推回 search 路径——"search 是读"那轮刚去掉它；第二次留出一个词面分的精度窗口，窗口长度由提供商延迟决定，不受我们约束。
- **用 KV 共享计数器限接入速率**：突发的失败形态（折叠争用）已与计数器无关，KV 计数器重新引入了热共享键——正是几轮重构去掉的东西。

## 后果

- `edgeone-entry.mjs` 现在传 `{ waitUntil: (task) => context.waitUntil(task) }` 作为 execution 插槽。
- extra：折叠之折叠跑进响应后的窗口，accept 客户端不再淮遇它延迟；服务的其他部分不影响。
- 后记 0006 的并发结论不变：未动提供商或平台限制。
