# 长 query 用「clause 本身 + 规划窗」检索

[English](2026-10-28-query-window-plan.md) · [Terms](2026-10-28-query-window-plan.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

payload 上限按平台请求体设定，所以一次 Search 携带的 query 可以合法地远长于
embedding 模型的 token 窗：单条 query 最长 1,000,000 字符，而模型只看 512 token。
长 query 因此要被切分，而切分同时决定了两件事——query 的哪些部分进入模型，以及
一次检索花掉多少次 embedding 调用。

此前的切分（`splitQueryChunks`）从开头向前铺窗、按边界吸附，末尾再补一个锚定结尾
的窗。对 36,833 字符的 query，那是 8 个窗覆盖 `[0, 14000)` 与 `[34833, 36833)`：
前部密集，中间是一整块约 20,800 字符的盲区。第一个特征还是整条原始 clause（最长
1,000,000 字符），由 provider 自己截断——等于付了兆字节的请求体，只换来一个头部
向量。

在 281 条 LoCoMo multi-hop 上量到的直接后果是：把问题放在文本中段时，得分**与完全
不切分完全相同**——整页覆盖 2.14%，而不切分也是 2.14%，还不如问题在结尾时的 5.34%。
多出来的窗并没有覆盖中段；在 36,000 字符下，此前的布局在该条件上完全没能超过
"不切分"基线（0W/0L）。

## 决策

用几何方式规划窗，并把特征预算变成可数的配额。

`planQueryWindows`（`onlion/backend/query-chunks.mjs`）按 `n = min(ceil(L / W),
MAX_QUERY_WINDOWS)`（`W = QUERY_CHUNK_CHARS`）在两套布局中选一套：

- `L <= n*W`：预算覆盖全文 → 切成 `n` 段等长、连续、互不重叠的整段，接缝共用一个
  吸附后的切点，既不丢字也不重复嵌入；
- `L > n*W`：预算不足 → `n` 个 `W` 窗，首窗从开头起、末窗锚定结尾，未被覆盖的文本
  在它们之间均匀分布。

`selectQueryFeatures` 随后把每条 clause 的特征列表构造成：**clause 本身放第一位**，
其后是尾锚窗与中间窗。规划出的**首窗被丢弃**——它只是重新覆盖开头，而 clause 特征
用更长（按 token 计）的窗口已经覆盖了同一区域。

预算是**按次数**计的，不是按时间。`MAX_QUERY_FEATURES = 24` 跨 clause 轮转共享，
因此任何一句拿到第三个窗之前，所有句都先拿到两端，一次请求会把预算填满而不是停在
固定条数。`MAX_QUERY_WINDOWS = 10` 是每句天花板，以 `limits.max_query_chunks` 上报。
不开放环境变量覆盖：同一个限制有两种改法，就等于多了一种没必要的改法，实测配置以
常量形式发布。此前的"内部窗额外调用预算"（`NMG_QUERY_INTERIOR_BUDGET`）出于同样理由
被删除。

`src` 侧的 embedding 客户端不受影响：整条 query 不再是单个输入，因此 provider 过去
那种静默截断不再决定什么内容可被检索。

## 实测结果

零 LLM 成本：在 `evals/locomo/results/locomo-eligible-manifest.json` 的 281 条
LoCoMo multi-hop 上量 gold 证据召回，page 20，本地 BGE
（`BAAI/bge-small-en-v1.5`），记录向量与产品路径一致。下表是四种长文本条件的整页
覆盖（`all%`），外加 `short` 对照——短 query 在每个 arm 里都是单个特征，因此必须
完全相同。

arm 定义：**E** = 现状（clause + 前向铺窗 + 一个尾锚窗）；**F** = 只有规划窗；
**G** = clause + 全部规划窗；**H** = clause + 规划窗但去掉首窗。

6,000 字符：

| arm             | long      | mixed | tail | mid  | 合计      |
| --------------- | --------- | ----- | ---- | ---- | --------- |
| E               | **11.74** | 7.83  | 7.12 | 3.91 | 30.60     |
| F（自适应 n=3） | 9.61      | 7.83  | 5.69 | 5.34 | 28.47     |
| G（n=10）       | 11.74     | 7.83  | 7.47 | 5.69 | 32.73     |
| H（n=10）       | 11.74     | 7.83  | 7.47 | 5.69 | **32.73** |

36,000 字符：

| arm             | long      | mixed | tail | mid  | 合计      |
| --------------- | --------- | ----- | ---- | ---- | --------- |
| E               | **11.74** | 7.83  | 5.34 | 1.78 | 26.69     |
| F（自适应 n=8） | 11.39     | 7.83  | 6.05 | 4.63 | 29.90     |
| G（n=10）       | 11.03     | 7.83  | 6.05 | 4.63 | 29.54     |
| H（n=10）       | 11.39     | 7.83  | 6.05 | 4.63 | **29.90** |

成对显著性用逐题的"整页命中与否"指标计算：

- **H > E，mid，36,000 字符：8W/0L，p=0.0078。** E 的 `mid` 不只是更弱，它等于
  "不切分"基线（1.78 对 2.14），说明 E 在那里花掉的窗是把参考答案挤出了页面。
- **H > E，mid，6,000 字符：6W/1L**（该长度下不显著）。
- **H 与 G：两个长度下所有条件都没有差异**（唯一例外是 36,000 的 `long`，H 1W/0L
  略好）。丢掉冗余首窗零损失，且每句省一次 embedding 调用。
- **E 与 H 在 `long` 上**：36,000 字符下在噪声内（0W/2L，p=0.5），6,000 字符下完全
  相同——因为两者都保留 clause 本身作为特征。
- `short` 在所有 arm 中完全一致，符合对照要求。

部署到 `nmg-memory-api-overseas`（`ap-hongkong`，部署 `dpedvhr1ryme`）后的在线验证：
`limits.max_query_chunks = 10`、`max_query_features = 24`、`npm run smoke:edgeone`
9/9；36,000 字符、问题分别落在头部/中段/结尾的 query 在 `top_k=100` 下都召回了植入
的记录（3.1 s / 4.3 s / 2.8 s）。

## 这确立了什么、没有确立什么

- 探针里的填充文本是**无信息的人工文本**，所以中段按构造不含信号。这里量到的是
  "没有中段窗的布局找不到落在中段的问题"，并不是"真实长 query 里有多少信息落在
  中段"。真实转写稿更可能有，那会让规划窗布局更占优——但那是推理，不是数字。
- 只量了检索：20 条页面的 gold 证据召回。没有 answer/judge 模型参与，本次改动没有
  任何端到端分数。因此它与此前任何 benchmark 结果**不可相加**。
- `W = 2000` 是**字符**，按英文标定（对该模型约 512 token）。中文里 512 token 大约
  只有 500 字符，所以一个窗仍可能超出模型 token 窗；布局本身不算错，但 `W` 不是
  语言中立的。
- 语料、问题、向量都是固定的，所以各 arm 之间可比，但不可与另一个语料、page 大小或
  embedding 模型的结果横比。

## 考虑过的替代方案

- **保留原有的前向铺窗** — 否决：留下一整块连续盲区，且在 mid 条件上与"不切分"持平。
- **只用规划窗、不要 clause 特征（F）** — 否决：丢掉头部对齐的召回（6,000 字符下
  9.61 对 11.74，7 次失利），因为模型自己的 token 窗给开头的上下文比字符窗更多。
- **保留 clause 特征 + 全部规划窗（G）** — 否决：它是 H 的超集且无收益，所有条件
  相同却多花一次 embedding 调用。
- **按墙钟预算**（"时间不够就停止切分"）— 否决：同一 query 在快机器与慢机器上会解析
  出不同窗口，使所有已记录的检索数字不可复现。
- **窗口向量池化** — 本次未重新评估；此前已量到，当 query 各部分方向不同时均值池化
  劣于按特征取最大。产品里没有任何地方池化窗口，因此该 helper 已从服务模块移除，
  只留在做过测量的探针里。

## 与本次一并被否决的：Add 的增量页写

同一轮排查还问了：Add 能否只上传变化的页，而不是整个分区快照（复用现有
`makePageDelta`）。用构建后的 worker 加真实的 384 维向量，在约 3 MB 的分区上实测：
8 条消息的 Add 改动 **72–86 页（每页 8 KiB，计 576–688 KB）**，20 条约 80–121 页，
30 条约 94–102 页，而 `PART_DELTA_LIMIT` 只有 256 KiB（32 页）。**13 次实测 0 次
命中。** overlay 是内联在 manifest 里的，抬高上限会让所有并发写者争用的那个对象变大，
而 `USER_DELTA_LIMIT` 是 1 MiB，约等于一次 Add。因此直接放弃，未做调参。

## 后果

- 一条长 clause 最多花 **10 次** embedding 调用（clause + 9 个窗）；改前是"一次无界
  输入 + 最多 8 个窗"。每次请求的特征数由 `MAX_QUERY_FEATURES` 兜底，所以上限不随
  调用方发送多少条 clause 而膨胀。
- 检索是确定性的：同一段 query 文本解析出的窗口与机器快慢、负载无关，已记录的
  benchmark 数字因此保持可比。
- 产品只保留三个常量（`QUERY_CHUNK_CHARS`、`MAX_QUERY_WINDOWS`、`MAX_QUERY_FEATURES`）
  和两个函数（`planQueryWindows`、`selectQueryFeatures`）。`NMG_QUERY_INTERIOR_BUDGET`
  从未发布、也没有新增覆盖变量，池化 helper 已离开服务模块。
- 探针保留了产出本记录的全部 arm（含旧布局）。只有"要跟随产品"的 arm 才 import 产品
  函数；基线若也 import，基线就会随产品一起漂移。
