# accept 不参与比较交换

[English](2026-10-29-accept-without-cas.md) · [Terms](2026-10-29-accept-without-cas.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

从干净网络对已部署构建实测：单用户在并发 1 时写入 2.6 秒，并发 4 时 **51-106 秒**，24 次请求里 7 次被 120 秒的调用上限杀掉；并发 16 时 32 次连接里 5 次根本没建立。被杀不是丢一分，而是整次评测作废——比赛方先探 `/health`，失败就停。

成因是结构性的，不是某个依赖慢。同一个用户的每次 accept 都要读 manifest、算新版本、带 ETag 写回；输家重读重算，最多十二次，而每次都要重新读写一个最多 8 MiB 的分区。而 accept 在 manifest 上写的**只有那个计数**。

## 决策

**写路径只追加，不争用。**

1. **accept 只写一样东西**：它自己的日志条目，键由请求哈希派生，没有对手能撞上。manifest 只读一次，为了拿日志答不了的两件事——代际，以及已折叠请求的回执。
2. **计数是派生的，不是写出来的。** 它唯一的消费者是看 `/capacity` 的运维，现在按有界前缀列举，并在触到上限时标 `pending_capped`。读路径不再信任零：`pendingForSearch` 与 `fusePendingRecords` 两处"计数为 0 就返回"的短路都已删除。
3. **折叠按排程触发，不再依赖计数。** 约每 `FOLD_TRIGGER` 次 accept 试一次（`NMG_FOLD_EVERY` 可覆盖）；折叠先列举，不足一批就什么都不做——浪费一次尝试只花一次列举，漏掉积压才会藏数据。
4. **accept 自己嵌自己这批消息，折叠复用这些向量。** 这条路径的文档文本是 `[日期 ]statement`（服务从不提供 `previous_turn`），所以在打开任何分区之前就已确定。accept 在 `NMG_ACCEPT_EMBED_MS`（8 秒）内嵌入并把向量与产生它的索引身份一起写进条目；折叠用它们播种客户端，只做存储。预算用尽不算错误：条目照写，折叠照旧嵌入。
5. **每个长操作都有界。** 折叠有 `NMG_FOLD_BUDGET_MS`（20 秒），超了跳过而不是失败；检索循环在 `NMG_SEARCH_DEADLINE_MS`（60 秒）停止并返回 `partial: true`；折叠的嵌入回填只做一批 32 条（`maxBatches: 1`），与检索路径一致——它原本会在一次请求里嵌完整个分区的积压。

| 测量                            | 值                                                                          |

| 并发 1 Add p50                  | 2.6 s（max 21.9 s，一次折叠）                                               |
| 并发 2 Add p50                  | 3.6 s（max 41.2 s，一次折叠）                                               |
| 并发 4 Add p50                  | 51.6-106 s，24 次里 7 次被杀                                                |
| 并发 16 连接失败                | 32 次里 5 次                                                                |
| 本次改动后每次 Add 的提供商调用 | **至多 1 次**，即使这次 Add 触发了折叠（24 次顺序 Add，且证明折叠确实跑过） |
| 提供商重试预算                  | 3 次尝试，只对 429/5xx；超时不重试                                          |

## 这确立了什么、没有确立什么

- **没有在已部署构建上验证。** 上面每个数字都是改动前；改动后需要一次真实运行。
- 它没有消除**折叠自身**的争用：同一用户两个并发折叠仍会在 manifest 上相遇并被重试。它消除的是**每次 accept 都会走的那条路**上的争用，而放大正是发生在那里。
- 计数滞后只会导致多折一次，绝不会导致漏折：偏高只花一次列举，而读路径不再信任零。

## 考虑过的替代方案

- **保留计数、加大重试**：这就是被测量的失败形态，十二次尝试每次都重做 MB 级工作。
- **分片计数（AWS 的 write sharding）或 G-Counter / PN-Counter**：分片只是把争用除以片数，仍然存在；只增计数器表达不了会缩小的积压，而 PN 的减法无法与日志核对共存，一旦核对就不再可合并。两者都劣于"派生"。
- **把计数放 KV**（本平台 1 GB、当前未用）——与业界同形的答案，因为对象存储本来不是队列。没有采纳的理由：唯一消费者是一个人偶尔看 `/capacity`，一次列举就能答。
- **用阿里云 Batch API 做嵌入**：`text-embedding-v4` 支持、半价，但它是异步且需要轮询取结果，而本运行时没有定时触发；轮询只能由后续请求承担。服务路径上否决，离线全库重嵌仍然适用。
- **响应之后再嵌（waitUntil）**：这里的平台陈述后来被证伪——两类函数模型都提供 `waitUntil`，见 `2026-10-30-fold-runs-after-the-response` 的修正。否决里仍然站得住的部分：向量随条目折叠落库，才让读路径不为文档嵌入买单；后置嵌入会把这条重新交出去。

## 后果

- 一次 accept 就是几 KB 的一次 PUT。突发不再放大成重试。
- `/capacity` 要花一次列举——所以由运维路径付，请求路径不付。
- **现在回滚代码必须先排空日志。** 旧部署用 `pendingCount === 0` 短路，而本部署不再维护该计数，于是它可能把有内容的日志读成空。守卫是 `/admin/fold`：未清空就返回 409。
- 一次 accept 的内联嵌入若超预算，那条记录会被嵌两次（一次被放弃、一次在折叠里）。这是本次引入的唯一重复花费，且只在提供商慢于 8 秒时发生。
