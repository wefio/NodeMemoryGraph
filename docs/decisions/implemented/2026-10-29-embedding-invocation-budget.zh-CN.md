# embed 路径由调用时长约束，而不是由上游决定

[English](2026-10-29-embedding-invocation-budget.md) · [Terms](2026-10-29-embedding-invocation-budget.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

一次计分跑被中断了两次。平台日志里，2026-10-29 有 **220 次调用全部精确跑了 120000 ms**
——那就是 EdgeOne 的上限（`cloudFunctions.maxDuration: 120` 已经配好）——常驻内存
762 MB 到 1014 MB（p50 892，p95 999）。没有一条是"慢"，全是被杀。

失败分两段，成因不同，**欠费只解释第二段**：

| 时间窗              | 发生了什么                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------- |
| 05:18:45 – 10:43:36 | 220 次调用挂到上限，此时账户还有额度（05 点 34 次、08 点 17 次、09 点 129 次、10 点 40 次） |
| 10:44:17 – 10:45:36 | 52 秒内 21 条 `embedding_http_400`，17 个 trace；上游开始拒绝，这些请求快速失败             |

占掉 7.3 个实例·小时的是第一段，它发生在上游"慢"而不是"拒绝"的时候。

## 根因

`onlion` 强制的单次嵌入超时比它自己以为的更大：

```js
// onlion/backend/worker.mjs
NMG_EMBED_TIMEOUT_MS: env.NMG_EMBED_TIMEOUT_MS ?? "90000",
```

而客户端会重试超时（注释原文是"请求可能只是慢"）：

```js
// src/core/openai-embedding.ts
} catch (error) {
  // A timeout is retried too: the request may simply have been slow.
  if (attempt >= RETRY_DELAYS_MS.length) throw error;
}
```

于是一次逻辑调用要花 `90 s + 0.15 s + 90 s` 才失败——已经越过 120 s 上限——而 pending 融合在
单次检索里最多发起 **40 次串行调用**。40 次各以 90 s 超时兜底的调用落在 120 s 的调用预算里，
不是"慢请求"，是**不可能完成的请求**，平台替我们杀掉了它。而被杀的调用不留下任何诊断，
所以事故看起来只剩"每条都是 120 s"。

## 决策

用调用时长约束 embed 路径：

1. **单次超时 10 s**（`EMBED_TIMEOUT_MS`），即客户端自己的默认值，取代强制的 90 s。
2. **超时不重试**；连接重置仍然重试，因为它不说明上游慢。
3. **一次批量调用，而不是每个文本一次**：向量完全相同，改变的只是往返次数。
4. **query 侧嵌入每请求 25 s 总预算**（`NMG_EMBED_QUERY_BUDGET_MS`），所有调用点共享。用尽后
   调用被拒绝，而每个调用方本来就已降级为词重叠打分。文档侧不设预算：它承载记忆本身，
   由单次超时与批量大小约束。
5. **COS 每次请求 20 s 超时**，并作为可重试错误上抛。此前没有任何东西约束它，卡住的桶同样
   制造 120 s 死亡。
6. **60 s 慢请求自报**（`nmg_slow_request`，带 trace、路由、耗时与队列状态），因为被杀的调用
   什么都不留。
7. `/health limits` 报出 `embed_timeout_ms`、`embed_query_budget_ms`、`slow_report_ms`，
   让约束调用的数字可见，而不是靠推断。

## 证据

| 论断                     | 依据                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------- |
| 是平台上限杀的           | 220 条全部 `运行时间 = 120000`，且 `maxDuration` 已是平台最大值                     |
| 挂死不发生在欠费窗口     | 21 条上游拒绝全部落在 10:44:17–10:45:36，晚于最后一次超时 10:43:36                  |
| 修复前是"每文本一次调用" | 六条 pending 记录的一次检索产生 **7 次调用，输入数 1/1/1/1/1/1/1**                  |
| 修复后是一次             | 同一次检索产生 **1 次调用、8 个输入**，测试断言此性质                               |
| 超时不重试               | `tests/core/openai-embedding.test.ts`：比预算更慢的服务只被访问一次，已越过两段退避 |
| 重置仍重试               | 同文件：首次尝试被销毁的 socket 会重试，第二次成功                                  |

## 这确立了什么、没有确立什么

- **内存压力没有被排除。** 220 次调用死在 762–1014 MB 之间，若实例上限是 1 GiB 就是 88–99%
  占用。被杀的调用没有阶段计时，数据无法区分"等上游"与"GC 抖动到上限"。60 s 自报就是用来
  在下一次分开这两者的。
- **上游自身行为未经证实。** 400 只按状态码归类。响应体本来就在异常信息里，`NMG_DEBUG_ERRORS=1`
  会记录它；不带该开关时，日志无法区分"余额不足"和"批量参数非法"。
- **90 s 这个默认值没有任何记录解释过。** 这里把它当缺陷处理，而不是推翻某个决定。

## 考虑过的替代方案

- **调大 `maxDuration`。** 已是平台最大值 120 s。
- **归因于 OPFS 初始化噪音。** `sqliteReady()` 有 memo，VFS 安装每个实例只发生一次，且异常被
  SQLite 模块吞掉。重复的日志行来自并发实例，不是重试，也没有可测的时间成本。
- **把上游拒绝当作超时的原因。** 非可重试状态由客户端立即返回，而且那批拒绝比最后一次超时
  晚 41 秒才出现。

## 后果

- 上游变慢现在只损失得分，不损失调用：缺失向量的部分用词重叠打分，检索仍然作答。
- 批量融合对健康的上游也更便宜：一次往返取代最多四十次，延迟与上游负载同步下降。
- 写入路径保持原有宽松度。文档不设预算，大 Add 不会被 query 预算截断，而由单次超时与
  批量大小约束。
- 运维可以从 `/health limits` 直接读到三个约束数字；活过 60 秒的请求会在仍存活时先自报。
- 未处理：单次调用常驻内存 762–1014 MB。若实例上限是 1 GiB，这就是下一个要查的失败，
  而慢请求自报会告诉我们是内存还是等待。
