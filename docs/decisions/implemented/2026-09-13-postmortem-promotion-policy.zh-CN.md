# 一篇事故复盘什么时候变成一条规则

[English](2026-09-13-postmortem-promotion-policy.md)

**Status:** implemented  
**Approved:** explicit

## 问题

事故复盘层落地时只有生产者契约：什么时候写、必须回答哪些章节、如何编号与索引（见[该层决策](2026-09-13-postmortem-tier.md)）。没有任何东西说明这份语料是_为了什么_。一篇在文字里点名自己防护的记录，读起来像是这一类已被拦住，而仓库里没有任何东西在强制什么；当同一类失败第二次出现时，也没有一条从"它又发生了"通向"现在它会大声失败"的路径。

这份语料还完全是事后的。每篇记录都写在失败之后、通常也写在修复之后，所以任何假设"先有记录、后有防护"的提升规则，描述的都是没人跑过的流程。它必须是一次对账：检验已经存在的防护，并在没有防护时如实说明。

两次失败已经暴露了这个缺口。两次都是偶然发现的，也属于同一类——本该大声失败却静默降级的回退——而都没有产生一条命名该类的规则。第三次发生也不会改变任何事。

## 决策

消费端由该层自己拥有，写在 [docs/postmortem/README.zh-CN.md](../../postmortem/README.zh-CN.md#消费端从记录到规则)：

- 记录是"这一类存在"的证据；防护是下次会大声失败的机制。记录永远不是防护。
- **提升落在第一个能承载它的 owner 上**，沿用仓库已有的优先顺序：一道校验，然后是拥有该领域的 `AGENTS.md` 或 Skill 里的一条常驻规则，然后是一篇决策，最后是已经拥有该流程的文档中的一节。
- **三个触发条件**：这一类已经逃过两次（索引里有两行同一 failure class）；唯一的防护就是记录自己的文字；记录是 `open`。
- **不提升也是正当结果**，并且要在 `Lessons` 里写明，而不是留空。只出现过一次、且预防成本高于失败成本的，就是一个故事。
- `Status: resolved` 意味着防护存在且已链接；若唯一的防护只是文字，记录保持 `open` 并写明原因。
- 把规则提升进 Skill 或 `AGENTS.md` 遵循[审批分层](2026-09-09-approval-tiers.zh-CN.md)。
- 这份策略刻意写得很薄；当语料显示它失效时，用一篇决策来修订，而不是直接编辑该节。

[分类表](../../postmortem/README.zh-CN.md#分类与典型案例)拥有分类体系：每一类一行，包含它的典型案例——读者应先读的那篇记录——和它产生的规则。记录的类别只写在索引里而不写在记录里，因此分类体系只有一处可读。

## 考虑过的替代方案

**不要消费端策略。** 这正是已知两起事故所处的现状：失败故事不断累积，彼此之间没有任何连接。否决理由：那样这份语料除了一份阅读清单之外不产出任何东西，而唯一值得计算的事实——哪些类别在重复——没有任何地方计算。

**单独的守则文件**（`docs/postmortem/POLICY.md`，或一份消费该层的 guide）。一份独立的"管理办法"更容易指认。目前否决：`docs:check` 规定记录名为 `NNNN-slug.md`，该层里任何其他文件都是命名错误，因此第二个文件需要开门的例外；而且第二份文档会复述该层自己的归属与命名规则，而那些规则 README 已经写明。目前 README 只有一屏。当消费端膨胀到超出该层自身规则时再重新考虑。

**把提升做成机械校验**：当两篇记录共用同一 failure class 而没有类别行指名典型案例时报错或告警。这是推迟而不是否决——原则上可校验，但需要把逐篇索引表当数据解析，而且目前还没有第二篇记录可供测试。它也正好是这份策略要引导的判断：门会在正当的单次发生上误报。

**要求先有规则才能把记录标为 `resolved`。** 否决：防护完全可能是一条没有可链接产物的局部约定，而为了关闭一篇记录去硬造出一条规则，正是这份策略要避免的失效方式。`open` 加原因才是诚实的状态。

**把提升规则放进 `skills/doc-maintenance/SKILL.md`。** 否决：提升是这份语料的属性，不是文档工作流的属性。Skill 只留指针，那正是 Agent 遇见它的地方。

## 后果

- 语料有了消费端，分类表就是"从失败类别到拦住它的东西"的映射。规则列为空的类别行是一次刻意且可见的承认。
- 没有任何机械机制强制提升。同一类的两篇记录可以一直不被提升；分类表就是信号，读它靠 Agent 或人的判断。被推迟的那道校验是它的机械版本，等形状稳定后再做。
- `Lessons` 多了第二份职责：说明何时没有规则适用。含糊的 `Lessons` 从此是在掩盖一个决定，而不只是写得薄。
- 这份策略是三个触发条件加四个 owner，细节上预计会出错。修订它就是写一篇像这样的决策。
