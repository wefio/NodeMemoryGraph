# Add 默认走日志受理

[English](2026-10-28-add-log-accept-default.md) · [Terms](2026-10-28-add-log-accept-default.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

`Add` 原本是对整个用户分区的读-改-写，由每用户的 manifest CAS 串行化。同一用户 16 路并发
会被拉成 16 轮，每轮搬动兆字节；评测方看到的结果是 `/add` 从 36 s 升到 95 s、最后 120 s
平台超时，而 `/health` 与 `/search` 一直是毫秒级。

日志受理路径就是为此而建（见[设计](../../design/add-append-log-and-fold-design.zh-CN.md)）：
受理只写一条不可变条目，折叠每次分区写吸收最多 `MERGE_BATCH` 条，读路径能看见尚未折叠的条目。
它一直藏在 `NMG_ADD_MODE` 后面，默认 `sync`，直到有测量能支撑切换。

## 决策

默认改为 `log`。`NMG_ADD_MODE=sync` 无需改代码即可回到旧路径，所以切换是配置、一次部署可逆。

门槛是"**无回退**"而不是某个绝对延迟：这条路径上的基础成本主要由连接与 embedding 决定，
要回答的是"经日志受理会不会让 Add 变慢"，而不是"能不能让链路变快"。

## 实测结果

同一用户、每次 8 条消息、16 路并发，同一客户端、同一端点（`ap-hongkong`），先做一次预热
Add，因此每次运行只有一轮。跨过折叠阈值的轮被排除；`rounds=1` 时没有任何一轮跨过。

| 模式   | 运行       | 响应                     | p50                     | max                     | 失败 |
| ------ | ---------- | ------------------------ | ----------------------- | ----------------------- | ---- |
| `sync` | 1 个干净轮 | 16 × 200                 | 21.8 s                  | 30.7 s                  | 0    |
| `log`  | 4 个干净轮 | 每轮 16 × 200（合计 64） | 3.8 / 4.3 / 4.3 / 3.8 s | 5.9 / 5.2 / 7.3 / 4.9 s | 0    |

这次突发里，受理路径的中位数便宜约 5 倍、最坏情况便宜约 6 倍。没有回退。

### 抖动本身也是结果

同一小时内约有半数的运行里，16 个请求中有 5–20 个**无法建立连接**
（`UND_ERR_CONNECT_TIMEOUT`），两种模式都出现，而同一次运行里另一些请求是毫秒级返回。
这些运行不是"可以丢掉的噪声"：客户端连不上端点，正是评测方报告的那种体验，而日志切换既
不制造它也不治愈它。对这个决策而言重要的是：两种模式的干净运行取自同一路径、相隔约一小时，
而它们之间的差异远大于同一模式内的运行间波动。

## 这确立了什么、没有确立什么

- **折叠成本未测量。** `rounds=1` 且是新用户，pending 峰值只有 17，从未到达
  `FOLD_TRIGGER`（24），所以这些运行里没有任何请求为折叠付过代价。测量的是受理路径。
  折叠的成本是"每批一次分区写"、由 `MERGE_BATCH` 封顶，但它在生产中的延迟未知。
- 一个地区、一个用户、一种 payload 形状（8 条消息）。不同的突发规模、长期存在的用户或别的
  地区都可能不同。
- 上面的抖动意味着单次运行之间不可横比；只有**零客户端失败**的运行被采用，其中 `log` 有四个、
  `sync` 只有一个。
- 不主张任何答案质量或检索效果的变化：这次改变的是"Add 何时成为分区的一部分"，不是"存了什么"。

## 考虑过的替代方案

- **保留 `sync`，只调重试预算。** 503 来自 16 个写者打满 12 次 CAS；预算调小只是把 503 提前，
  调大只是把成功推后，都不改变一次突发要重写多少次分区。
- **`Add` 走增量页写。** 此前实测否决：8 条消息的 Add 改 72–86 页（每页 8 KiB），而预算是
  32 页（`PART_DELTA_LIMIT`），13 次里 0 次命中；且 overlay 内联在所有写者争用的 manifest 里。
- **服务端合并并发的 `Add`。** 函数实例之间无共享状态，"收集并发写一次性落盘"需要一个部署里
  没有的协调者，以及这个运行时提供不了的队列。
- **等稳定客户端测完再切。** 这条路径的基础成本是连接与模型调用，两条路径共享；受理路径上
  5 倍的差异远大于运行间波动，而切回只差一个环境变量。

## 后果

- 受理后的 Add 在折叠之前通过 `pendingForSearch` 可读，每次检索最多 `MAX_PENDING_READ` 条。
- `/capacity` 上报 `pending_entries`；`sqlite_bytes` 在首次折叠前保持 0——这就是 EdgeOne smoke
  不能再断言"Add 之后 `sqlite_bytes > 0`"的原因。
- 存在 pending 条目时回滚**代码**需要先排空：`POST /admin/fold?user_id=` 在日志清空前返回 409，
  而 v4 的 manifest 对旧部署不可读。
- 折叠只发生在 `Add` 路径（pending 达到 `FOLD_TRIGGER` 时），读路径永不折叠，因此检索延迟不
  继承写竞争。

## 后续修正：检索窗口取最新的条目

这条路径的第一版把**最老**的 pending 条目放进检索窗口——那是折叠该有的顺序，不是读取该有的
顺序。在已部署服务上用同一用户连续 20 次 Add 实测（低于折叠阈值，因此没有发生折叠）：
marker 0、3、7 命中，marker 8、12、19 缺失——窗口装的是最老的 8 条，之后的全被挡住。而且没有
任何机制会把它们捞回来：检索从不折叠，折叠由计数器触发。

`listPending` 增加 `newest` 选项：先按名字取到达顺序的尾部，再读 body；检索路径传它。折叠仍读
头部，因此条目依旧按到达顺序被应用。一条测试同时钉住两个方向，因为只钉一边会看起来"都对"。
