# 只进追加段（append-only）的检索子句

[English](2026-10-23-onlion-append-only-clauses.md) · [术语](2026-10-23-onlion-append-only-clauses.terms.yaml)

**Status:** implemented
**Approved:** explicit
**Relates to:** [多子句检索](2026-10-23-onlion-multi-clause-search.zh-CN.md)

## 问题

子句按 memory id 取最高分融合，再截到 `top_k`。这个融合假设各子句可比：**分数偏高但精度低的子句会劫持页面**。在 LoCoMo 多跳集上实测，第 4 条只检索问题实体名的子句，返回记录里仅 0.4% 携带标注证据；融合进 20 条页面后，全覆盖从 20.8% 掉到 7.9%（0 胜 36 负）。按名次融合与逐路归一化更差（12.9% 与 7.5%）。

同一条子句只作**补充**——放在页旁边而不是页里——在同一批题上把覆盖提到 24.7%（+3.9pp）。

页面是**分配决策**。一个宽而糙的维度不应该参与这个决策。

## 决策

`queries` 的子句可带 `appendOnly: true`（或 `mode: "append"`）。其结果不进入排序池：单独收集、与页面按 memory id 去重、以与 `data` 相同的投影作为 `appended` 返回。页面仍只来自参与排序的子句。

边界与拒绝：

- 第一条子句承载呈现语义，不能是 append-only；
- 至少要有 1 条参与排序的子句；
- `appended` 按 `top_k` 条数封顶；无 append-only 子句时该字段不出现，保持仅排序响应形状不变。

服务端只按**条数**封顶。追加段的**字符预算**属于渲染它的调用方：实测覆盖率随追加字符增长，到约页面文本 2 倍为止，之后趋平。

## 考虑过的替代方案

- 全部融合、让分数决定：用宽子句实测 7.9%。
- RRF 或逐路归一化融合：12.9% 与 7.5%，仍低于仅排序的 20.8%。
- 按子句精度自动判定 append-only：需要在查询时就有标注信号，而这种信号不存在。
- 降低宽子句权重：权重仍能让它挤掉页面记录，且每题正确的权重未知。

## 后果

调用方现在可以挂一个宽但不精确的维度，而不必在页面上付代价。两个字段而不是一个，让这一区分显式化：读者可以在自己的预算下渲染追加段，或直接忽略。

追加段与页面之间**不做排序**：两个字段里哪条更好仍是调用方的决定。归因沿用相同的 `contributes`/`exclusive` 计数；append-only 子句按构造在页面上恒为 0 贡献。
