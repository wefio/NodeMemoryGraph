# 依赖调用需要一个由调用方强制的截止时间

**Status:** implemented
**Approved:** explicit
**Relates to:** [search-time-budget-design](../../design/search-time-budget-design.zh-CN.md)

## 问题

六次 `/search` 在 60.0–60.2 秒被报告，`stage_isolate: "embedding"`，随后跑到平台 120 秒上限被杀，没有留下任何回答行。

有两件事让日志无法解释它：

1. 线上配置把嵌入阶段界定得远低于 60 秒：请求开始时启动的预算时钟、单次调用 10 秒超时、每次调用前过预算门。单次嵌入调用不该活过约 35 秒。
2. 同一批报告里有 `last_embedding: { status: "ok", ms: 168 }`——一次**已经完成**的嵌入——却与声称仍在嵌入的阶段并排出现。所以那个阶段名不能当作"卡在这里"的证据。

随后在生产运行时版本（Node 20.19，Node 24 复测一致）上测了三类悬挂：对端接受连接但不回响应、TLS 握手永不完成、回了响应头而 body 卡住。三类全部准时 abort（10 019 / 5 012 / 5 010 毫秒）。因此"abort 不работа"在一般情况下是错的，而具体是哪条路径挂住仍然未知。

不未知的是这个洞的形状：取消信号曾是**唯一**的界，而传输层自己的兜底是 `headersTimeout` / `bodyTimeout` = **300 秒**（undici 文档默认值，且不承诺精确触发）。因此任何没有如期结算的信号，背后只剩 120 秒的掐断。

## 决策

- 每次嵌入调用额外带一个由调用方强制的截止：调用自身超时加宽限（`EMBED_DEADLINE_GRACE_MS`，3 秒），由 `hardDeadline` 执行。正常情况下信号先到，错误分类不变；该截止只在 promise 完全不结算时触发。其错误码 `embedding_deadline` 与依赖超时同等对待（熔断器与读路径降级清单）。
- 慢请求报告增加 `ms_in_stage`，每条请求行增加 `stage_at_exit`。

## 证据

| 检查                                           | 结果                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------- |
| 对永不结算的 promise 施加 `hardDeadline`       | 在截止处拒绝，码为 `embedding_deadline`                                    |
| 对返回值 / 调用方自身的错误 / 慢但会完成的工作 | 值原样返回，调用方错误对象不被替换，30 毫秒的调用在 200 毫秒截止下不被切断 |
| 阶段年龄：阶段内、结束后、嵌套                 | 报告自身年龄、结束时不再作为当前阶段、嵌套恢复外层阶段及其年龄             |
| 端到端：提供商回答文档、永不回答查询文本       | `Add` 56 毫秒，`/search` 176 毫秒返回 200，且观测到至少一次挂起的调用      |
| `npm run verify`                               | 46 PASS                                                                    |

## 这确立了什么、没有确立什么

- 它**没有**找出那个窗口里挂住的是什么。它让下一次可被回答：只剩 60 秒报告的掐断，现在会说出该阶段已进入多久；而一个跑完的请求会记录它离开时所处的阶段。
- 它不会让挂住的提供商变快。它界定的是单次调用的代价；需要多次调用的请求仍要付多份界，这也是预算仍是外层界的原因。

## 后果

- 永不结算的调用现在只花掉自身超时加 3 秒，而不是跑到上限。读路径上结果是一张更短的页面，`degraded` 给出错误码；写路径上记录以无向量形式存下，由后续折叠重试。
- `embedding_deadline` 加入熔断器的触发清单与读路径降级清单，于是一次挂起会抑制该次调用的其余调用，而不是重复付代价。
- 两个日志字段从此恒在：慢报告的 `ms_in_stage`、请求行的 `stage_at_exit`。按字段名读日志的地方会多一个字段，而下一次事故不必再开一轮假设。
- 机制文档新增的是不变量 8 与 9，而不是"超时"章节：调参仍然不得改动它。

## 考虑过的替代方案

- **相信信号，只把超时调小**：至少有一条路径已经证明不然；而且调小并不能覆盖"永不结算"。
- **熔断器打开时关掉向量检索**：熔断器在第一次失败后确实这么做；它帮不了第一次调用——而那次正是挂住的那次。
- **什么都不做，等下一次事故**：下一次会打印同样无法回答的那一行。
