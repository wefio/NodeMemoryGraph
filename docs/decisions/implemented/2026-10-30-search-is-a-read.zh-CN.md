# 检索是读操作：查询路径不参与比较交换

[English](2026-10-30-search-is-a-read.md) · [Terms](2026-10-30-search-is-a-read.terms.yaml)

**Status:** implemented
**Approved:** explicit

## 问题

2026-10-30 01:31:48，一次 `/search` 以 **90 ms**、53 MB、503 失败，平台日志为空。测量结果能收窄它的形态：一次 manifest CAS 重试至少要 12 次对象往返（实测 2.4 s 起），`storage_corrupt` 也要先读一次 manifest——**90 ms 短到根本没碰过存储**。同一时间窗里 Add 一切正常，与已知的非对称吻合：accept 移到追加日志之后，**search 是唯一还在写的读路径**——它 stage 分区 delta、编码页、在 ETag 比较交换下提交 manifest，因此只有它可能死于冲突或写路径的存储故障。

空日志本身是同一个缺陷：每请求内存采样是 1/20，90 ms 的请求通常什么都不留。事后无法区分"我们的 handler 报了错"和"平台根本没调用我们"。

## 决策

**查询永不写。向量物化属于写侧；读侧只嵌入它要读的东西。**

- search **只读一次** manifest，用读到的东西作答：不 stage、不导出快照、不 `commitManifest`、无 CAS、无重试循环。不能写的读者不可能输掉比较交换，也不可能死于 `write_conflict` 或 `snapshot_changed`。
- search 的每个分区的 service **拒绝无向量记录的回填**（`allowBackfill: false`）。除非调用方在写路径上，文档不再嵌在提问里。
- 没有存储向量的记录**在 fold 回填之前按词面打分**——fold 是压缩作业，留在写路径上，带着它的 20 s 预算和一批 32 条。
- accept 已经嵌过的 pending 记录**向量随条目走**；融合直接用存储的向量打分，不再为文档文本调提供商。只有 accept 丢了嵌入预算的条目才把文本交给那一次批量调用。
- 老 receipt 不再由 search 拷入 manifest；fold（写方）负责回放。

这是同类引擎共同的形态：RocksDB 把压缩放进后台线程、MANIFEST 由压缩器记录；Hudi 保持 `hoodie.log.compaction.inline` 为 false，因为内联排程会"在写路径上加延迟"；Cassandra 的运维直接关掉 `read_repair_chance`，因为用它要付约 20% 的读负载而不带来任何保证，保留的部分也是异步的。我们此前同时踩了他们点名的三个：内联压缩、阻塞读修复、查询路径上的 CAS。

## 证据

| 测量                                                 | 值                                                                                                                                          |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 失败的 search                                        | 503、90 ms、53.4 MB、空日志                                                                                                                 |
| CAS 失败的最小时长                                   | 12 次 × manifest 读 ≈ 2.4 s 起——90 ms 的那次在此之前就已结束                                                                                |
| 修复后构建的串行 add+search 探针（干净网络、走代理） | 20 轮全 200，search p50 ≈ 1.4 s，第 16 轮折叠真实执行（`parts` 0→1），零失败                                                                |
| 零写入钉                                             | 新的等价测试断言两次 search 后 manifest **字节不变**、分区键不变；诊断计时阶段断言无 `partition_save` / `sqlite_export` / `manifest_commit` |
| 读复用钉                                             | 覆盖 pending 的 search 最多只做一次特征批量调用；已带向量的条目文本永不触达提供商                                                           |

## 这确立了什么、没有确立什么

- 那次 90 ms 503 的**确切成因无法事后复现**——它发生在旧构建上，而旧构建在读路径上 stage 并提交。本改动消灭的是这一整类（读路径 + CAS + stage 对象），不是钉死某一个异常。
- 查询做的功**多于幂等性所需**：两次相同 search 各自重读分区。这一点一直如此，本决策没有改变它。
- 无向量记录只有词面打分的窗口是真实的：内联向量部署之前接收的数据、或 accept 超过 8 s 预算丢失嵌入的数据，在它的 fold 到来之前只有词面分。fold 在写路径上以每次 32 条的速度回填，窗口按 fold 的节奏关闭。
- 尚未在部署构建上验证；本地套件（37 PASS）是目前唯一的证据。

## 考虑过的替代方案

- **保留 search 写入，加大重试，或把计数器放 KV。** staging 存在只为持久化 search 产出的东西（delta、回填向量、legacy receipt）。取消这些产物的生产，就取消了提交的理由；为一个读不需要做的写去修重试，是给更小的问题动更大的手术。
- **保留回填，仅在"确实变了"时才 stage。** 这正是旧设计（`readOnlyIfUnchanged`）：把常见情形转成读，把少见情形原样留下——而 503 正是少见情形。
- **由读路径触发折叠。** 从 search 折叠 = 读修复。按 Cassandra 的证据否决：它把写的代价放到每一次查询上。

## 后果

- 读路径剩下唯一一类失败：读到的东西缺失或不可读。这类错误是诚实的，带着 trace 以 `storage_corrupt` 上抛，而不是猜出来的 503。
- search 便宜了它不再上传的东西：每个变更分区的页 delta 和至多一次 manifest 写——对有分区的用户，每次回答省掉的是 MB 级。
- **测试的含义变了**：delta/snapshot 持久化等价测试退役，替真品断言的是负命题——两种情况下 search 都什么都不改。
- `stageSearchPart` 删除；随它一起消失的还有 search staging 的 reuse 管道。fold 和同步逃生通道仍用 `stagePart`。
- 每次请求现在必写一行 `nmg_request`（`trace_id, route, status, elapsed_ms, seq`），永不采样。handler 根本没跑的请求一行都不留——这正是"我们的代码失败了"与"平台没有调用我们"的分界线。调试模式下失败记录还带异常栈前六行。
