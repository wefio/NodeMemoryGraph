## teeth 检查抓到了什么

mutation harness 现在位于仓库的 `tools/mutation-teeth.ts`（`npm run mutation:teeth`），这是后来的仓库入口；它当前存在不复现旧 register、测试身份或计数。它对每个 target 报告三种结局——干净运行通过、每个 mutant 使套件失败**且**失败它的正是点名测试、文件被逐字节还原。在所报检查点，缺失／重复 marker 被拒绝而非半应用，存活项不算抓到。这是记录中的 harness 行为，不是对当前所有失败／恢复路径的新测试。把两个更早的本地 board-teeth 脚本折叠进来时，发现了一个正是该 harness 存在意义所在的 stale anchor：board-verdict mutant 仍指向 #56 之前的行，那里的 `accepted()` 自己拼接了裁决。重新指向它——然后检查**哪个**测试实际失败，而不是假定——显示该规则是被 `the board verdict is what accepts an artifact, not the round's own column` 抓到的。

新 mutant `assumption-may-carry-a-dependency` 在第一次运行中**未被抓到**，尽管本应抓到它的测试是通过的。问题出在 harness：每个 target 只列一个套件，而设计的用例住在一个新文件里，于是该 mutant 从未对着它们运行。harness 现在每个 target 接受一个套件列表。这与上面的 stale anchor 属于同一失败类——当被检查的东西移动时，检查自身的覆盖范围会漂移。

## 本工作不做什么

- **该检查点没有多轮命名空间。** 所报私有 store 持有一个 run：`ooo_probe_meta` 有 `CHECK(id=1)`，`ooo_probe_tasks` 只以 `id` 为键，board 通道是固定的 `ooo-process-probe`。设计把这三者点名为无法原样移入共享数据库的部分（当时第 229 行，不是稳定的当前定位）：该单运行表示无法测试跨 run 同 task ID。命名空间是注入共享事务 store 的前置条件，不是收尾整理。后续[研究 run 命名空间报告](ooo-run-namespace-2026-09-13.zh-CN.md)记录该切片；不是产品命名空间或新验证回执。
- 记录中的模型通过 `UNMODELLED_BY_MODEL` 排除 preparation、mergeability、真实验证、外部等待及墙钟；这是有范围的缺口列表，不是对所有当前调用者的审计。
- 所报通过覆盖至多四个单元、已声明模型计划／结局上的点名检查，不建立所有可能输入／计划，也不证明任意 Agent 程序正确（设计也如此限定）。
