## What the teeth check caught

The new mutant `assumption-may-carry-a-dependency` was **not** caught on the first run even though the
test that should catch it passes. The harness was the problem: each target listed one suite, and the
design's cases live in a new file, so the mutant was never run against them. The harness now takes a
list of suites per target. This is the same failure class as the earlier stale-anchor finding — the
check's own coverage drifts when the thing it checks moves.

Three of the harness's targets cover code that only exists on the retention branch, so its mutants
report "anchor not found, refusing to claim a check" there rather than passing quietly. The harness
therefore takes a `--targets` filter: here it ran the two semantics modules (10 mutants, 10 caught);
the full four-target run with 16 caught was measured on the branch that carries retention.

## What this does not do

- **No multi-round namespacing.** One private store still holds exactly one run: `ooo_probe_meta` has
  `CHECK(id=1)`, `ooo_probe_tasks` is keyed by `id` alone, and the board channel is the fixed
  `ooo-process-probe`. The design names these three as what cannot move into a shared database as-is
  (line 229), and it is right: "two rounds with the same taskId must not collide" is not testable
  until they change. This is the next slice, and it is a prerequisite for injecting the shared
  transaction store — not a tidy-up.
- The model still does not model preparation, mergeability, real verification, external waits or wall
  clock, and says so in `UNMODELLED_BY_MODEL`.
- Passing means this finite model satisfies the listed properties over at most four units. It does not
  prove an arbitrary agent program correct (the design says so too).
