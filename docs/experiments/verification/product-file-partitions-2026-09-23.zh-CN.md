# 产品测试文件分区探针（2026-09-23）

[English](product-file-partitions-2026-09-23.md) | [简体中文](product-file-partitions-2026-09-23.zh-CN.md) · [术语](product-file-partitions-2026-09-23.terms.yaml)

证据边界（2026-10-17 文档审阅）：下文耗时、测试计数、检查结果与工具／路由描述均属于其记录输入上的历史观察，不是对当前文档工作树的新检查。本次翻译审阅未执行套件、门禁、覆盖率运行或 benchmark；缺失的 run 身份或快照细节仍是明确的不确定性。

## 问题

用测得的测试耗时把每个测试文件分配到一组有界的进程中，能否让产品测试阶段更早结束？这里测量的是单个阶段，不是完整的验证时限，也不是替代闸门。

## 参照与差异

原始对比把 DSH 的 `test:coverage:partitioned` 描述为当时受支持的覆盖率路由。这是历史源码阅读背景，不是新的 DSH 审计，也不授权修改该仓库。其协调器把带覆盖率插桩的测试与重型豁免套件分开运行，因为插桩会成倍放大编译器与子进程夹具的运行时，而这些夹具对逐文件覆盖率阈值没有贡献。它在这些套件之间共享一个 worker 预算，要求所有分区都完成，并在作出覆盖率判定前合并覆盖率（`C:/Documents/GitHub/dsh/deepseek-harness/scripts/run-gates.ts`、`scripts/coverage-partitions.ts`）。

NMG 的产品测试使用 Node 测试运行器，且没有与之对应的逐文件覆盖率豁免契约。这并不排除采纳 DSH 的分区设计：先找出哪些 NMG 文件被插桩、启动、子进程或共享资源拖慢，再沿用针对这些成本的机制。本探针把按耗时加权的文件分配作为可能的机制之一来测试；把它单独成篇，便于与当前的 `test:product` 路由比较。

## 方法与结果

- 基线：既有的 `test:product` 文件 glob，用 Node 的 JUnit 报告器与 `--test-concurrency=4` 运行一次。报告包含 175 个不同的测试文件、1536 个通过的测试、80,594 ms 耗时。
- 候选：一个一次性脚本用基线的 JUnit 用例耗时把全部 175 个文件分配到四个分区。每个分区使用一个 Node 测试 worker。该脚本在报告结果前，把实际 JUnit 文件清单与测试总数与 profile 比对。
- 候选：各分区为 43/43/43/46 个文件与 356/358/396/426 个通过测试；全部 175 个文件与 1536 个测试都在。各分区耗时为 67,852/67,630/65,552/69,213 ms；整个候选耗时 69,254 ms。这一次运行比基线阶段快 11,340 ms（14.1%）。
- 候选输出 `comparison-only` 与 `fullGateRequired: true`，并在比较成功时以退出码 2 结束。它没有被接入 `test:product`、`agent:verify` 或 CI。

## 分区为何可能在这里有帮助

基线 JUnit 报告把 218.5 秒的用例时间归给 175 个文件。最长的三个文件分别贡献 35.7 秒（`tests/tools/agent-verify.test.ts`）、28.3 秒（`tests/rcp/reconcile.test.ts`）与 25.5 秒（`tests/cli/process.test.ts`）。第一个反复启动验证器、Git、npm 与 Node 子进程；第二个重复 Git 观察与对账；第三个启动 CLI/daemon 进程并包含显式等待。这些操作解释了文件耗时为何不均，但报告并没有分别隔离出它们各自的成本。

用同样的用例耗时做四 worker 贪心模拟：按字母顺序提供文件时，worker 负载为 51.7/69.7/50.1/47.0 秒；按最长优先放置时为 54.6/54.6/54.6/54.6 秒。这是一个调度模型，不是 Node 实际 worker 启动时间的轨迹：它省略了模块加载、进程建立与资源争用。它在最长模拟负载上减少的 15.1 秒与观察到的 11.3 秒阶段缩短是一致的。现有证据指向长尾调度气泡是最强解释，但不能证明进程分离本身既无收益也无成本。

公共测试运行时为每个测试工作区提供唯一临时目录，并把 daemon 的 HTTP 服务器绑定到端口 0（`tests/support/test-runtime.ts`）。复杂度闸门的探针名称包含进程 ID，并位于被忽略的 `.nmg/complexity-probes` 之下（`tools/complexity-gate.ts`），因此其测试中固定的 `probePath` 参数本身并不是共享的输出文件。当前完整验证器在启动 `test:product` 之前先完成构建/打包与静态检查（`tools/agent-verify.ts`、`src/rcp/verification.ts`），避免对生成的输入并发写入。这些是所测快照的源码阅读观察，不是穷尽的运行时共享资源审计。它们为有界文件并行试验提供依据；它们不确立产品测试与构建或静态检查重叠执行的安全性，也不确立提高总并发数的安全性。

DSH 的覆盖率豁免通道针对的是另一项实测成本：覆盖率插桩成倍放大重型夹具的运行时，却对其逐文件阈值没有贡献。NMG 尚未测得类似的插桩代价，也未确立豁免集，因此 DSH 设计中的这部分仍是开放假设。其按耗时加权的分配针对的正是本 profile 中可见的不均衡。

## 资源边界试验

既有的[无文件系统决策](../../decisions/implemented/2026-09-20-tests-need-no-filesystem.zh-CN.md)把候选 worktree 从纯数据检查中移除，因为这些检查并未断言工作区行为。四类资源及其夹具边界现已写在[测试运行时设计](../../design/ci-cd-and-quality.zh-CN.md#可组合测试运行时)中。下面的试验测量这些类别内部的具体改动；它们不改变 Safety/Contract/Guardrail 或窄范围/完整验证的成员资格。

在这台 Windows 检出上，40 次重复测得目录创建/删除为均值 0.258 ms（中位 0.228 ms），`NmgStore(":memory:")` 打开/关闭为均值 17.419 ms（中位 17.106 ms），文件后端 store 的打开/关闭（含唯一目录与删除）为均值 32.874 ms（中位 32.459 ms）。每次 store 构造都运行了 schema 迁移。这些摘要比较启动成本，而非整个测试的工作量。报告均值中目录创建相对 store 构造较小，但未提供离散度或不确定性区间，不能把它当作通用成本比例。

`tests/core/store.test.ts` 用其原先基于文件的 `withStore` 辅助函数有 52 个通过的测试，耗时 12.153 秒。45 处单连接调用被改为全新的内存 store；仍有七个显式的文件后端测试覆盖重开、外部读取器与迁移。同一文件在两次候选运行中分别用 9.363 秒与 8.706 秒通过 52/52。这是一次基线加两次候选的实机测量，因此差值只是暂定的；不能把差值全部归因于目录移除。慢的 FTS5 用例还写入 1,041 条记录，使数据库 I/O 也占其耗时的一部分。定向的完整 `agent:verify` 运行在 110.955 秒内、于 150 秒预算下通过了全部 13 项阻塞检查；`test:product` 用了 88.695 秒。该整阶段时间比更早的独立 80.594 秒基线更慢，因此这次运行确立的是正确性与时限合规，而不是可归因于夹具改动的端到端加速。

同一单连接判据也适用于 `tests/core/store/maintenance.test.ts` 中的 55 个维护测试：用文件 store 时全部通过，耗时 2.494 秒；改成每个测试使用全新内存 store 后为 1.470 秒。该文件没有任何重启或独立连接的断言。

`tests/tools/agent-verify.test.ts` 中有四个测试只断言路由测试失败/TAP 证据，却通过夹具运行了七个成功的共享 npm 检查。它们现在在这些夹具路由上声明既有的 `verify.sharedChecks: none`，同时保留真实 CLI、Git 发现、路由测试、回执与输出；另一个测试仍在默认窄范围模式下断言全部七个共享检查。28 个测试在改动前后都通过。在一次成对文件运行中，耗时从 32.672 秒降到 22.244 秒；四个受影响的用例合计从约 17.55 秒降到 5.53 秒。这测量的是定向运行中被避免的进程工作，不是完整闸门的加速。

RCP 仓库夹具是另一项资源试验。最初，全部 18 个 `tests/rcp/reconcile.test.ts` 用例都用 `init`、两条 `config` 命令、`add` 与 `commit` 初始化 Git；该文件耗时 22.153 秒。在 `commit` 上通过 `git -c` 提供身份，去掉了两个 config 子进程而不改变真实仓库边界；两次运行分别为 21.647/20.494 秒。随后检查显示，八个编排测试消费了 `RepositoryProvider` 观察，但并未断言 Git 发现、脏作用域或提交来源。这八个现在使用固定 provider 并跳过 Git 建立；十个作用域、失败与 forge 测试保留真实 provider 与仓库。全部 18 个测试在两次运行中分别为 13.802/13.776 秒通过。准确地说，八个使用固定 provider 的编排用例不再初始化 Git；其余每个真实 Git 夹具少两个 config 子进程。这是同一 Windows 检出上重复的文件级结果，不是端到端验证加速的证明。

随后的一次相邻整次运行 A/B 只在已提交的基线 blob（`fixture.ts` `3da0dd527ad9f7caf3b6892004423c39325478c4`、`reconcile.test.ts` `195f87ef6796431fc109b0869fcbe5704d8c56c4`）与候选 blob（`665a76f75ef850eb2070af1c0ed78cae79f33fad`、`a4bfa01a6237c7712922c79a086787736b56c7b0`）之间改动了这两个 RCP 测试文件。脏工作树其余部分保持不变，运行串行执行。两次 `agent:verify` 运行都通过了全部 13 项阻塞检查与 1536 个产品测试：基线整体 77.287 秒，其中 `test:product` 61.026 秒；候选整体 77.406 秒，其中 `test:product` 60.869 秒。成对差值（整体 +0.119 秒、产品测试 −0.157 秒）在该测量尺度上实际为零。没有记录 worker 启动轨迹，因此"更快的 RCP 文件不在该套件关键路径上"这一可能解释仍只是假设。这一对运行尽管有可重复的文件级下降，仍不确立整次运行的加速。

加上维护与仅路由夹具的改动后，一次定向的完整 `agent:verify` 运行在 101.832 秒内、于 150 秒预算下通过了全部 13 项阻塞检查；`test:product` 用 78.844 秒。在这两项改动之前的上一次完整运行用了 102.541 秒，其中 `test:product` 80.130 秒。这些未配对的整次运行样本过于接近且波动，无法确立整闸门加速。

对 28 个验证器测试的一次聚焦 c8 运行通过并报告 0%，因为这些测试没有执行 c8 include 集合中配置的任何源文件。原始 V8 blob 包含仓库 URL，但没有 `src/core` 之下的项。另一次针对 `tests/core/ann.test.ts` 的单文件探针为 `src/core/ann.ts` 产出 84.42% 覆盖率，因此 0% 的样本并不表明 c8 报告有缺陷。在 c8 的 0.01% 行下限下，五个范围外的工具测试通过，但覆盖率命令在 0% 处失败；而单个 ANN 测试在整体行覆盖率 0.38% 处通过。官方 `test:coverage` 路由随后在 126.454 秒内以 85.16% 行覆盖率通过了全部 1536 个测试。这些运行验证的是"非零证据"检查；它们不隔离出插桩豁免组，也不确立覆盖率质量目标。

## 界限与下一步决定

早先那一次 14.1% 的加速在当前工作树上没有重现。在单连接与仅路由夹具改动之后做的一次配对重跑使用了相同的 176 文件、1539 测试清单：普通 `test:product` 路由在 68.337 秒内通过（Node 报告 67.784 秒），而四个固定分区用了 87.067 秒。profile 描述的仍是先前那次 175 文件、1536 测试的运行；候选给新文件分配了中位回退权重，并从 JUnit 核验了每个当前文件与测试。各分区耗时为 68.856/83.405/80.403/86.999 秒。另一次单父进程 Node 运行把同样这 176 个文件按记录耗时从长到短提供，同时保留 `--test-concurrency=4`，在 75.453 秒内通过了全部 1539 个测试。当前两个候选都比未改动的路由更慢，因此候选代码与 profile 被移除，而不是被推广。

这些是在实机 Windows 检出上的一次配对基线/分区运行与一次按序运行，不是重复测量的分布。它们确立了先前的 14.1% 加速在该树上不可靠。旧的 JUnit 权重也早于对最长验证器测试文件的改动；启动与资源争用仍未被隔离。进一步的调度工作需要当前 profile 与重复的配对运行，才能替代 `test:product`。对当时的改动，报告保留了资源夹具削减和既有的 150 秒整次运行闸门，而没有推广分区候选；其回执不验证本轮后来修改的文档工作树。
